Module 01: Getting Started

In this module you will confirm that your cluster can serve models on IBM Z or IBM Power, inspect the pre-installed vLLM CPU ServingRuntime for KServe, and deploy a model with the Deploy a model wizard in the RHOAI dashboard.

Learning objectives:

  • Explain why the vLLM CPU ServingRuntime for KServe is the supported vLLM runtime on IBM Z and IBM Power

  • Check your cluster architecture and locate the pre-installed runtime from the CLI

  • Deploy a model from the RHOAI dashboard with the vLLM CPU ServingRuntime for KServe

  • Deploy the same model from the CLI with the real ServingRuntime and InferenceService manifests

  • Validate the result of every step

Exercise 1: Check your architecture and the pre-installed runtime

RHOAI Self-Managed is supported on x86_64, ppc64le, s390x, and aarch64 architectures, and IBM Power and IBM Z are explicitly supported deployment topologies. The vLLM CPU ServingRuntime for KServe is the runtime that brings vLLM to those architectures: the Red Hat supported configurations article describes it as "a high-throughput and memory-efficient inference and serving runtime that supports IBM Power (ppc64le) and IBM Z (s390x)".

Two constraints apply on these architectures:

  • No GPU accelerators. You cannot use GPU accelerators with IBM Z and IBM Power architectures. All compute for the model server comes from the CPU and memory resources you configure on the deployment.

  • Standard deployment mode only. For the vLLM CPU ServingRuntime for KServe, you can only deploy models in standard deployment mode — the KServe RawDeployment mode, not Knative Serverless.

Prerequisites

  • You are logged in to the workshop cluster with the working project you created in Getting Connected

Procedure

  1. Confirm the architecture of your cluster nodes:

    oc get nodes -o jsonpath='{.items[0].status.nodeInfo.architecture}'

    The output is s390x on IBM Z or ppc64le on IBM Power.

  2. Confirm that the RHOAI DataScienceCluster instance is ready:

    oc get dsc

    The READY column shows True for the DataScienceCluster instance, for example default-dsc.

  3. List the pre-installed serving runtimes shipped with RHOAI — they live in the redhat-ods-applications namespace:

    oc get servingruntimes -n redhat-ods-applications

    Exact resource names of pre-installed runtimes can vary between releases. Find the vLLM CPU runtime by its vllm-cpu name in the list.

  4. Inspect the container image that the vLLM CPU runtime uses. The default resource name is vllm-cpu-runtime; adjust it if the name you found in the previous step differs:

    oc get servingruntime vllm-cpu-runtime -n redhat-ods-applications -o jsonpath='{.spec.containers[0].image}'

    The output shows the Red Hat-provided vLLM CPU container image from registry.redhat.io.

Verify

The architecture command returned s390x or ppc64le, the DataScienceCluster instance reports READY: True, and the serving runtime list includes the vLLM CPU ServingRuntime for KServe. If the runtime list is empty or the runtime is missing, ask your workshop facilitator to enable the pre-installed model-serving runtimes in the RHOAI dashboard under Settings, Serving runtimes.

Locating the runtime is only half the story — next you deploy an actual model with it from the dashboard.

Exercise 2: Deploy a model from the dashboard

You can deploy generative AI (gen AI) or predictive AI models on the model serving platform by using the Deploy a model wizard. The wizard lets you configure the model location and type, select a serving runtime, assign a hardware profile, and set advanced configurations like external routes and token authentication.

Prerequisites

  • The model serving platform is enabled and the vLLM CPU ServingRuntime for KServe is enabled in your cluster

  • A project exists (you created one in Getting Connected)

  • Your model is stored in a location accessible to the model server and a connection to it exists in your project: an OCI-compliant registry, S3-compatible object storage, a URI, or a persistent volume claim (PVC)

Procedure

  1. In the RHOAI dashboard, click Projects in the left menu.

  2. Click the name of your working project. The project details page opens.

  3. Click the Deployments tab.

  4. Click Deploy model. The Deploy a model wizard opens.

  5. In the Model details section, provide information about the model:

    1. From the Model location list, specify where your model is stored and complete the connection detail fields. The OCI-compliant registry, S3 compatible object storage, and URI options are preinstalled connection types. If you uploaded model files to a PVC attached to your workbench, the Cluster storage option becomes available and you can select the PVC and the path to the model file.

    2. From the Model type list, select Generative AI model.

    3. Click Next.

  6. In the Model deployment section, configure the deployment:

    1. In the Model deployment name field, enter a unique name for your model deployment.

    2. In the Description field, enter a description of your deployment.

    3. From the Hardware profile list, select a hardware profile.

    4. Optional: To modify the default resource allocation, click Customize resource requests and limits and enter new values for the CPU and Memory requests and limits.

    5. In the Serving runtime field, select Select from a list of serving runtimes, including custom ones and choose the vLLM CPU (ppc64le/s390x) ServingRuntime for KServe.

    6. In the Number of model server replicas to deploy field, specify a value.

    7. Click Next.

  7. In the Advanced settings section, configure the remaining options:

    1. Optional: Select the Model access checkbox to make your model deployment available through an external route. Keep this selected for the inference exercises in Module 02.

    2. Select Require token authentication and enter vllm-demo-sa as the Service account name that the token will be generated for. Use this same service account name in the inference exercises in Module 02.

    3. Optional: Select Add custom runtime arguments or Add custom runtime environment variables to add configuration parameters to your deployment.

    4. In the Deployment strategy section, select Rolling update or Recreate.

    5. Click Deploy.

There are no GPUs to request on IBM Z and IBM Power. Size the deployment through the CPU and Memory requests and limits in the Customize resource requests and limits step — this is where all of your model server compute comes from.

Verify

Confirm that the deployed model is shown on the Deployments tab for the project, and on the Deployments page of the dashboard with a checkmark in the Status column. Loading a model on CPU-backed nodes can take several minutes depending on the model size and the resources you requested.

The model is deployed. In the next module you verify the deployment from the CLI and send authenticated inference requests to it.

Exercise 3: Deploy the same model from the CLI

The wizard Deploy step creates a KServe InferenceService resource in your working project. Every field you set in the wizard has a manifest equivalent, so you can also deploy the same model from the terminal — and see exactly what the wizard generates when you deploy through the dashboard.

Prerequisites

  • You are logged in to the workshop cluster and working in the project you created in Getting Connected

  • The model serving platform is enabled with the vLLM CPU ServingRuntime for KServe (Exercise 1)

Procedure

  1. KServe resolves the spec.predictor.runtime from the deployment’s own namespace, so instantiate the pre-installed vLLM CPU runtime template into your project. The template carries the Red Hat s390x / ppc64le vLLM CPU container image from registry.redhat.io:

    oc process -n redhat-ods-applications vllm-cpu-runtime-template \
  | oc apply -n abc123-user1 -f -

    On x86_64 clusters the template is named vllm-cpu-x86-runtime-template and the instantiated runtime is vllm-cpu-x86-runtime. Exact resource names of pre-installed runtimes can vary between releases — list them with oc get templates -n redhat-ods-applications | grep vllm-cpu if the name differs.

  2. Stamp the template-origin annotations the dashboard expects on the instantiated runtime:

    oc annotate servingruntime vllm-cpu-runtime -n abc123-user1 \
  opendatahub.io/template-name=vllm-cpu-runtime-template \
  opendatahub.io/template-display-name="vLLM CPU (ppc64le/s390x) ServingRuntime for KServe" \
  --overwrite

  3. Deploy the model. The manifest mirrors the wizard choices from Exercise 2: standard deployment mode (RawDeployment — the only mode on IBM Z and IBM Power), an OCI modelcar URI for the model location, CPU resource bounds instead of GPU requests, and vLLM runtime arguments:

The model pulls the modelcar image and reports READY in a few minutes on a CPU-backed node.

  4. Enable token authentication the way the wizard does — create the service account you entered as Service account name and its token Secret. If you deployed through the wizard in Exercise 2, these already exist and the commands confirm them:

    oc create serviceaccount vllm-demo-sa -n abc123-user1
cat <<'EOF' | oc apply -f - -n abc123-user1
apiVersion: v1
kind: Secret
metadata:
  name: vllm-demo-sa
  annotations:
    kubernetes.io/service-account.name: vllm-demo-sa
type: kubernetes.io/service-account-token
EOF

Verify

The instantiated vLLM CPU runtime exists in your project and the inference service reports Ready: True:

+ The predictor pod is Running:

+

Module summary

What you accomplished:

  • Confirmed your cluster architecture is s390x (IBM Z) or ppc64le (IBM Power) and located the pre-installed vLLM CPU ServingRuntime for KServe

  • Deployed a generative model from the RHOAI dashboard with the Deploy a model wizard, selecting the vLLM CPU runtime and configuring CPU and memory resources

  • Deployed the same model from the CLI with the real ServingRuntime template instantiation and InferenceService manifest

  • Verified the deployment shows a checkmark in the Status column on the Deployments tab

Key takeaways:

  • The vLLM CPU ServingRuntime for KServe is the only supported vLLM path on IBM Z (s390x) and IBM Power (ppc64le) — GPU accelerators cannot be used with those architectures

  • On IBM Z and IBM Power you can only deploy models in standard deployment mode (KServe RawDeployment), not Knative Serverless

  • On CPU-only architectures, model server capacity is controlled entirely by the CPU and Memory requests and limits in the deployment wizard
