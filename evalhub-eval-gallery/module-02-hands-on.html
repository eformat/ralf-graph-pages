Module 02: Hands-on — the Mode 4 demo flow

In this module you drive the kitchensink Mode 4 demo flow end to end for the curated evaluation collection gallery (evalhub-eval-gallery): one step per section, each with concrete commands and the evidence capture expected at that step. Mode 4 is the workshop factory’s locked recipe for producing feature demos as self-correcting units — every step leaves evidence, and every claim in the final content is bound to a capture.

The demo surface of this feature is the GA back end: the EvalHub collections API and the cluster objects behind it. The hands-on in this module is therefore read-only against the cluster — every command inspects state, and nothing here creates, modifies, or removes a cluster object. The demo runtime is GitOps-owned platform state; the one additive change you will make (authoring your own collection) comes in Module 03.

Learning objectives:

  • Stage the environment: connect to the cluster, mint a bearer token, and reach the EvalHub back-end health endpoint

  • Record evidence with capture discipline at every step of the flow

  • Author the in-tree artifacts: the workshop content and the additive deploy/ manifests

  • Build — verify read-only what the platform materialized: the evalhub custom resource and the collection ConfigMaps

  • Validate: enumerate the three curated collections through the collections API, and honestly record the Tech-Preview UI’s empty gallery state

  • Integrate: files land in the assets repo, pages publish, the daily digest records the run

The flow is idempotent: re-running any step against an already-satisfied state is a no-op that still records evidence.

Exercise 1: ENV — connect and reach the back end

The environment has one gate: a cluster session whose bearer token the EvalHub API accepts, and a back end that answers.

  1. Connect to the cluster (Getting Connected covers the login flow in depth), then export the back-end URL and mint the token:

oc login https://api.cluster.example.com:6443 --username user1 --password %password%
oc whoami
export EVALHUB_URL="https://evalhub-redhat-ods-applications.apps.cluster.example.com"
export TOKEN=$(oc whoami -t)

The route host is the EvalHub back-end service in the redhat-ods-applications namespace under your cluster’s ingress domain — evalhub-redhat-ods-applications.<ingress-domain>. If your facilitator published a different URL for the EvalHub API, export that instead.

  1. Evidence the token by checksum, never by value:

echo "token sha256:$(oc whoami -t | sha256sum | cut -c1-12)…"

  1. The health probe needs no authentication — a plain GET answers:

curl -sS "$EVALHUB_URL/api/v1/health"

Expected output (real capture; the timestamp differs on your run):

{"status":"healthy","timestamp":"2026-11-27T00:30:59.137720471Z"}

Capture (ENV)

Submit one command capture bundling the three outputs above with a UTC timestamp header: your username (oc whoami), the token checksum (never the token value), and the health probe.

Verify

oc whoami prints your workshop username — prelude on the cluster where this module was captured — oc whoami -t mints a bearer token (50 bytes in the verified capture, evidenced by its SHA-256 prefix 2edb63d17659), and the health endpoint returns "status":"healthy".

Exercise 2: RECORD — capture-first discipline

Every subsequent step produces evidence before any claim is written down. The factory evidence pipe accepts captures of these kinds:

Kind Used for

screenshot

UI states — the Tech-Preview AI Evaluations pages, including the empty gallery state you will meet in Exercise 5

video

End-to-end walkthroughs (the arcade demo recording)

frame

Single extracted frames from a recording

ffprobe

Recording format proof (resolution, duration, codec)

log

Command output bundles, page trees, digests

command

Single command + output pairs

validator

Automated check results (JSON parse checks, link checks)

The discipline rules:

  1. Capture before you claim. A fact without a capture ID is refused by the engine — and a claim without a fact is invisible to the graph.

  2. One step, one capture. The capture content is the raw command output or screenshot, timestamped; summaries stay one line.

  3. Never fabricate. If a step fails, capture the failure — a blocked state with honest evidence is a valid outcome; a fabricated pass is the cardinal sin. For this feature that rule bites in Exercise 5: the Tech-Preview gallery renders empty, and that empty state is the evidence.

  4. Checksums over values. Secrets are evidenced by length and SHA-256 prefix, never by printing them — exactly how Exercise 1 handled the bearer token.

Capture (RECORD)

Practice the discipline once: submit a command capture of the health probe from Exercise 1 — the exact command and its raw output, timestamped.

Verify

Your capture exists and carries real content — the exact command and its output, not a description of what you saw.

Exercise 5: VALIDATE — enumerate the curated collections

Validation has two halves, and they disagree — that disagreement is the lesson of this feature. The GA back end enumerates the curated collections reliably; the Tech-Preview UI honestly shows an empty gallery.

  1. Enumerate the collections through the API. Three headers: your bearer token, the tenant namespace (where EvalHub runs), and the tenant user:

curl -sS \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant: redhat-ods-applications" \
  -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections" \
  | jq '.total_count'

Expected output (real capture):

3

X-Tenant is the EvalHub namespace, redhat-ods-applications. X-User is the tenant identity — prelude on the cluster where this module was captured; use the tenant user your facilitator specifies. The token is the same one oc whoami -t minted in Exercise 1.

  1. Get the names and benchmark counts — they must match the Module 01 table:

curl -sS -H "Authorization: Bearer $TOKEN" -H "X-Tenant: redhat-ods-applications" -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections" \
  | jq -r '.items[] | "\(.name) — \(.benchmarks | length) benchmarks"'

Expected output (real capture):

Toxicity and Ethical Principles — 3 benchmarks
Safety and Fairness — 6 benchmarks
Open LLM Leaderboard v2 — 6 benchmarks

The same three collections with the same benchmark counts (3, 6, 6) and the same thresholds as Module 01 — enumerated live from the back end rather than hard-coded.

The endpoint returns a pagination envelope, not a bare array:

{"first":{"href":"/api/v1/evaluations/collections"},"limit":50,"total_count":3,"items":[…]}

total_count is the collection count and items is the page. A naive jq '. | length' returns 4 — the number of envelope keys — not the number of collections. Count with .total_count (or .items | length).

  1. The UI half — and the honest part. Open https://rh-ai.apps.cluster.example.com/evaluation and select the Gallery tab. It renders the Tech-Preview empty state — "No collections found / No collections are available" — even though the API just enumerated three curated collections. That skew is a known UI/API version issue: Module 03 walks the root cause (the UI sends a query parameter the back end rejects) and the API workaround you are using right now. Capture the empty state as screenshot evidence — an honestly blocked UI is valid evidence.

Capture (VALIDATE)

Submit a command capture of the enumeration (count and names) and a screenshot capture of the gallery empty state with the Tech-Preview banner visible.

Verify

total_count is 3, the names match the Module 01 table, and the UI gallery empty state is recorded honestly rather than worked around. If the enumeration returns an error instead, record the blocked state with the capture — the flow is still complete; the content documents the blocked verdict.

The collections API query contract

The back end (evalhub 1.0.3) validates query parameters strictly, and namespace is not a valid one. This is worth verifying yourself — it is the exact request the Tech-Preview UI sends, and the exact failure behind the empty gallery:

curl -sS -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant: redhat-ods-applications" \
  -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections?namespace=redhat-ods-applications"

Expected output (real capture):

400

And the response body:

curl -sS -H "Authorization: Bearer $TOKEN" -H "X-Tenant: redhat-ods-applications" -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections?namespace=redhat-ods-applications"

Expected output (real capture; the trace id differs on every request):

{"message_code":"query_bad_parameter","message":"The parameter 'namespace' is not a valid query parameter. Allowed parameters are: limit, offset, name, category, tags, owner, scope, domains, tasks, modalities, industries, evaluation_targets, sort_by.","trace":"68408dbb-09c8-403d-8e02-c0576a0cd9fa"}

The contract, verbatim from the back end:

  • Rejected: namespace — HTTP 400, query_bad_parameter. This is a product-level UI/API version skew (the eval-hub-ui sends it), not something you can fix from the cluster — see Module 03.

  • Allowed: limit, offset, name, category, tags, owner, scope, domains, tasks, modalities, industries, evaluation_targets, sort_by — the pagination, filtering, and sorting surface.

  • The verified working request carries no query parameters at all — the plain GET returns every curated collection.

Verify

The rejected probe returns 400 with query_bad_parameter naming the allowed set verbatim, and the plain GET — no query parameters — returns total_count: 3 with the three curated collections. That pairing is the whole contract: authenticate with the three headers, add nothing else.

Exercise 6: INTEGRATE — land the files, publish, digest

Integration is where the flow closes: files land in the assets repo, the site rebuilds, and the factory’s daily digest records the run.

  1. Check the working tree is exactly the set of files you intended — nothing else:

  1. The integration contract for this workshop factory:

    • The engine owns git — the engine’s git writer commits the staged files to the assets repo; workers never run git commit or git push.

    • The engine builds pages — after meaningful content commits the publisher runs the Antora build and pushes the site; the component appears in the catalog once its content source is registered in the site playbook.

    • The graph carries outcomes — facts, findings, and captures record what happened; transcripts are disposable.
