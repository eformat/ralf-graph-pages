Module 03: Advanced — the AI Evaluations UI and your own collection

Module 02 verified the GA back end: the collections API enumerated the three curated collections with the three-header request. This module walks the other half of the experience — the AI Evaluations UI in the RHOAI console, which is badged Tech Preview — exactly as it behaves on a live RHOAI 3.6 cluster, including a known issue where the Gallery tab renders empty while the GA API serves three curated collections. The module closes with the one additive change this workshop makes to the cluster: authoring a custom evaluation collection as a new ConfigMap in a demo namespace, using this feature’s deploy/ artifacts.

Learning objectives:

  • Walk the AI Evaluations UI: sign in to the console, open Develop & train → Evaluations, and identify the Technology Preview banner, the project selector, and the Gallery | Benchmark collections | Runs tabs

  • Diagnose the known Gallery-empty issue to its root cause — a product-level UI/API version skew — and apply the API workaround from Module 02

  • Apply the transferable debugging lesson: when a preview UI and a GA API disagree, capture the failing request, read the error body, and fall back to the API contract

  • Author a custom evaluation collection as an additive ConfigMap in a demo namespace, and state honestly what the platform does — and does not — serve

Exercise 1: Walk the AI Evaluations UI

The AI Evaluations UI ships inside the RHOAI dashboard at https://rh-ai.apps.cluster.example.com. Sign-in is Keycloak OIDC federated to your OpenShift workshop credentials — the same username and password as oc login (Getting Connected covers the flow):

After sign-in you land on the dashboard’s Projects page. A one-time "Welcome to OpenShift AI 3.6!" guided-tour dialog may open — close it and continue:

Now walk to the feature:

  1. In the left navigation, expand Develop & train and select Evaluations. The nav entry carries an orange Tech Preview badge — the first honest signal of the maturity split you read about in the Overview.

  2. The AI Evaluations page opens at https://rh-ai.apps.cluster.example.com/evaluation and shows, top to bottom:

    • An information banner, verbatim: "The AI Evaluations UI is in Technology Preview; the AI Evaluations back end is Generally Available."

    • A Project selector — ai-tenants on the cluster where this workshop was captured; select the project your evaluations belong to.

    • The page copy, verbatim: "Evaluate models using curated benchmark collections. Start with a curated collection, customize it, or create your own. Add a collection to your project to use it in your evaluations."

    • Three tabs: Gallery | Benchmark collections | Runs.

  3. Open the Benchmark collections tab. This is what the UI shows even while the Gallery list is empty:

Two cards render verbatim:

  • Create your own collection — "Build a reusable collection by selecting benchmarks, setting thresholds, and configuring pass criteria." with a Create collection button.

  • Browse all benchmarks — "Explore 100+ individual benchmarks across all evaluation frameworks to run a one-off evaluation." with an Explore button.

The Create your own collection card is the UI-side invitation to exactly the authoring pattern you will exercise in Exercise 3 below — with one honest caveat about serving, documented there.

Captured evidence for this walkthrough covers the sign-in page, the dashboard landing, the Gallery tab’s empty state, and the Benchmark collections tab. The third tab, Runs, is visible in the tab strip of every captured page, but no Runs-tab content state was captured for this workshop — this page deliberately does not describe what it did not capture.

You can also state which parts of the walkthrough are backed by captured screenshots — and that the Runs tab is not.

Exercise 2: The Gallery tab’s known issue — a UI/API skew debugging lesson

Back on the Gallery tab you see the empty state. Search field, magnifier icon, and the message pair "No collections found / No collections are available." — with the Technology Preview banner still above and the Evaluations [Tech Preview] nav entry still highlighted:

You just watched the API enumerate three curated collections in Module 02. The empty gallery is not a broken cluster — it is a known product issue, and it is the lesson of this module.

Known issue in 3.6: the Gallery tab renders "No collections found / No collections are available" even though the GA back end serves three curated collections. The root cause is a UI/API version skew: the eval-hub-ui queries

/eval-hub/api/v1/evaluations/collections?namespace=<project>&limit=200&scope=system&sort_by=curation_order

but evalhub 1.0.3 rejects the namespace query parameter outright (HTTP 400, query_bad_parameter). The same request without the namespace parameter returns all three curated collections. This is a product-level skew between the Tech Preview eval-hub-ui and the GA evalhub back end — both pinned in GitOps-owned images, so it is not something a workshop user can fix with oc. The dependable surface is the API: the plain GET with the Authorization + X-Tenant + X-User headers — the exact request you verified in Module 02.

The transferable debugging lesson — practice it on this skew:

  1. Capture the failure. An honestly blocked UI is valid evidence: screenshot the empty state as-is (the RECORD discipline from Module 02).

  2. Read the error body. Re-issue the failing request from the CLI and let the back end speak — message_code, message, and the allowed-parameter list.

  3. Diff the requests. The UI appends namespace=<project>; the verified working request carries no namespace at all.

  4. Fall back to the API contract. File the skew as a product issue against the GitOps-owned images and keep the demo on the API surface.

Reproduce the skew from the terminal. Connect and export the back-end URL and token exactly as in Module 02 (the UI reaches the same back end through the platform gateway’s /eval-hub path; the CLI reaches it through the route host directly):

oc login https://api.cluster.example.com:6443 --username user1 --password %password%
export EVALHUB_URL="https://evalhub-redhat-ods-applications.apps.cluster.example.com"
export TOKEN=$(oc whoami -t)

This is the UI’s request — namespace included. Watch it fail:

curl -sS -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant: redhat-ods-applications" \
  -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections?namespace=redhat-ods-applications"

Expected output (real capture):

400

And the body — the back end names the rejected parameter and the allowed set verbatim (the trace id differs on every request):

curl -sS \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant: redhat-ods-applications" \
  -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections?namespace=redhat-ods-applications"

Expected output (real capture):

{"message_code":"query_bad_parameter","message":"The parameter 'namespace' is not a valid query parameter. Allowed parameters are: limit, offset, name, category, tags, owner, scope, domains, tasks, modalities, industries, evaluation_targets, sort_by.","trace":"68408dbb-09c8-403d-8e02-c0576a0cd9fa"}

Now the workaround — the same request without the rejected parameter:

curl -sS \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant: redhat-ods-applications" \
  -H "X-User: prelude" \
  "$EVALHUB_URL/api/v1/evaluations/collections" \
  | jq '.total_count'

Expected output (real capture):

3

Verify

The namespace-laden request returns 400 with query_bad_parameter, and the plain GET returns total_count: 3 — while the Tech Preview Gallery tab in the browser still renders its empty state. That disagreement, observed in one session, is the UI/API skew: the images are GitOps-owned, so the fix belongs to the product, and your reliable demo surface is the API.

Exercise 3: Author your own collection — the additive ConfigMap pattern

Module 01 established the storage model: curated collections are materialized as collection ConfigMaps, with a single data key named <collection-id>.yaml holding the collection spec. Authoring your own collection means writing exactly that shape — additively: a new ConfigMap with a distinct name, in a namespace you own. This feature’s deploy/ tree ships the artifacts; nothing here touches a GitOps-owned resource.

From the feature’s deploy/ directory, apply the two additive manifests:

cd features/evaluation/evalhub-eval-gallery/deploy
oc apply -f manifests/00-namespace.yaml
oc apply -f manifests/10-sample-collection-configmap.yaml

Expected output (real capture):

namespace/evalhub-eval-gallery-demo created
configmap/evalhub-collection-workshop-sample-v1 created

What you just created:

  • evalhub-eval-gallery-demo — a dedicated demo namespace (manifests/00-namespace.yaml).

  • evalhub-collection-workshop-sample-v1 — a sample collection ConfigMap (manifests/10-sample-collection-configmap.yaml) whose data shape mirrors the live operator-rendered ConfigMaps exactly: one data key, workshop-sample-v1.yaml, holding id, name, category, domains, tasks, modalities, evaluation_targets, curation_order, description, tags, pass_criteria, and benchmarks with provider_id / weight / primary_score / pass_criteria. Its benchmark entries are lifted verbatim from the live leaderboard-v2 collection; the workshop-authored deltas are the id (workshop-sample-v1), the name, the tags (workshop, sample), the curation_order (100), and the collection-level threshold (70.0).

Read back what the platform materialized:

oc get configmap -n evalhub-eval-gallery-demo

Expected output (real capture; the AGE differs on your run):

NAME                                             DATA   AGE
evalhub-collection-workshop-sample-v1            1      5m

Now confirm the GA catalog end to end with the tree’s read-only verify script — it probes /api/v1/health, then the collections API, then asserts exactly 3 curated collections (and self-guards against ever sending the namespace parameter from Exercise 2):

scripts/verify-catalog.sh

Expected output (real capture, abridged; the timestamp and ages differ on your run):

[1/3] GET /api/v1/health (no auth) ...
  {"status":"healthy","timestamp":"2026-11-27T00:38:33Z"}
  OK: healthy

[2/3] GET /api/v1/evaluations/collections (Bearer + X-Tenant + X-User) ...
  OK: response received (pagination envelope)

[3/3] assert 3 curated collections ...
  OK: total_count=3, items=3

Curated collections:
  - Toxicity and Ethical Principles  [toxicity-and-ethical-principles]  3 benchmark(s), category=safety
  - Safety and Fairness  [safety-and-fairness-v1]  6 benchmark(s), category=safety
  - Open LLM Leaderboard v2  [leaderboard-v2]  6 benchmark(s), category=general

PASS: catalog healthy, 3 curated collections served.

What this sample is — and honestly is not. The evalhub Deployment consumes collections through a projected volume (evalhub-collections, mounted at /etc/evalhub/config/collections) whose sources list exactly the ConfigMaps named in the GitOps-owned EvalHub CR spec.collections — the three curated ConfigMaps in redhat-ods-applications. Your demo-namespace ConfigMap is the authoring pattern made tangible: it is not mounted into the back end and not served by the collections API — which is why the verify script still asserts exactly 3 collections. Serving a custom collection requires adding it to the GitOps-owned EvalHub CR, a platform-level change that belongs in the platform’s cluster/ directory and is deliberately out of scope for this workshop. Hand the tested manifest to your platform team.

Clean up when you are done — the demo namespace removal takes the sample ConfigMap with it, and nothing in redhat-ods-applications is touched:

oc delete -f manifests/10-sample-collection-configmap.yaml
oc delete -f manifests/00-namespace.yaml

Expected output:

configmap "evalhub-collection-workshop-sample-v1" deleted
namespace "evalhub-eval-gallery-demo" deleted

Verify

The read-back lists evalhub-collection-workshop-sample-v1 in the evalhub-eval-gallery-demo namespace with one data key, the verify script passes with total_count=3, items=3 and the three curated collection names from Module 01, and you can state the mechanism honestly: the sample ConfigMap is the authoring pattern — it is not mounted, not served, and serving it would require a platform-level change to the GitOps-owned EvalHub CR. After cleanup the cluster holds no trace of the demo namespace.

What you accomplished:

  • Diagnosed the Gallery-empty known issue to its root cause — the UI’s namespace query parameter rejected by evalhub 1.0.3 with query_bad_parameter — reproduced it from the CLI, and applied the API workaround from Module 02

  • Authored a custom evaluation collection as an additive ConfigMap in the evalhub-eval-gallery-demo namespace from the deploy/ artifacts, verified the GA catalog end to end, and cleaned up

Key takeaways:

  • The AI Evaluations UI is Tech Preview; the back end is GA. Walk the UI as it behaves and keep the demo surface on the API

  • When a preview UI and a GA API disagree: capture the failure, read the error body, diff the requests, fall back to the API contract — and file the skew against the GitOps-owned images rather than patching the cluster

  • Custom collections are authored additively as new ConfigMaps in your own namespace; serving them is a platform-level change to the EvalHub CR
