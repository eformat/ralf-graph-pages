Module 03: Advanced Usage

In this module you will go beyond the basic RAG loop from Module 02: compare retrieval search modes directly in pgvector, learn the high-availability and autoscaling knobs on the OGXServer custom resource, reproduce the whole OGX stack as a second server from the same blueprint, understand the MaaS facade pattern that keeps the AutoRAG wizard working, and inspect the PostgreSQL storage layer that everything above it depends on. The module closes with two forward-looking sections — external S3 file storage and OAuth token authentication — that require a newer OGX build than the one running here.

Learning objectives:

  • Compare keyword, vector, and hybrid retrieval modes directly against a pgvector table

  • Configure replicas, disruption budgets, topology spread, and autoscaling on the OGXServer CR

  • Reproduce the OGX stack: two Ready servers deployed from one distribution digest

  • Explain the MaaS facade pattern and why the AutoRAG wizard needs it

  • Inspect the pgvector storage layer that backs the server

Exercise 1: Choose a retrieval search mode

Retrieval quality depends on how you match a question against stored chunks. Three search modes offer different tradeoffs in precision, recall, and computational cost:

  • Keyword search — lexical matching (TF-IDF, BM25). Effective when precise term-matching is required, such as searching for identifiers, names, or regulatory terms. It finds nothing when your wording does not overlap the documents.

  • Vector search — encodes documents and queries as embeddings and measures similarity with cosine distance. Captures semantic meaning beyond exact word overlap.

  • Hybrid search — blends lexical and semantic rankings to balance exact term matching with semantic similarity.

Module 02 ended with a pgvector table you built by hand. You can demonstrate all three modes against that same kind of table using plain SQL — which has the bonus that you see each mode’s scoring instead of treating retrieval as a black box.

Every step below uses a throwaway table named ogx_module03_modes that you drop at the end — the exercise leaves the shared environment exactly as it found it. Do not create or modify any other database objects.

  1. Reconnect to the MaaS facade from Module 02 (it computes the embeddings for this exercise):

    export FACADE="https://$(oc -n autorag-ml-demo get route aml-maas-facade-tls -o jsonpath='{.spec.host}')"

  2. Write three small documents with deliberately different vocabularies:

    mkdir -p chunks
cat > chunks/c1.txt <<'EOF'
OGX servers are configured declaratively: the OGXServer custom resource wires
vLLM inference providers, a pgvector vector store, and PostgreSQL storage into
a single workload, and the OGX Operator reconciles it.
EOF
cat > chunks/c2.txt <<'EOF'
RAG — retrieval-augmented generation — reduces hallucinated answers by
grounding the model in your own documents instead of relying on what the
model memorized during training.
EOF
cat > chunks/c3.txt <<'EOF'
pgvector adds a vector column type and cosine distance operators to
PostgreSQL; ivfflat and hnsw indexes keep nearest-neighbour queries fast as
the corpus grows.
EOF

  3. Create the throwaway table and ingest the chunks — embed each through the facade, then insert the vector:

    TABLE=ogx_module03_modes
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -c "CREATE TABLE $TABLE (id text, source text, content text, embedding vector(1024))"
for f in chunks/c*.txt; do
  id=$(basename "$f" .txt)
  vec=$(curl -s "$FACADE/v1/embeddings" -H 'Content-Type: application/json' \
        -d "$(jq -n --arg t "$(cat "$f")" '{model:"aml-bge-m3", input:$t}')" \
        | jq -r '.data[0].embedding | join(",")')
  body=$(sed "s/'/''/g" "$f")
  oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
    -c "INSERT INTO $TABLE (id, source, content, embedding) VALUES ('$id', '$id.txt', '$body', '[$vec]')"
done

    Expected output: CREATE TABLE, then three INSERT 0 1 lines, one per chunk.

  4. Keyword mode. Embed the question, then rank with PostgreSQL full-text search. Only chunks that lexically contain the query words score at all:

    QUERY="How does RAG reduce hallucinated answers?"
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx -c \
  "SELECT id, round(ts_rank(to_tsvector('english', content), q.tsq)::numeric, 4) AS keyword_score
   FROM $TABLE, (SELECT plainto_tsquery('english', '$QUERY') AS tsq) q
   WHERE to_tsvector('english', content) @@ q.tsq
   ORDER BY keyword_score DESC"

    Expected output — exactly one chunk matches, because it is the only one sharing the query’s vocabulary:

     id | keyword_score
----+---------------
 c2 |        0.4383
(1 row)

  5. Vector mode. Rank the same table by cosine similarity against the query embedding. Now every chunk gets a score, ranked by meaning rather than by shared words:

    VEC=$(curl -s "$FACADE/v1/embeddings" -H 'Content-Type: application/json' \
      -d "$(jq -n --arg t "$QUERY" '{model:"aml-bge-m3", input:$t}')" \
      | jq -r '.data[0].embedding | join(",")')
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx -c \
  "SELECT id, round((1 - (embedding <=> '[$VEC]'))::numeric, 4) AS similarity
   FROM $TABLE ORDER BY embedding <=> '[$VEC]'"

    Expected output — the RAG chunk still ranks first, but the semantic neighbours are ranked too:

     id | similarity
----+------------
 c2 |     0.7750
 c3 |     0.3336
 c1 |     0.3141
(3 rows)

  6. Hybrid mode. Reciprocal rank fusion (RRF) combines the two rankings: each chunk earns 1/(k + rank) points from every list it appears on, with k = 60 dampening the influence of any single list. A chunk ranked first on both lists wins; a chunk first on one list and last on the other can lose to a chunk ranked second on both:

    oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx -c \
  "WITH s AS (
     SELECT plainto_tsquery('english', '$QUERY') AS tsq, '[$VEC]'::vector AS vec
   ),
   kw AS (
     SELECT id, row_number() OVER (ORDER BY ts_rank(to_tsvector('english', content), s.tsq) DESC, id) AS keyword_rank
     FROM $TABLE, s
   ),
   ve AS (
     SELECT id, row_number() OVER (ORDER BY embedding <=> s.vec) AS vector_rank
     FROM $TABLE, s
   )
   SELECT m.id, kw.keyword_rank, ve.vector_rank,
          round((1.0/(60 + kw.keyword_rank) + 1.0/(60 + ve.vector_rank))::numeric, 5) AS rrf_score
   FROM $TABLE m
   JOIN kw ON kw.id = m.id
   JOIN ve ON ve.id = m.id
   ORDER BY rrf_score DESC"

    Expected output — c2 is ranked first by both lists and wins; c1 and c3 split the second place between them, each having traded a better rank on one list for a worse rank on the other:

     id | keyword_rank | vector_rank | rrf_score
----+--------------+-------------+-----------
 c2 |            1 |           1 |   0.03279
 c1 |            2 |           3 |   0.03200
 c3 |            3 |           2 |   0.03200
(3 rows)

  7. Clean up — drop the throwaway table and confirm nothing remains:

    oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -c "DROP TABLE $TABLE"
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -t -c "SELECT tablename FROM pg_tables WHERE tablename LIKE 'ogx_module03%'"

    Expected output: DROP TABLE, then no rows.

Verify

  • The keyword query returns exactly one row: keyword search is precise but blind to synonyms and paraphrases.

  • The vector query ranks all three chunks and still puts the RAG chunk first: semantic search recalls related material keyword search cannot see.

  • The RRF scores show why hybrid search is robust: it fuses two independent opinions about relevance instead of trusting either one.

  • Ask the question again in different words. Run the keyword query with How do I stop the model from making things up? — it returns zero rows (live-verified). Re-run the vector step with the new question embedded: c2 stays first (similarity 0.4594 in the captured run). That contrast is the whole argument for semantic and hybrid retrieval.

On this build the OGX-native multi-mode retrieval API (client.vector_io.query(…​, params={"mode": "keyword|vector|hybrid"})) is not reachable: vector stores cannot be created until the server exposes working embedding-typed models, and the files API they depend on is absent — see "Looking ahead" at the end of this module. The SQL above is the same computation OGX’s pgvector provider performs for you once that lands.

With retrieval understood at the SQL level, look at how the server itself scales.

Exercise 2: Configure high availability and autoscaling

OGX servers stay available if a pod restarts, an application crashes, or node maintenance occurs — and can scale capacity automatically. All of the knobs live on the OGXServer custom resource under spec.workload; you declare the intent and the operator manages the resulting Deployment, PodDisruptionBudget, and HorizontalPodAutoscaler.

Changing the replica configuration recreates OGX server pods. Keep a record of the values you change so you can restore them. The workshop’s staged servers are shared — inspect them, but apply these settings only on an OGXServer of your own.

  1. To enable high availability, add the following to your OGXServer CR:

    spec:
  workload:
    replicas: 2 (1)
    podDisruptionBudget:
      maxUnavailable: 1 (2)
    topologySpreadConstraints: (3)
      - maxSkew: 1 (4)
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app.kubernetes.io/instance: aml-ogx (5)
1 replicas — runs two OGX pods for high availability.
2 podDisruptionBudget.maxUnavailable — voluntary disruption tolerance; this keeps at least one server pod available during voluntary disruptions.
3 topologySpreadConstraints — specifies how matching pods are spread across the cluster topology.
4 maxSkew — minimizes replica imbalance across zones, using the topology.kubernetes.io/zone node label as the failure domain; ScheduleAnyway allows scheduling to proceed even if the constraint cannot be fully satisfied.
5 labelSelector — selects the server’s own pods; the operator labels them app.kubernetes.io/instance: <server-name> (the staged server’s pods carry app.kubernetes.io/instance: aml-ogx).

  1. To enable autoscaling, add the following to your OGXServer CR:

    spec:
  workload:
    autoscaling: (1)
      minReplicas: 1 (2)
      maxReplicas: 5 (3)
      targetCPUUtilizationPercentage: 75 (4)
      targetMemoryUtilizationPercentage: 70 (5)
6 autoscaling — configures a HorizontalPodAutoscaler (HPA) for the server pods.
7 minReplicas — the minimum number of replicas maintained by the HPA.
8 maxReplicas — the maximum number of replicas maintained by the HPA.
9 targetCPUUtilizationPercentage — enables CPU-based scaling.
10 targetMemoryUtilizationPercentage — enables memory-based scaling.

Verify

On a server where you applied these settings, check that the HPA was created and that replica counts stay within the configured bounds:

oc get hpa -n autorag-ml-demo
oc get pods -n autorag-ml-demo -l app=ogx

Expected output: an HPA targeting your OGX server with TARGETS below the configured CPU and memory thresholds, MINPODS 1, MAXPODS 5, and a running pod count within those bounds.

On the shared workshop project the oc get pods -l app=ogx check shows the staged aml-ogx pod Running, and the field names above are live-verified against the ogxservers.ogx.io v1beta1 schema (spec.workload.{replicas, podDisruptionBudget, topologySpreadConstraints, autoscaling}). The HPAs you see in this project belong to the model predictors, not to the OGX server — the staged servers intentionally run a single replica, so exercise the autoscaling knobs on a server of your own.

With the scaling model understood, look at how the same stack is reproduced across projects.

Exercise 3: Reproduce the stack — a second OGX server from the same blueprint

An OGXServer custom resource is a blueprint: one declarative object that wires a distribution image, provider endpoints, and storage into a self-contained server. The proof is that this cluster runs the blueprint twice. Project autorag-ml-demo hosts aml-ogx (the server you have been using); project autorag-ocr-demo hosts aocr-ogx (a server for a document intelligence workshop). Different projects, different names — same stack.

  1. List the servers in both projects:

    oc get ogxserver -n autorag-ml-demo
oc get ogxserver -n autorag-ocr-demo

    Expected output: both servers listed with PHASE Ready and PROVIDERS 3 (the two vLLM inference providers plus the pgvector vector store).

  2. Compare the wiring. Same distribution, same provider IDs, in each project:

    oc -n autorag-ml-demo get ogxserver aml-ogx -o json \
  | jq -c '{distro:.spec.distribution.name, vllm:[.spec.providers.inference.remote.vllm[].id]}'
oc -n autorag-ocr-demo get ogxserver aocr-ogx -o json \
  | jq -c '{distro:.spec.distribution.name, vllm:[.spec.providers.inference.remote.vllm[].id]}'

    Expected output — identical wiring, declared twice:

    {"distro":"rh-dev","vllm":["vllm-inference","vllm-embedding"]}
{"distro":"rh-dev","vllm":["vllm-inference","vllm-embedding"]}

  3. Prove the servers run the same build. Resolve each Deployment’s container image and compare the digests:

    IMG1=$(oc -n autorag-ml-demo get deploy aml-ogx -o jsonpath='{.spec.template.spec.containers[0].image}')
IMG2=$(oc -n autorag-ocr-demo get deploy aocr-ogx -o jsonpath='{.spec.template.spec.containers[0].image}')
echo "$IMG1"
echo "$IMG2"
[ "$IMG1" = "$IMG2" ] && echo "IDENTICAL distro digest"

    Expected output:

    registry.redhat.io/rhoai/odh-ogx-core-rhel9@sha256:73880c133bd337c7d264331b776c9c9b7099f172a5cd79783fc022fc99955eab
registry.redhat.io/rhoai/odh-ogx-core-rhel9@sha256:73880c133bd337c7d264331b776c9c9b7099f172a5cd79783fc022fc99955eab
IDENTICAL distro digest

Verify

  • Both servers report PHASE Ready with PROVIDERS 3, each backed by its own pgvector instance in its own project (aml-pgvector in autorag-ml-demo, aocr-pgvector in autorag-ocr-demo) — the blueprint carries its storage with it.

  • The image digests match exactly: both servers run odh-ogx-core-rhel9 at sha256:73880c13…​. Reproducibility means the same digest, the same wiring, and the same API surface — deploy the blueprint into a new project and you get the same server.

  • What differs is only the per-instance naming (aml- versus aocr-): project, server name, model endpoints, and routes. That is the pattern to copy when you stage your own environment.

The same blueprint-backing philosophy explains the facade you met in Module 02.

Exercise 4: Serve models through the MaaS facade pattern

In Module 02 you computed embeddings through the MaaS facade instead of the OGX-native /v1/embeddings endpoint. The facade is worth understanding as a pattern, because it is what keeps the AutoRAG wizard working on this build.

The problem: the AutoRAG wizard probes a model service with OpenAI-compatible requests before it lets you use it. This OGX build exposes only the inference, models, and vector_io APIs — the endpoint the wizard probes is absent, so every model reports ready: false and the wizard’s model-selection checkboxes render disabled.

The fix: a small OpenAI-compatible facade service sits in front of the two model-serving services, which do serve the endpoints the wizard probes. The wizard sees ready: true; your code gets a clean OpenAI API; the OGX server is left untouched.

  1. Reconnect to the facade and read its model catalog:

    export FACADE="https://$(oc -n autorag-ml-demo get route aml-maas-facade-tls -o jsonpath='{.spec.host}')"
curl -s "$FACADE/v1/models" | jq '{object, models: [.data[] | {id, ready, owned_by}]}'

    Expected output — both models ready, with plain (non-provider-qualified) IDs:

    {
  "object": "list",
  "models": [
    {
      "id": "aml-llama32-3b",
      "ready": true,
      "owned_by": "vllm"
    },
    {
      "id": "aml-bge-m3",
      "ready": true,
      "owned_by": "vllm"
    }
  ]
}

  2. Confirm the facade proxies real work, not just readiness: request an embedding:

    curl -s "$FACADE/v1/embeddings" -H 'Content-Type: application/json' \
  -d '{"model":"aml-bge-m3","input":"facade pattern check"}' \
  | jq '{id, model, dims: (.data[0].embedding | length)}'

    Expected output — a real embedding (the id varies per request):

    {
  "id": "embd-bfebdf9283b451f0",
  "model": "aml-bge-m3",
  "dims": 1024
}

Verify

  • GET /v1/models returns ready: true for both models — this is exactly what the AutoRAG wizard’s readiness probe consumes.

  • The facade speaks OpenAI: {"object": "list", "data": […​]} with per-model ready flags. Compare with the OGX server’s own /v1/models from Module 02, whose IDs are provider-qualified (vllm-inference/aml-llama32-3b) and which carries no ready flag.

  • The embeddings request returns 1024 dimensions — the facade forwards to the real model service. The OGX-native endpoint still refuses the same request (400: the model is registered as type llm, not embedding) — the facade is the documented workaround until an operator fix or a newer build renders the static model registration.

  • Facade IDs are plain (aml-bge-m3); OGX IDs are provider-qualified (vllm-embedding/aml-bge-m3). When you write clients, check which surface you are talking to.

With the patterns covered, go one layer deeper: the database the whole stack stands on.

Exercise 5: Inspect the pgvector storage layer

Every exercise so far has touched PostgreSQL: Module 02’s RAG tables, Module 03’s retrieval experiments, and the server’s own state. Time to look inside. The staged aml-pgvector instance hosts two databases with two distinct jobs:

  • ogx — the vector database: the pgvector extension lives here, and your retrieval tables (from Module 02 and Exercise 1) are created here.

    1. Check which extensions are installed in the vector database:

      oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx -c '\dx'

      Expected output — the pgvector extension, version 0.8.7, with both index access methods:

--------------------+---------+------------+------------------------------------------------------------------------

 plpgsql            | 1.0     | pg_catalog | PL/pgSQL procedural language
 vector             | 0.8.7   | public     | vector data type and ivfflat and hnsw access methods
(3 rows)

    2. List the control-plane tables the OGX server maintains in ogx_metadata:

      oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx_metadata -c '\dt'

      Expected output:

                     List of relations

--------+----------------------+-------+-------

    3. List the vector database’s tables:

      Expected output — the server’s key-value store, plus any vector tables you created and dropped along the way:

                  List of relations

--------+----------------+-------+-------

(1 row)

    4. Peek inside one control-plane table to see what the OpenAI-compatible conversations API persists:

      Expected output:

                        Table "public.openai_conversations"

  • The database split is real: ogx_metadata holds six control-plane tables (note the OpenAI API vocabulary: openai_conversations, conversation_items, prompts, jobs, connectors), while ogx holds the server’s metadata_store key-value table and is where your vector tables live.

  • openai_conversations stores conversation items as JSON with an owner_principal column — multi-user state, ready for the server’s OpenAI-compatible conversations API.

You now know the stack from the API down to the rows. The last stop is honest: the two capabilities this build does not ship yet.

Looking ahead: what a newer OGX build adds

The build running here (odh-ogx-core-rhel9 at digest sha256:73880c13…​) implements the inference, models, and vector_io APIs only — verified against the live server: GET /v1/files returns 404, and the rendered runtime config lists exactly those three APIs, with no oauth2_token authentication provider. The two exercises below are kept from the full OGX curriculum because the content is what you will need the day your cluster runs a newer build. They are marked clearly so nobody wastes an afternoon trying them here.

Requires a newer OGX build. Neither exercise below runs on this cluster. The retry condition is a newer odh-ogx-core image that (a) exposes the files and responses APIs — gate: GET /v1/files returns 200 instead of the 404 captured on this build — and (b) ships the oauth2_token authentication provider — gate: oauth2_token appears in the server’s provider surface. Re-run these exercises when your build meets both conditions.

External S3-compatible storage for the Files API

The OGX Files API uses the inline::localfs provider by default, storing files on the local file system of the OGX pod. The remote::s3 provider stores file content in an external S3-compatible object store — Amazon S3, MinIO, Ceph Object Gateway, or any storage system that implements the S3 API — while file metadata stays in the PostgreSQL metadata store.

The shape of the exercise, for when your build supports it:

  1. Create a secret with the object store credentials: oc create secret generic s3-files-credentials --from-literal=AWS_ACCESS_KEY_ID=…​ --from-literal=AWS_SECRET_ACCESS_KEY=…​.

  2. Add the remote::s3 wiring to your OGXServer CR under spec.workload.overrides.env: ENABLE_S3=true, S3_BUCKET_NAME=<bucket>, AWS_DEFAULT_REGION=us-east-1, and S3_ENDPOINT_URL=<endpoint> for non-AWS backends (omit for AWS S3), with the two credentials pulled from the secret via secretKeyRef.

  3. Watch for the documented gotcha: if the bucket does not exist and S3_AUTO_CREATE_BUCKET is "false", the OGX pod enters CrashLoopBackOff with RuntimeError: S3 bucket '<bucket_name>' does not exist — create the bucket, or set auto-create to "true" in development.

  4. Verify by uploading through POST /v1/files (multipart form with purpose=assistants and the file), then GET /v1/providers should list an entry with "api": "files", "provider_id": "s3", "provider_type": "remote::s3". The file id returned by the upload is the handle for later operations; content lands in your bucket, metadata in PostgreSQL.

Secure the API with OAuth token authentication

Every request this workshop has made to the OGX API was unauthenticated — that is the documented default: authentication is disabled unless AUTH_ISSUER is set. For any server exposed beyond your project, enable OAuth token authentication. The oauth2_token provider validates the Authorization: Bearer token on each request against the issuer’s JWKS endpoint — using asymmetric signature algorithms only (RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512; symmetric algorithms such as HS256 are excluded to prevent algorithm confusion attacks) — and extracts user principals and role claims straight from the JWT.

The shape of the exercise, for when your build supports it:

  1. Stand up an OIDC issuer (for example Keycloak) with a realm, a client with direct access grants enabled, a role such as inference_max, a protocol mapper adding realm roles to the access token, and two test users — one without roles, one with the role.

  2. Request access tokens with the OAuth password grant against the realm’s token endpoint, and inspect the claims: iss, sub, preferred_username, and the role claim.

  3. Enable the provider in the server config under server.auth: type: "oauth2_token" with the JWKS uri, issuer, audience, and a claims_mapping from your role claim to roles, then declare access_policy rules — for example permit: actions: [read], resource: model::<model-id> for everyone, and a second rule with when: user with inference_max in roles for restricted models.

  4. Verify the three responses: 401 without a token, 200 with a valid token for a permitted model, and 403 for a token lacking the required role on a restricted model.
