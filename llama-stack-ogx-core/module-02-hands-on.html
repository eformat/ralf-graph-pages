Module 02: Deploy an OGX server and build a RAG workflow

In this module you will activate the OGX Operator, connect to a running OGX server through its route, explore the OpenAI-compatible API surface that the server exposes, and build an end-to-end RAG workflow: compute embeddings, ground a chat completion in retrieved documents, and leave the environment exactly as you found it.

Learning objectives:

  • Enable the OGX Operator in the DataScienceCluster custom resource

  • Connect to an OGX server and verify its health, model catalog, and chat completions

  • Call the API with provider-qualified model IDs

  • Compute embeddings through the MaaS facade pattern

  • Build a grounded RAG loop with pgvector cosine retrieval, and clean up afterwards

Exercise 1: Activate the OGX Operator

You activate the OGX Operator by setting its management state to Managed in the DataScienceCluster (DSC) custom resource.

If your facilitator has already activated OGX, run the verification step and continue to Exercise 2.

  1. Log in to the OpenShift web console as a cluster administrator.

  2. Go to the Installed Operators page: on OpenShift 4.20 and later, click Ecosystem → Installed Operators; on OpenShift 4.19, click Operators → Installed Operators.

  3. Click the Red Hat OpenShift AI Operator to open its details.

  4. Click the Data Science Cluster tab and select the default-dsc object.

  5. Click the YAML tab, locate spec.components, and set the ogx component to Managed:

    spec:
  components:
    ogx:
      managementState: Managed

  6. Click Save to apply your changes.

You can also activate the operator from the CLI:

oc patch datasciencecluster default-dsc --type=merge -p '{"spec":{"components":{"ogx":{"managementState":"Managed"}}}}'

Verify

Confirm that the OGX Operator pod is running in the redhat-ods-applications namespace:

oc get pods -n redhat-ods-applications | grep -E '^(ogx|opendatahub-ogx)'

Expected output:

ogx-k8s-operator-controller-manager-<suffix>     1/1   Running   <n>   <age>
opendatahub-ogx-operator-<suffix>                1/1   Running   <n>   <age>

With the operator running, connect to your first OGX server.

Exercise 2: Meet your OGX server

The OGXServer custom resource deploys a server that exposes the OGX APIs in your project. For this workshop the facilitator has staged a server named aml-ogx in the autorag-ml-demo project from the workshop’s deployment manifests — it wires a vLLM inference model, a vLLM embedding model, and a pgvector vector store into one server. In this exercise you inspect the resource and open a connection to it.

  1. Inspect the server and confirm it is ready. The PROVIDERS column counts the configured providers — inference, embedding, and the pgvector vector store:

    oc -n autorag-ml-demo get ogxserver
oc -n autorag-ml-demo get ogxserver aml-ogx -o jsonpath='{.status.phase}'

    Expected output: aml-ogx is listed with PHASE Ready and PROVIDERS 3.

  2. Look at the resource anatomy — distribution, storage, and the model providers it wires in. Do not copy the connection string contents; the Secret reference is all a client needs:

    oc -n autorag-ml-demo get ogxserver aml-ogx -o yaml

    The fields that matter:

apiVersion: ogx.io/v1beta1
kind: OGXServer
metadata:
  name: aml-ogx
  namespace: autorag-ml-demo
spec:
  distribution:
    name: rh-dev
  storage:
    sql:
      type: postgres
      connectionString:
        name: aml-ogx-postgres-conn <1>
        key: connection
  providers:
    inference:
      remote:
        vllm:
          - id: vllm-inference <2>
            endpoint: http://aml-llama32-3b-conn.autorag-ml-demo.svc.cluster.local:8080/v1
          - id: vllm-embedding <3>
            endpoint: http://aml-bge-m3-conn.autorag-ml-demo.svc.cluster.local:8080/v1
1 connectionString — the PostgreSQL metadata store; the Secret must carry the ogx.io/watch: "true" label so the operator picks it up.
2 vllm-inference — the chat model served through a vLLM endpoint.
3 vllm-embedding — the embedding model served through the same vLLM provider type.

  1. Export the server route and verify that it is healthy:

    export OGX="https://$(oc -n autorag-ml-demo get route aml-ogx-tls -o jsonpath='{.spec.host}')"
curl -s -w "\nHTTP %{http_code}\n" $OGX/v1/health

Expected output:

 
{"status":"OK"}
HTTP 200

  1. List the models the server exposes:

    curl -s $OGX/v1/models | jq -r '.data[].id'

    Expected output:

vllm-inference/aml-llama32-3b
vllm-embedding/aml-bge-m3
Model IDs are provider-qualified: <provider_id>/<model_id>. Every OGX API call must use the full qualified ID. Requesting the bare model name returns 404: 
curl -s -w "\nHTTP %{http_code}\n" $OGX/v1/models/aml-llama32-3b

Expected output:

HTTP 404
{"error":{"message":"Model 'aml-llama32-3b' not found. Use 'client.models.list()' to list available Models."}}

Verify

  1. The health endpoint returns {"status":"OK"} with HTTP 200.

  2. The model list returns the two provider-qualified IDs.

  3. The server phase is Ready:

    oc -n autorag-ml-demo wait --for=jsonpath='{.status.phase}'=Ready ogxserver/aml-ogx --timeout=300s

    Expected output: ogxserver.ogx.io/aml-ogx condition met.

With the connection verified, send your first chat completion.

Exercise 3: Send a chat completion

The chat completions API is OpenAI-compatible: point it at the OGX route, pass a provider-qualified model ID, and read the answer from choices[0].message.content.

  1. Send a completion that asks the model to confirm it is up:

    curl -s $OGX/v1/chat/completions \
  --header 'Content-Type: application/json' \
  -d '{
    "model": "vllm-inference/aml-llama32-3b",
    "messages": [
      {"role": "system", "content": "You are a helpful assistant. Reply with exactly one word."},
      {"role": "user", "content": "Confirm you are available by replying with the word READY."}
    ]
  }' | jq '{model, system_fingerprint, content: .choices[0].message.content}'

Expected output:

{
  "model": "vllm-inference/aml-llama32-3b",
  "system_fingerprint": "vllm-0.31.0+rhaiv.8-596d449d",
  "content": "READY"
}
The system_fingerprint identifies the serving stack — vLLM 0.31.0 with the Red Hat AI inference vehicle. Your fingerprint may carry a different short build suffix.

Verify

  • The response has HTTP 200 and content is READY.

  • The model in the response echoes the provider-qualified ID you sent.

An ungrounded model answers from its training data alone. Next you produce the vectors that grounding needs.

Exercise 4: Compute embeddings through the MaaS facade

RAG starts with embeddings — numeric vectors that capture what a piece of text means, so that similar texts land close together in vector space. This environment serves the multilingual aml-bge-m3 embedding model (1024 dimensions) behind a MaaS facade: a small OpenAI-compatible proxy that exposes /v1/embeddings for the workshop.

  1. First, try the OGX-native embeddings endpoint and observe the honest state of this build. The server auto-registered aml-bge-m3 with the wrong model type, so the native endpoint rejects it:

    curl -s -w "\nHTTP %{http_code}\n" $OGX/v1/embeddings \
  --header 'Content-Type: application/json' \
  -d '{"model": "vllm-embedding/aml-bge-m3", "input": "OGX embeddings probe"}'

Expected output:

HTTP 400
{"error":{"message":"Model 'vllm-embedding/aml-bge-m3' is of type 'llm' rather than the expected type 'embedding'"}}
This is a known limitation of the current OGX build: the operator’s config render drops the static model registration, so the embedding model is typed as llm and the native /v1/embeddings returns 400. Once you upgrade to a build that renders the static models section (or a fixed operator), the same request returns 200 and the facade step becomes optional.

  1. Compute real embeddings through the facade route instead:

    export FACADE="https://$(oc -n autorag-ml-demo get route aml-maas-facade-tls -o jsonpath='{.spec.host}')"
curl -s $FACADE/v1/embeddings \
  --header 'Content-Type: application/json' \
  -d '{"model": "aml-bge-m3", "input": "OGX embeddings via the facade"}' \
  | jq '{id, model, dims: (.data[0].embedding | length)}'

Expected output:

{
  "id": "embd-<hex>",
  "model": "aml-bge-m3",
  "dims": 1024
}

Verify

  • The native endpoint returns HTTP 400 with the llm rather than embedding error — you know the boundary of this build.

  • The facade returns HTTP 200 with a 1024-dimensional vector for the same model.

With embeddings working, inspect the vector-store surface before you store anything.

Exercise 5: Inspect the vector-store surface

OGX exposes an OpenAI-compatible vector-store API. On this build you can list stores, but creating one fails for the same model-type reason you saw in Exercise 4 — so this workshop grounds its RAG answers with manual retrieval in Exercise 6 instead. Knowing what works is part of working with a real platform.

  1. List the vector stores. The list is empty — nothing has been created on this server:

    curl -s $OGX/v1/vector_stores | jq '{object, store_count: (.data | length)}'

Expected output:

{
  "object": "list",
  "store_count": 0
}

  1. Try to create a store and observe the honest failure — store registration requires an embedding-typed model, and this build serves aml-bge-m3 as llm:

    curl -s -w "\nHTTP %{http_code}\n" $OGX/v1/vector_stores \
  --header 'Content-Type: application/json' \
  -d '{"name": "ogx_rag_store", "embedding_model": "vllm-embedding/aml-bge-m3"}'

Expected output:

HTTP 400
{"error":{"message":"Embedding model 'vllm-embedding/aml-bge-m3' not found or not an embedding model"}}
What a newer build adds

On an OGX build that exposes the Files and Responses APIs, this exercise continues with a fully managed ingest-and-search flow, and Exercise 6 becomes a one-call RAG answer:

  1. Upload a document: client.files.create(file=…​, purpose="assistants") — the Files API stores the object and returns a file_id.

  2. Index it into a vector store with a chunking strategy: client.vector_stores.files.create(vector_store_id=…​, file_id=…​, chunking_strategy={"type": "static", …​}) — OGX chunks, embeds, and indexes the file for you.

  3. Ask a grounded question with the file_search tool: client.responses.create(model=…​, input=…​, tools=[{"type": "file_search", "vector_store_ids": […​]}]) — OGX retrieves the matching chunks and hands them to the model as context.

This flow requires a newer OGX build: this one implements only the inference, models, and vector_io APIs — GET /v1/files returns 404. Retry this section once your server runs a build whose API surface includes files and responses (check with curl -s $OGX/v1/files; a 200 means the flow is available).

Verify

  • GET /v1/vector_stores returns HTTP 200 with an empty list, and the create attempt returns the documented 400 — you know exactly what this server can and cannot do.

For the RAG workflow itself, you now take the retrieval step into your own hands.

Exercise 6: Build a grounded RAG loop with manual retrieval

Retrieval-augmented generation is a loop: embed your documents, store the vectors, embed the question, retrieve the closest chunks by cosine similarity, and pass them to the chat completions API as context. On this build you run the storage and retrieval steps yourself against the pgvector instance that backs the OGX server — which has the bonus that you can see every step of the loop instead of treating RAG as a black box.

Every step below uses a throwaway table named ogx_module02_chunks that you drop at the end — the exercise leaves the shared environment exactly as it found it. Do not create or modify any other database objects.

  1. Write three small domain documents to ground against:

    mkdir -p chunks
cat > chunks/c1.txt <<'EOF'
OGX is the Open GenAI Stack in Red Hat OpenShift AI 3.6. It replaces Llama Stack and
exposes OpenAI-compatible APIs for chat completions, embeddings, and vector stores.
The OGX Operator manages OGXServer custom resources through the ogx.io/v1beta1 API group.
EOF
cat > chunks/c2.txt <<'EOF'
Retrieval-augmented generation grounds a language model in your own documents: chunks
are embedded, stored in a vector database such as PostgreSQL with pgvector, and the
most similar chunks to a user question are injected into the chat completion prompt
as context.
EOF
cat > chunks/c3.txt <<'EOF'
pgvector supports cosine distance with the <=> operator. Ordering by
embedding <=> query_vec returns the nearest neighbours first. The stored dimension
must match the embedding model output; the aml-bge-m3 model served through the
MaaS facade produces 1024-dimensional vectors.
EOF

  2. Create the throwaway table in the pgvector database that backs the OGX server:

    TABLE=ogx_module02_chunks
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -c "CREATE TABLE $TABLE (id text, source text, content text, embedding vector(1024))"

    Expected output: CREATE TABLE.

  3. Ingest each chunk: embed it through the facade, then insert the vector. The vector column stores the 1024 dimensions as a PostgreSQL array literal:

    for f in chunks/c*.txt; do
  id=$(basename "$f" .txt)
  vec=$(curl -s "$FACADE/v1/embeddings" -H 'Content-Type: application/json' \
        -d "$(jq -n --arg t "$(cat "$f")" '{model:"aml-bge-m3", input:$t}')" \
        | jq -r '.data[0].embedding | join(",")')
  body=$(sed "s/'/''/g" "$f")
  oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
    -c "INSERT INTO $TABLE (id, source, content, embedding) VALUES ('$id', '$id.txt', '$body', '[$vec]')"
done

    Expected output: three INSERT 0 1 lines, one per chunk.

  4. Retrieve: embed the question with the same model, then order by cosine distance. The <⇒ operator is pgvector’s cosine distance — 1 - distance is the similarity:

    QUESTION="How does RAG ground the model in my own documents?"
VEC=$(curl -s "$FACADE/v1/embeddings" -H 'Content-Type: application/json' \
      -d "$(jq -n --arg t "$QUESTION" '{model:"aml-bge-m3", input:$t}')" \
      | jq -r '.data[0].embedding | join(",")')
oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -c "SELECT id, source, round(1 - (embedding <=> '[$VEC]')::numeric, 4) AS similarity
      FROM $TABLE ORDER BY embedding <=> '[$VEC]' LIMIT 3"

Expected output — the RAG chunk ranks first:

 id | source | similarity
----+--------+------------
 c2 | c2.txt |     0.5707
 c3 | c3.txt |     0.4560
 c1 | c1.txt |     0.3816
(3 rows)

  1. Ground the answer: pull the top chunks back out of the table and pass them to the chat completions API as context. The model must answer from the context only:

    CTX=$(oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx -t -A -c \
      "SELECT content FROM $TABLE ORDER BY embedding <=> '[$VEC]' LIMIT 2")
jq -n --arg m "vllm-inference/aml-llama32-3b" --arg c "$CTX" --arg q "$QUESTION" \
   '{model:$m, messages:[
      {role:"system", content:"You are a precise assistant. Answer using ONLY the retrieved context. If the context does not contain the answer, say so clearly."},
      {role:"user", content:("Context:\n" + $c + "\n\nQuestion: " + $q)}]}' > rag-request.json
curl -s "$OGX/v1/chat/completions" -H 'Content-Type: application/json' -d @rag-request.json \
  | jq '{model, system_fingerprint, answer: .choices[0].message.content}'

Expected output — an answer grounded in the retrieved chunk, not in generic knowledge:

{
  "model": "vllm-inference/aml-llama32-3b",
  "system_fingerprint": "vllm-0.31.0+rhaiv.8-596d449d",
  "answer": "According to the context, Retrieval-augmented generation grounds a language model in your own documents by embedding chunks, storing them in a vector database (specifically, PostgreSQL with pgvector), and then using these embedded chunks as context to the chat completion prompt."
}

  1. Clean up. Drop the throwaway table and confirm the vector-store list is unchanged:

    oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -c "DROP TABLE $TABLE"
curl -s "$OGX/v1/vector_stores" | jq '{object, store_count: (.data | length)}'

    Expected output: DROP TABLE, and the list shows store_count: 0 again.

Verify

  • The retrieval step ranks the RAG chunk (c2) first with the highest similarity score.

  • The grounded answer quotes the retrieved context instead of answering generically.

  • Ask an ungrounded follow-up — replace the question with something the chunks do not cover (for example What is the capital of France? sent with the same context) and confirm the model says the context does not contain the answer.

  • DROP TABLE succeeds and no ogx_module02 tables remain:

    oc exec aml-pgvector-0 -n autorag-ml-demo -- psql -U ogx -d ogx \
  -t -c "SELECT tablename FROM pg_tables WHERE tablename LIKE 'ogx_module02%'"

    Expected output: no rows.

You have now run a complete RAG loop by hand. Module 03 looks at what happens when you run more than one OGX server, and how the facade pattern from Exercise 4 generalizes.

Module summary

What you accomplished:

  • Activated the OGX Operator in the DataScienceCluster and confirmed the operator pods running

  • Connected to a staged OGXServer backed by vLLM inference, vLLM embeddings, and pgvector

  • Sent chat completions with provider-qualified model IDs and read the serving fingerprint

  • Computed 1024-dimensional embeddings through the MaaS facade, and mapped the API surface that this build exposes — including where it honestly stops

  • Built a grounded RAG loop: facade embeddings, pgvector cosine retrieval, and a context-constrained chat completion — with net-zero cleanup

Key takeaways:

  • The OGXServer CR is the single entry point for wiring providers: inference, embedding, and vector storage all come from one custom resource

  • Model IDs are provider-qualified (vllm-inference/aml-llama32-3b); bare names 404

  • The MaaS facade is the documented embeddings path on builds where the operator render drops the static model registration — the native endpoint returns 400 until then

  • RAG is a loop you can run by hand: embed, store, retrieve by cosine distance, ground the prompt — doing it manually once teaches you what every RAG framework automates

Next steps:

With the RAG loop understood end to end, scale out to multiple OGX servers, inspect the storage layer, and explore the facade pattern in depth in Module 03.
