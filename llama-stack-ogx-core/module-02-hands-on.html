Module 02: Deploy an OGX server and build a RAG workflow

In this module you will activate the OGX Operator, deploy an OGX server connected to a vLLM inference service and PostgreSQL metadata storage, and build an end-to-end RAG workflow: ingest documents into a vector store and query them from a notebook.

Learning objectives:

  • Enable the OGX Operator in the DataScienceCluster custom resource

  • Deploy an OGXServer connected to a vLLM inference service, a vector store, and PostgreSQL metadata storage

  • Ingest documents into a vector store and run retrieval-augmented queries with the file_search tool

Exercise 1: Activate the OGX Operator

You activate the OGX Operator by setting its management state to Managed in the DataScienceCluster (DSC) custom resource.

If your facilitator has already activated OGX, run the verification step and continue to Exercise 2.

  1. Log in to the OpenShift web console as a cluster administrator.

  2. Go to the Installed Operators page: on OpenShift 4.20 and later, click Ecosystem → Installed Operators; on OpenShift 4.19, click Operators → Installed Operators.

  3. Click the Red Hat OpenShift AI Operator to open its details.

  4. Click the Data Science Cluster tab and select the default-dsc object.

  5. Click the YAML tab, locate spec.components, and set the ogx component to Managed:

    spec:
  components:
    ogx:
      managementState: Managed

  6. Click Save to apply your changes.

You can also activate the operator from the CLI:

oc patch datasciencecluster default-dsc --type=merge -p '{"spec":{"components":{"ogx":{"managementState":"Managed"}}}}'

Verify

Confirm that the OGX Operator pod is running in the redhat-ods-applications namespace:

oc get pods -n redhat-ods-applications -l name=ogx-k8s-operator

Expected output:

NAME                               READY   STATUS    RESTARTS   AGE
ogx-k8s-operator-<pod-suffix>      1/1     Running   0          <age>

With the operator running, deploy your first OGX server.

Exercise 2: Deploy an OGX server

The OGXServer custom resource deploys a server that exposes the OGX APIs in your project. You are responsible for provisioning the PostgreSQL instance used for metadata storage; it can run in-cluster or be hosted externally, as long as it is reachable from the cluster network.

Create the PostgreSQL credential secret in the same namespace as the OGXServer resource. Avoid placing passwords directly on the command line, as they can be stored in shell history.

  1. Create a secret that contains only the database password, then create the secret from that file:

    echo "%password%" > pg-password.txt
oc create secret generic postgres-secret --from-file=password=pg-password.txt -n abc123-user1
rm -f pg-password.txt

  2. Create the ogxserver.yaml file — a shell heredoc with the PostgreSQL secret from the previous step. Point VLLM_URL at your vLLM inference service; here the granite-vllm predictor from the vLLM ServingRuntime workshop (a GPU cluster substitutes its deployed model, e.g. https://llama32-3b.<project>.svc.cluster.local/v1):

    PGPASSWORD=$(oc get secret postgres-secret -n abc123-user1 -o jsonpath='{.data.password}' | base64 -d)
oc create secret generic ogx-postgres-conn -n abc123-user1 \
  --from-literal=connection="postgresql://ogx:${PGPASSWORD}@postgres.abc123-user1.svc.cluster.local:5432/ogx" \
  --dry-run=client -o yaml | oc apply -n abc123-user1 -f -
oc label secret ogx-postgres-conn -n abc123-user1 ogx.io/watch=true --overwrite
cat > ogxserver.yaml <<'EOF'
apiVersion: ogx.io/v1beta1
kind: OGXServer
metadata:
  name: ogx-custom-server
  namespace: abc123-user1
spec:
  distribution:
    name: rh-dev
  storage:
    sql:
      type: postgres
      connectionString:
        name: ogx-postgres-conn
        key: connection
EOF

The fields map to the RHOAI documentation (OGXServer v1beta1): distribution.name is an internal image reference (the RHOAI Operator resolves rh-dev to the container image in the appropriate registry). spec.storage.sql configures the PostgreSQL metadata store — the connectionString Secret must carry the ogx.io/watch: "true" label and the key holds a postgresql:// connection string to your PostgreSQL instance (deploy a PostgreSQL instance and Service in your project first; the in-lab flow uses an in-cluster PostgreSQL). Inference provider endpoints are registered via spec.resources or the server’s registry — point your client at the deployed model’s OpenAI-compatible API.

  1. Apply the OGXServer CR:

    oc apply -f ogxserver.yaml -n abc123-user1
The rh-dev distribution value is an internal image reference resolved automatically by the OpenShift AI Operator; you do not need to replace it with a registry URL.

Verify

  1. Check that the custom resource became ready and the server pods are running:

    oc get ogxserver -n abc123-user1
oc wait --for=jsonpath='{.status.phase}'=Ready ogxserver/ogx-custom-server -n abc123-user1 --timeout=300s
oc get pods -n abc123-user1 | grep ogx-custom-server

    Expected output: oc get ogxserver lists ogx-custom-server, the oc wait command prints condition met once .status.phase is Ready, and the pod listing shows the ogx-custom-server pods with STATUS Running.

  2. Check the server logs for startup output:

    oc logs -n abc123-user1 -l app=ogx

Expected output:

INFO: Started server process
INFO: Waiting for application startup.
INFO: Application startup complete.
INFO: Uvicorn running on http://['::', '0.0.0.0']:8321

The server listens on port 8321. The OGX Operator names the service <ogxserver-name>-service, so this instance is reachable in-cluster at http://ogx-custom-server-service.abc123-user1.svc.cluster.local:8321.

With the base server running, pair it with a vector store and ingest real documents.

Exercise 3: Ingest documents and query with RAG

The RAG stack connects your OGX server to a vector store so that you can ingest, embed, and query domain-specific documents during inference. In this exercise you configure the pgvector provider, upload a PDF from a Jupyter notebook, and answer questions grounded in the ingested content.

For RAG you need a remote embedding model reachable from the cluster, for example nomic-embed-text-v1-5 served through a vLLM embedding endpoint. RAG queries without ingested content return empty or non-contextual responses.

  1. Create a secret that contains the inference model and remote embedding environment variables, replacing <token-identifier> with the API token for your vLLM inference service and <embedding-token> with the API token for your embedding endpoint:

    export INFERENCE_MODEL="llama-3-2-3b"
export VLLM_URL="https://llama-32-3b-instruct-predictor:8443/v1"
export VLLM_TLS_VERIFY="false"
export VLLM_API_TOKEN=""
export VLLM_MAX_TOKENS=16384
export EMBEDDING_MODEL="nomic-embed-text-v1-5"
export EMBEDDING_PROVIDER_MODEL_ID="nomic-embed-text-v1-5"
export VLLM_EMBEDDING_URL="https://nomic-embed-text-v1-5-predictor:8443/v1"
export VLLM_EMBEDDING_API_TOKEN=""
export VLLM_EMBEDDING_MAX_TOKENS=8192
export VLLM_EMBEDDING_TLS_VERIFY="true"
oc create secret generic ogx-secret -n abc123-user1 \
  --from-literal=INFERENCE_MODEL="$INFERENCE_MODEL" \
  --from-literal=VLLM_URL="$VLLM_URL" \
  --from-literal=VLLM_TLS_VERIFY="$VLLM_TLS_VERIFY" \
  --from-literal=VLLM_API_TOKEN="$VLLM_API_TOKEN" \
  --from-literal=VLLM_MAX_TOKENS="$VLLM_MAX_TOKENS" \
  --from-literal=EMBEDDING_MODEL="$EMBEDDING_MODEL" \
  --from-literal=EMBEDDING_PROVIDER_MODEL_ID="$EMBEDDING_PROVIDER_MODEL_ID" \
  --from-literal=VLLM_EMBEDDING_URL="$VLLM_EMBEDDING_URL" \
  --from-literal=VLLM_EMBEDDING_TLS_VERIFY="$VLLM_EMBEDDING_TLS_VERIFY" \
  --from-literal=VLLM_EMBEDDING_API_TOKEN="$VLLM_EMBEDDING_API_TOKEN" \
  --from-literal=VLLM_EMBEDDING_MAX_TOKENS="$VLLM_EMBEDDING_MAX_TOKENS"

  2. Create a secret with the pgvector connection values, replacing <pgvector-password> with your pgvector user’s password:

    oc create secret generic pgvector-connection -n abc123-user1 \
  --from-literal=PGVECTOR_HOST="postgres.abc123-user1.svc.cluster.local" \
  --from-literal=PGVECTOR_PORT="5432" \
  --from-literal=PGVECTOR_DB="ogx_metadata" \
  --from-literal=PGVECTOR_USER="ogx" \
  --from-literal=PGVECTOR_PASSWORD=""

  3. Create a RAG-enabled OGXServer that reads its configuration from these secrets. In the console, select Administrator → Quick Create (+) → Import YAML, and apply:

    apiVersion: ogx.io/v1beta1
kind: OGXServer
metadata:
  name: ogx-rag-server
  namespace: abc123-user1
spec:
  distribution:
    name: rh-dev
  workload:
    replicas: 1
    storage:
      size: 5Gi
  overrides:
    env:
      - name: POSTGRES_HOST <1>
        value: postgres.abc123-user1.svc.cluster.local
      - name: POSTGRES_PORT
        value: "5432"
      - name: POSTGRES_DB
        value: ogx_metadata
      - name: POSTGRES_USER
        value: ogx
      - name: POSTGRES_PASSWORD
        valueFrom:
          secretKeyRef:
            name: postgres-secret
            key: password
      - name: INFERENCE_MODEL <2>
        valueFrom:
          secretKeyRef:
            name: ogx-secret
            key: INFERENCE_MODEL
      - name: VLLM_URL
        valueFrom:
          secretKeyRef:
            name: ogx-secret
            key: VLLM_URL
      - name: VLLM_API_TOKEN
        valueFrom:
          secretKeyRef:
            name: ogx-secret
            key: VLLM_API_TOKEN
      - name: EMBEDDING_MODEL
        valueFrom:
          secretKeyRef:
            name: ogx-secret
            key: EMBEDDING_MODEL
      - name: VLLM_EMBEDDING_URL
        valueFrom:
          secretKeyRef:
            name: ogx-secret
            key: VLLM_EMBEDDING_URL
      - name: ENABLE_PGVECTOR <3>
        value: "true"
      - name: PGVECTOR_HOST <4>
        valueFrom:
          secretKeyRef:
            name: pgvector-connection
            key: PGVECTOR_HOST
      - name: PGVECTOR_PORT
        valueFrom:
          secretKeyRef:
            name: pgvector-connection
            key: PGVECTOR_PORT
      - name: PGVECTOR_DB
        valueFrom:
          secretKeyRef:
            name: pgvector-connection
            key: PGVECTOR_DB
      - name: PGVECTOR_USER
        valueFrom:
          secretKeyRef:
            name: pgvector-connection
            key: PGVECTOR_USER
      - name: PGVECTOR_PASSWORD
        valueFrom:
          secretKeyRef:
            name: pgvector-connection
            key: PGVECTOR_PASSWORD <5>
1 POSTGRES_* — the PostgreSQL metadata store; OGX requires PostgreSQL 14 or later for metadata persistence.
2 INFERENCE_MODEL — the vLLM-served LLM identifier; VLLM_URL points at its /v1 endpoint.
3 ENABLE_PGVECTOR — enables the remote::pgvector vector_io provider in the OGX server.
4 PGVECTOR_* — the pgvector vector store connection, read from the pgvector-connection secret.
5 PGVECTOR_PASSWORD — credentials must come from secrets, never as plaintext values in the CR.
If you switch between vector store configurations, delete the existing OGX pod to ensure the new environment variables and backing store are picked up cleanly.

  1. In a workbench in your project, open a Jupyter notebook and install the OGX client:

    %pip install ogx_client

  2. Create a client instance and list the available models:

    from ogx_client import OGXClient

client = OGXClient(base_url="http://ogx-rag-server-service:8321")
models = client.models.list()
print(models)

Expected output:

[Model(identifier='llama-32-3b-instruct', model_type='llm', provider_id='vllm-inference'),
 Model(identifier='nomic-embed-text-v1-5', model_type='embedding', metadata=
 {'embedding_dimension': 768})]
Provider IDs can differ between interfaces. In the Python SDK you use the provider name directly (for example, provider_id: "pgvector"); in some CLI tools remote providers use a prefixed identifier (for example, --vector-db-provider-id remote-pgvector). Use the format that matches the interface you are using.

  1. Select an LLM and an embedding model, and register a vector store:

    model_id = next(m.identifier for m in models if m.model_type == "llm")
embedding_model = next(m for m in models if m.model_type == "embedding")
embedding_model_id = embedding_model.identifier
embedding_dimension = int(embedding_model.metadata["embedding_dimension"])

vector_store = client.vector_stores.create(
    name="my_pgvector_store",
    extra_body={
        "embedding_model": embedding_model_id,
        "embedding_dimension": embedding_dimension,
        "provider_id": "pgvector",
    },
)
vector_store_id = vector_store.id
print(vector_store_id)

  2. Download a PDF, upload it to OGX, and add it to the vector store with a chunking strategy:

    import requests

pdf_url = "https://www.federalreserve.gov/aboutthefed/files/quarterly-report-20250822.pdf"
filename = "quarterly-report-20250822.pdf"
response = requests.get(pdf_url)
response.raise_for_status()
with open(filename, "wb") as f:
    f.write(response.content)

with open(filename, "rb") as f:
    file_info = client.files.create(
        file=(filename, f),
        purpose="assistants",
    )

vector_store_file = client.vector_stores.files.create(
    vector_store_id=vector_store_id,
    file_id=file_info.id,
    chunking_strategy={
        "type": "static",
        "static": {
            "max_chunk_size_tokens": 800,
            "chunk_overlap_tokens": 400,
        },
    },
)
print(vector_store_file)

  3. Query the ingested content with the Responses API and the file_search tool:

    system_instructions = """You are a precise and reliable AI assistant.
Use retrieved context when it is available.
If nothing relevant is found, say so clearly."""
query = "Summarize the key findings in the report."

response = client.responses.create(
    model=model_id,
    input=query,
    instructions=system_instructions,
    tools=[
        {
            "type": "file_search",
            "vector_store_ids": [vector_store_id],
        }
    ],
)
print(response.output_text)

When you include the file_search tool with vector_store_ids, OGX retrieves relevant chunks from the vector store and provides them to the model as context for the response.

  1. Query the vector store directly to inspect the retrieved chunks:

    query_result = client.vector_io.query(
    vector_store_id=vector_store_id,
    query="key findings",
)
print(query_result)

Verify

  • client.vector_stores.files.create() returns a file object with status completed, confirming the PDF was chunked and indexed into my_pgvector_store.

  • print(response.output_text) outputs a summary grounded in the report content, and a question about a topic the document does not cover returns a statement that no relevant information was found.

  • client.vector_io.query() returns the ingested report chunks matching key findings, confirming the pgvector store holds indexed content.

You now have a working RAG loop. Before scaling it up, test the underlying model endpoints directly from the CLI.

Exercise 4: Test your vLLM model endpoints

To confirm your deployed model is accessible, test the vLLM endpoint with a chat completion request. If you selected Make deployed models available through an external route during model deployment, the endpoint is already exposed outside the cluster.

Manually exposing vLLM model endpoints, for example with oc expose, creates an unsecured route unless you configure authentication. Avoid exposing endpoints without security controls.

  1. Log in to the cluster from the CLI. In the upper-right corner of the web console, click your user name, select Copy login command, then Display Token, and copy the displayed command, replacing <token> with the API token shown on that page:

    oc login --token= --server=https://api.cluster.example.com:6443

  2. If you enabled Require token authentication during model deployment, retrieve the model token:

    export MODEL_TOKEN=$(oc get secret default-name-llama-32-3b-instruct-sa -n abc123-user1 -o jsonpath='{.data.token}' | base64 -d)

  3. Obtain the model endpoint URL from Endpoint details on the Deployments page in the RHOAI dashboard, or from the route:

    export MODEL_ENDPOINT="https://$(oc get route llama-32-3b-instruct -n abc123-user1 -o jsonpath='{.spec.host}')"

  4. Test the endpoint with a sample chat completion request:

    curl -s -k $MODEL_ENDPOINT/v1/chat/completions \
  --header "Authorization: Bearer $MODEL_TOKEN" \
  --header 'Content-Type: application/json' \
  -d '{
    "model": "llama-32-3b-instruct",
    "messages": [
      {"role": "user", "content": "Hello"}
    ]
  }' | jq .
The -k flag disables SSL verification and should only be used in test environments or with self-signed certificates.

Verify

You receive a JSON response containing a chat completion, similar to:

{
  "id": "chatcmpl-05d24b91b08a4b78b0e084d4cc91dd7e",
  "object": "chat.completion",
  "model": "llama-32-3b-instruct",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": "Hello! It's nice to meet you. Is there something I can help you with or would you like to chat?"
    },
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 37,
    "total_tokens": 62,
    "completion_tokens": 25
  }
}

If you do not receive a response similar to the example, verify that the endpoint URL and token are correct, and ensure your model deployment is running.

Module summary

What you accomplished:

  • Activated the OGX Operator in the DataScienceCluster and confirmed the operator pod running

  • Deployed OGXServer instances backed by vLLM inference, PostgreSQL metadata storage, and a pgvector vector store

  • Ingested a PDF into a vector store and ran grounded RAG queries with the file_search tool

Key takeaways:

  • The OGXServer CR is the single entry point for wiring providers: inference, embeddings, vector store, and metadata all come from environment variables sourced from secrets

  • Ingestion is a two-step flow — upload the file with the Files API, then index it into a vector store with a chunking strategy

  • The file_search tool on the OpenAI-compatible Responses API is what turns a plain chat into RAG

Next steps:

With the base RAG stack working, tune retrieval modes and scale the deployment for availability in Module 03.
