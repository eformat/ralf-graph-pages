Module 02: Hands-on Exercise

In this module you will work through the full governed arc of the Feast MCP server on RHOAI 3.6: apply the demo manifests, verify the deployment, watch a tokenless request get rejected, act as the AI agent with a ServiceAccount token, retrieve real feature values, register the server in the AI hub, and confirm its health.

Learning objectives:

  • Apply the additive demo manifests (namespace, ConfigMap, FeatureStore CR, RBAC, Route, NetworkPolicy, materialization Job)

  • Verify the FeatureStore reconciles with an McpServer condition and the pod runs three containers

  • Prove governance: tokenless 401 at /mcp, healthy 200 at /health

  • Discover the 22 MCP tools with an authenticated feast-agent token

  • Retrieve real online features for real entities over MCP

  • Register the MCP server in the AI hub (MCP servers → Registry)

Every command in this module was executed against the workshop cluster and the outputs shown are the actual captured results.

Exercise 1: Apply the demo manifests

The demo runtime lives in seven additive manifests under deploy/ in the workshop repository. Each change corresponds to exactly one file:

  • 00-namespace.yaml — the dedicated feast-mcp-demo namespace

  • 10-feast-mcp-config.yaml — the feast-mcp-config ConfigMap holding feast_mcp.yaml with auth.mode: kubernetes

  • 20-featurestore-mcp.yaml — the FeatureStore CR: credit-scoring feature repository from Git, feature server + REST registry with in-pod TLS disabled, and the mcpServer block referencing the ConfigMap

  • 30-agent-rbac.yaml — the feast-agent ServiceAccount with a read-only Role and RoleBinding

  • 40-mcp-route.yaml — the edge-TLS Route feast-mcp to the mcpserver Service

  • 50-mcp-ingress-netpol.yaml — NetworkPolicy allowing ingress to port 8100 from the OpenShift router and the RHOAI dashboard

  • 60-materialize-demo-data.yaml — a one-off Job that materializes the credit-scoring demo data into the online store (the init containers only run feast apply, so a fresh online store starts empty)

From the root of the workshop repository:

oc apply -f deploy/

The feature server and registry run with services.*.server.tls.disable: true on purpose: both are reachable only inside the pod on localhost, and the MCP container cannot trust the service-CA certificates the operator would otherwise issue (the 3.6.0 operator has no custom-volume support to mount the CA). The MCP endpoint itself stays protected by the edge-TLS Route.

Verify

The first apply creates every object; re-running it reports each one as unchanged (captured on the workshop cluster):

namespace/feast-mcp-demo unchanged
configmap/feast-mcp-config unchanged
featurestore.feast.dev/feast-mcp unchanged
serviceaccount/feast-agent unchanged
role.rbac.authorization.k8s.io/feast-reader-use unchanged
rolebinding.rbac.authorization.k8s.io/feast-agent-reader unchanged
route.route.openshift.io/feast-mcp unchanged
networkpolicy.networking.k8s.io/allow-mcp-server-ingress unchanged
job.batch/feast-materialize-demo-data unchanged

Every object reports unchanged — the apply is idempotent, so the demo runtime is in place and safe to re-run at any time. Now that the manifests are applied, verify what the operator built from them.

The deployment is verified end to end. Before calling it as an agent, prove that the governance you configured is actually enforced — Exercise 3 knocks on the door with no credentials at all.

Exercise 3: Prove governance — a tokenless request is rejected

Before authenticating anything, see what an anonymous caller gets. Export the Route host and ask for health first, then try to speak MCP without a token:

ROUTE_HOST=$(oc get route feast-mcp -n feast-mcp-demo -o jsonpath='{.spec.host}')
curl -s -i https://$ROUTE_HOST/health
curl -s -i -X POST https://$ROUTE_HOST/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"feast-workshop","version":"1.0"}}}'

Verify

The health endpoint answers 200 with its status body — it is deliberately unauthenticated so probes work without credentials (captured):

HTTP/1.1 200 OK
...
content-type: application/json

{"status":"healthy","service":"mcp-server"}

The MCP endpoint itself rejects the tokenless initialize with 401 and a Bearer challenge (captured):

HTTP/1.1 401 Unauthorized
...
www-authenticate: Bearer

That is auth.mode: kubernetes doing its job: no token, no tools.

Anonymous callers are locked out, exactly as configured. Exercise 4 now acts as a legitimate caller: it mints a feast-agent token and discovers the tools the governed way.

Exercise 4: Act as the agent — authenticate and discover the tools

The agent’s identity is the feast-agent ServiceAccount from deploy/30-agent-rbac.yaml. Mint a short-lived token for it (never print or commit it):

TOKEN=$(oc create token feast-agent -n feast-mcp-demo)

Initialize the MCP session with the token, capture the issued session id, complete the initialization handshake, and list the tools:

curl -s -D headers.txt -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"feast-workshop","version":"1.0"}}}'
SESSION=$(grep -i '^mcp-session-id:' headers.txt | tr -d '\r' | awk '{print $2}')
curl -s -o /dev/null -w 'initialized: HTTP %{http_code}\n' -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H "mcp-session-id: $SESSION" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
curl -s -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H "mcp-session-id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

Verify

The initialize returns 200 OK with an SSE frame announcing the server and its capabilities (captured):

HTTP/1.1 200 OK
content-type: text/event-stream
mcp-session-id: ffc4f8e260774453854f6584a2515685

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-03-26",
"capabilities":{"experimental":{},"logging":{},"prompts":{"listChanged":true},
"resources":{"subscribe":false,"listChanged":true},"tools":{"listChanged":true},
"extensions":{"io.modelcontextprotocol/ui":{}}},
"serverInfo":{"name":"feast","version":"3.4.8"},
"instructions":"Feast Feature Store — retrieve online features, search documents,
manage materialization, and browse the feature registry."}}

The handshake notification answers 202 (captured: initialized: HTTP 202), and tools/list returns 22 tools — 9 features_* and 13 registry_* (captured verbatim):

features_list_vector_stores      features_get_vector_store
features_vector_store_search     features_push
features_materialize             features_materialize_incremental

registry_search_registry         registry_get_lineage

Every subsequent MCP call must repeat the Authorization and mcp-session-id headers — the session id ties your requests to the initialized session. Tokens from oc create token expire; mint a fresh one if requests start failing with 401.

With the session initialized and all 22 tools listed, it is time to call them — Exercise 5 browses the registry and fetches real feature values for real entities.

Exercise 5: Call real tools — browse the registry, fetch real features

First let the agent look around: list the entities of the credit-scoring project that the FeatureStore CR cloned from the tutorial repository:

curl -s -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H "mcp-session-id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"registry_list_entities","arguments":{"project":"credit_scoring_local"}}}'

The registry reports three entities (captured, abbreviated to the spec fields):

"entities": [
  {"spec": {"name": "zipcode",  "valueType": "INT64",  "joinKey": "zipcode"}},
  {"spec": {"name": "dob_ssn",  "valueType": "STRING",
            "description": "Date of birth and last four digits of social security number",
            "joinKey": "dob_ssn"}},
  {"spec": {"name": "__dummy",  "joinKey": "__dummy_id"}}
],
"pagination": {"totalCount": 3, "totalPages": 1}

Now fetch online feature values for two real dob_ssn entities that the materialization Job loaded into the online store:

curl -s -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H "mcp-session-id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"features_get_online_features","arguments":{"features":["credit_history:mortgage_due","credit_history:credit_card_due","credit_history:hard_pulls"],"entities":{"dob_ssn":["19530219_5179","19781116_7723"]}}}}'

Verify

The response reports isError: false and returns the materialized values (captured):

"metadata": {"feature_names": ["dob_ssn", "mortgage_due", "credit_card_due", "hard_pulls"]}
"results": [
  {"values": ["19530219_5179", "19781116_7723"], "statuses": ["PRESENT", "PRESENT"]},
  {"values": [91803, 741165], "statuses": ["PRESENT", "PRESENT"],
   "event_timestamps": ["2021-08-29T18:01:04Z", "2021-08-29T18:01:04Z"]},
  {"values": [8419, 2944], "statuses": ["PRESENT", "PRESENT"],
   "event_timestamps": ["2021-08-29T18:01:04Z", "2021-08-29T18:01:04Z"]},
  {"values": [0, 0], "statuses": ["PRESENT", "PRESENT"],
   "event_timestamps": ["2021-08-29T18:01:04Z", "2021-08-29T18:01:04Z"]}
]

Two call-shape rules, both learned the hard way on this cluster:

  • Do not list the entity key as a feature. Asking for "credit_history:dob_ssn" in features fails with Feature dob_ssn not found in projection credit_history — dob_ssn is the entity join key, not a feature. The server includes entity columns in the response metadata automatically.

  • features is required even when you pass a feature_service; a feature_service-only payload fails tool-argument validation with a missing-argument error.

Your agent can now read governed feature values over MCP. Make the endpoint discoverable to every agent in your project: Exercise 6 registers the server in the AI hub.

Exercise 6: Register the server in the AI hub

With the endpoint proven, make it discoverable. The Feast MCP server is not in the AI hub Catalog (that lists partner servers only) — self-hosted servers surface through the Registry.

  1. In the RHOAI dashboard, go to AI hub → MCP servers → Registry.

  2. Select your project from the project selector (the demo uses ai-tenants).

  3. Click + Create MCP server.

  4. Fill in the registration:

    • Name: feast-mcp

    • Transport: http (Streamable HTTP — the transport pinned in feast_mcp.yaml)

    • Endpoint: your Route URL with the /mcp path — for the demo cluster: https://feast-mcp-feast-mcp-demo.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com/mcp

  5. Save the registration.

Verify

The Registry list now shows a Feast MCP Server card (captured on the workshop cluster):

  • version 1.0.0, status Active, alias @latest

  • description "Governed feature access for AI agents through the Feast Model Context Protocol server (credit scoring demo)"

  • on the card’s Connect view, the access endpoint is streamable-http → https://…​/mcp — the same Route URL the governed arc just ran against

Open the card to confirm the endpoint details and the View raw server.json payload. This is the registration your AI agents consume; walk the same flow in the interactive demo walkthrough.

With the registration in place, one check remains — Exercise 7 confirms the server is healthy from the CLI.

Exercise 7: Confirm health — from the CLI

Health evidence for the demo comes from the CLI, which always works:

curl -s https://$ROUTE_HOST/health
curl -s -X POST https://$ROUTE_HOST/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H "mcp-session-id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"features_health","arguments":{}}}'

Verify

The unauthenticated health probe returns the status body (captured):

{"status":"healthy","service":"mcp-server"}

and the MCP features_health tool answers inside the authenticated session with isError: false (its success payload is an empty string — silence means healthy).

Do not rely on the AI hub Deployments tab for health checks. In this environment the tab fails to load components for any project (the dashboard’s mcp_deployments API answers HTTP 500, and the Deploy button on a Registry card is disabled). This is a platform-level issue, not a problem with your deployment — the CLI checks above are the dependable health evidence.

Module summary

What you accomplished:

  • Applied seven additive manifests and verified the FeatureStore reconciled Ready with an McpServer condition, one pod with registry/online/mcpserver containers, the mcpserver Service, and the edge-TLS Route

  • Proved the governed arc: tokenless 401 at /mcp, 200 at /health

  • Authenticated as feast-agent and discovered 22 tools over MCP

  • Retrieved real feature values for real entities and registered the server in the AI hub Registry

Key takeaways:

  • One Route, one endpoint: https://<route-host>/mcp is everything an agent needs

  • Governance is a config line (auth.mode: kubernetes) plus an RBAC identity — but authorization scoping needs Feast Permissions (Module 03)

  • The Registry tab is the discovery surface for self-hosted MCP servers; health is verified from the CLI
