Module 01: Core Concepts

In this module you will learn what the Feast MCP server is, how the standalone feast mcp process differs from the embedded MCP endpoint of a Feast feature server, and how the FeatureStore custom resource deploys it on RHOAI 3.6. You will inspect the live CRD schema on your cluster so every concept is tied to a field you can query.

Learning objectives:

  • Explain what an MCP server contributes to the Feature Store and what tools an AI agent gets

  • Distinguish the standalone feast mcp server from the embedded MCP feature-server endpoint

  • Identify the mcpServer block of the FeatureStore CRD and the feast_mcp.yaml it consumes

  • Describe the authorization modes (passthrough, kubernetes, oidc) and the operator default

Exercise 1: Where the Feast MCP server fits

The Feature Store exposes features to humans and programs: the Python SDK for notebooks, the feature server REST API for inference services. AI agents need a third door. An agent does not read documentation — it discovers tools and calls them. The Model Context Protocol is the emerging standard for that conversation: a client (the agent runtime) connects to a server, lists its tools with JSON Schemas, and invokes them.

The Feast MCP server is that server for the Feature Store. When an agent connects, the server introduces itself like this (captured from the MCP initialize response of a running feast-mcp deployment on RHOAI 3.6):

serverInfo: {"name": "feast", "version": "3.4.8"}
instructions: "Feast Feature Store — retrieve online features, search documents,
manage materialization, and browse the feature registry."

A tools/list call then returns 22 tools in two families:

  • features_ (9 tools)* — online feature retrieval (features_get_online_features), semantic search over feature descriptions (features_search), vector store access (features_list_vector_stores, features_get_vector_store, features_vector_store_search), data push (features_push), materialization (features_materialize, features_materialize_incremental), and health (features_health)

  • registry_ (13 tools)* — read access to the feature registry: registry_list_projects, registry_get_project, registry_list_entities, registry_get_entity, registry_list_feature_views, registry_get_feature_view, registry_list_features, registry_list_feature_services, registry_get_feature_service, registry_list_data_sources, registry_get_data_source, registry_search_registry, and registry_get_lineage

The registry tools are the agent’s map: before fetching features, the agent can list projects, entities, and feature views to discover what exists. The features tools are the agent’s hands: they return actual feature values. In this workshop the registry is the credit-scoring tutorial repository with 3 entities and 16 features.

Now that you have seen the tool surface an agent discovers, let’s look at where that MCP server can run.

Exercise 2: Standalone feast mcp versus the embedded MCP endpoint

Feast can serve MCP in two ways. The feast mcp --help output from the workshop image states the difference precisely:

Serves the Model Context Protocol in its own process, proxying to a running
Feast feature server and/or REST registry server. At least one of --feast-url
or --registry-url is required.

This is separate from `feast serve` with `mcp_enabled: true`, which mounts
an OpenAPI-derived MCP endpoint inside the feature server itself.

Settings resolve in priority order: CLI options, environment variables,
feast_mcp.yaml, defaults.

The embedded mode turns on MCP inside an existing Feast server. In the FeatureStore CRD the toggles are:

  • services.onlineStore.serving.mcp — "Mcp enables MCP (Model Context Protocol) server support. When set, feature server type is mcp."

  • services.registry.local.server.mcp — "Mcp enables MCP (Model Context Protocol) on the REST registry server. Requires restAPI to be true."

The standalone mode runs feast mcp as its own container. It proxies to a running feature server and/or REST registry, which means the MCP process, its configuration, and its authorization policy are independent of the Feast services it fronts. That independence is what the RHOAI 3.6 Feast operator exploits: spec.services.mcpServer deploys the standalone server as an additional container, so the governed-access story (Module 02) can be built and changed without touching the feature server or registry.

The registry tools require the REST registry (services.registry.local.server.restAPI: true): the standalone MCP server speaks to the registry over REST, not gRPC.

With the two deployment shapes distinguished, you are ready to inspect the operator’s CRD block for the standalone server.

Exercise 3: The mcpServer block of the FeatureStore CR

With the Feast operator installed, the CRD schema on your cluster documents the standalone server. Inspect it:

oc explain featurestore.spec.services.mcpServer

You should see output like the following (captured on the workshop cluster):

GROUP:      feast.dev
KIND:       FeatureStore
VERSION:    v1

FIELD: mcpServer <Object>


DESCRIPTION:
    McpServer deploys a standalone Feast MCP (Model Context Protocol) server
    container (`feast mcp`).

FIELDS:
  config	<Object>
    Config references a ConfigMap holding the feast_mcp.yaml file passed to
    `feast mcp --config`.
  ...

The fields that matter for this workshop:

  • config.configMapRef (required) — a ConfigMap in the same namespace holding the feast_mcp.yaml file, passed to feast mcp --config. This is where the transport, the upstream Feast URLs, and the auth mode are pinned.

  • logLevel, metrics, resources, workerConfigs, tls — the usual server tuning knobs, shared with the other Feast services.

When you apply a FeatureStore CR with this block, the operator produces:

  • One pod with three containers — registry, online, and mcpserver

  • A Service named feast-<cr-name>-mcpserver exposing port 80, which forwards to the MCP container listening on port 8100

  • A health endpoint at /health on the MCP container — deliberately unauthenticated, so load balancers and the dashboard can probe it without credentials

  • gRPC and REST registry services plus the online feature server, all inside the same pod

The feast_mcp.yaml used in Module 02 pins five settings (full file in deploy/10-feast-mcp-config.yaml):

server:
  transport: http <1>
features:
  url: http://localhost:6566 <2>
registry:
  url: http://localhost:6572 <3>
auth:
  mode: kubernetes <4>
timeout: 30 <5>
1 server.transport: http — the MCP server speaks Streamable HTTP on its Service.
2 features.url — the feature server (online reads) inside the same pod.
3 registry.url — the REST registry that feeds the registry_* tools.
4 auth.mode: kubernetes — every MCP call validates the caller’s token with a Kubernetes Token Access Review. This is the governed demo mode.
5 timeout: 30 — HTTP timeout in seconds for calls to Feast.

Verify

You already ran the verify command above: oc explain featurestore.spec.services.mcpServer must show the field description that starts with "McpServer deploys a standalone Feast MCP (Model Context Protocol) server container (feast mcp)". If it errors instead, the Feast operator is not installed — enable the feastoperator component as shown in Module 01 of the Feature Store workshop and retry.

With the mcpServer block and its feast_mcp.yaml pinned, one question remains: who may call the server. Exercise 4 walks the three authorization modes.

Exercise 4: Authorization modes — who may call the server

The standalone server has three auth modes, straight from feast mcp --help:

--auth-mode [passthrough|kubernetes|oidc]
    Auth mode. 'kubernetes' checks ServiceAccount and user tokens with
    Token Access Review, and only works inside a cluster.
    [default: passthrough]

  • passthrough (default) — no authentication check: all calls are accepted and the token, if any, is merely forwarded. Convenient for local development; a governance hole if exposed.

  • kubernetes — the mode used in this workshop. Every MCP request must carry a Kubernetes token; the server validates it with a Token Access Review before acting. Tokenless calls get HTTP 401 with a www-authenticate: Bearer challenge. The Feast services behind it are also protected: on RHOAI 3.6 the Feast operator enables Kubernetes authentication for deployed services by default.

  • oidc — validates OIDC tokens against an identity provider. Configured through a Secret; covered in Module 03.

Kubernetes auth answers "are you authenticated?" — not "what are you allowed to do?". In the default configuration, any valid token gets full access to all 22 tools. Scope comes from Feast Permissions and spec.authz.kubernetes.roles, which you will add in Module 03.

One more thing to know before Module 02: the Feast MCP server is not in the AI hub MCP servers → Catalog. The Catalog lists partner-provided servers only (there is no Feast card). Your server becomes visible under MCP servers → Registry after you register its Route URL there — that registration is Exercise 6 of the hands-on module.

Verify

Inspect the CRD-level authorization settings:

oc explain featurestore.spec.authz

You should see the three authorization shapes (captured on the workshop cluster):

FIELD: authz <Object>

DESCRIPTION:
    AuthzConfig defines the authorization settings for the deployed Feast
    services.

FIELDS:
  kubernetes	<Object>
    KubernetesAuthz provides a way to define the authorization settings using
    Kubernetes RBAC resources.
  noAuth	<boolean>
    NoAuth explicitly disables authentication and authorization.
  oidc	<Object>
    OidcAuthz defines the authorization settings for deployments using an Open
    ID Connect identity provider.

Module summary

What you accomplished:

  • Learned what the Feast MCP server offers an AI agent: 22 discoverable tools across the features_* and registry_* families

  • Distinguished the standalone feast mcp process from the embedded MCP endpoint (mcp_enabled: true, services.onlineStore.serving.mcp, services.registry.local.server.mcp)

  • Inspected the mcpServer CRD block and the feast_mcp.yaml it consumes

  • Reviewed the passthrough, kubernetes, and oidc auth modes and the RHOAI 3.6 operator default

Key takeaways:

  • The standalone server is the governance point: it fronts the Feast services and enforces the auth mode on every call

  • auth.mode: kubernetes makes the server validate tokens with Token Access Review — tokenless means 401

  • The AI hub Catalog is for partner servers; the Feast MCP server surfaces via Registry registration
