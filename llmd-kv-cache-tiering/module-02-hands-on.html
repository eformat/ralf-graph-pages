Module 02: Hands-on Exercise

In this module you will work through the cache-aware routing workflow end to end: you will inspect the live scheduling and flow-control configuration that makes RHOAI 3.6 model serving KV-cache-aware, verify that this routing stack is attached to and running for the deployed model in your project, and observe the metrics that show KV cache behavior during inference.

Learning objectives:

  • Inspect the live KV-cache-aware scheduling preset and the scheduler’s effective flow-control configuration with oc

  • Verify the cache-aware routing stack on a deployed model — the routing presets in spec.baseRefs, the running pods, and the serving-path conditions

  • Observe the live llm_d_epp_ metrics that report KV cache utilization and flow control for your inference pool

Exercise 1: Explore the KV-cache-aware routing configuration

Routing behavior for llm-d model serving is assembled from routing presets: LLMInferenceServiceConfig resources that an LLMInferenceService combines into its effective configuration. A deployment names presets in its spec.baseRefs list, and the platform adds its well-known defaults on top — the PresetsCombined=True condition on the LLMInferenceService reports that the combination succeeded. Custom presets are optional, and none are pre-provisioned in this environment: RHOAI 3.6 ships no router-labeled configs, which you can verify yourself:

oc get llminferenceserviceconfig -A -l opendatahub.io/config-type=router

Expected output:

No resources found

Creating a custom router preset is YAML-driven, not a dashboard exercise. For reference — so you can recognize the shape if you meet one in the wild — this is what a custom router preset looks like. Do not create it; this workshop inspects the live default instead:

apiVersion: serving.kserve.io/v1alpha2
kind: LLMInferenceServiceConfig
metadata:
  name: kv-cache-router-single-node
  labels:
    opendatahub.io/config-type: router (1)
  annotations:
    opendatahub.io/supported-topologies: '["workload-single-node"]' (2)
spec:
  router:
    scheduler:
      replicas: 1 (3)
      config:
        inline: |
          plugins:
          - name: prefix-cache-scorer
            weight: 100 (4)
          - name: queue-scorer
            weight: 50
    route: {}
    gateway: {}
1 opendatahub.io/config-type: router — an optional categorizing label; RHOAI 3.6 ships no presets carrying the router value, so a preset like this is something an administrator would author as YAML.
2 opendatahub.io/supported-topologies — optional metadata describing which deployment topologies the preset suits.
3 spec.router.scheduler.replicas — the scheduler replica; the KV-cache-aware routing component runs here.
4 Inline plugin config — this reference example uses the older scorer-weight format; the 3.6 default preset instead uses the llm-d.ai/v1 producer/filter/scorer plugins you met in module 01.

Inspect the live default scheduling preset

The KV-cache-aware scheduling default is itself a preset, shipped and managed by the platform. Module 01 introduced its four plugins; here you open the live resource and read it:

oc get llminferenceserviceconfig -n redhat-ods-applications \
  v3-6-0-kserve-config-llm-scheduler-eppconfig-default -o yaml

The spec.router.scheduler.config.inline section holds the scheduling configuration — apiVersion llm-d.ai/v1, kind EndpointPickerConfig, with scheduling profile default activating the prefix-cache-affinity filter and the token-load scorer:

apiVersion: llm-d.ai/v1
kind: EndpointPickerConfig
plugins:
- type: approx-prefix-cache-producer
- type: inflight-load-producer
- type: prefix-cache-affinity-filter
- type: token-load-scorer
schedulingProfiles:
- name: default
  plugins:
  - pluginRef: prefix-cache-affinity-filter
  - pluginRef: token-load-scorer

The status section tells you this preset is live and in use (timestamps and ages will differ on your cluster):

status:
  conditions:
  - message: referenced by 2 LLMInferenceService(s)
    reason: InUse
    severity: Info
    status: "True"
    type: ConfigInUse
  - status: "True"
    type: Ready
  referencedBy:
  - name: cpu-demo-llm
    namespace: abc123-user1
  - name: maas-llmd-demo
    namespace: abc123-user1

ConfigInUse=True with a referencedBy list naming the two models deployed in your project namespace (abc123-user1) — this is the preset your models are actually scheduled with.

Read the scheduler’s effective flow-control configuration

The scheduling preset decides where each request is routed. The flow-control layer decides when requests are dispatched — module 01 noted that the queue-depth and KV-cache-utilization thresholds live there. That layer is the llm-d router scheduler process itself, and its effective configuration is passed to it as the --config-text container argument. Find the scheduler pod and print the argument:

POD=$(oc get pods -n abc123-user1 \
  -l app.kubernetes.io/component=llminferenceservice-router-scheduler \
  -o jsonpath='{.items[0].metadata.name}')
oc get pod $POD -n abc123-user1 -o jsonpath='{.spec.containers[0].args[1]}'

Expected output:

apiVersion: llm-d.ai/v1alpha1
featureGates:
- flowControl
flowControl:
  saturationDetector:
    pluginRef: utilization-detector
kind: EndpointPickerConfig
plugins:
- name: utilization-detector
  parameters:
    kvCacheUtilThreshold: 0.8
    metricsStalenessThreshold: 200ms
    queueDepthThreshold: 5
  type: utilization-detector
- parameters:
    scheme: https
  type: metrics-data-source

This is the KV-cache-aware control loop, in the cluster’s own words:

  • metrics-data-source with scheme: https — the scheduler reads live pool metrics over TLS, and metricsStalenessThreshold: 200ms says a metric older than that is too stale to schedule on.

  • kvCacheUtilThreshold: 0.8 — a replica whose KV cache utilization crosses 80% counts as saturated.

  • queueDepthThreshold: 5 — five or more requests waiting in a queue also counts as saturation.

  • saturationDetector.pluginRef: utilization-detector — the plugin that combines these signals for flow control: when a replica is saturated, new requests are queued (back-pressured) instead of being pushed onto cache-hot replicas.

You will watch the matching metrics in Exercise 3.

Verify

You read the live default scheduling preset (llm-d.ai/v1, profile default, the four llm-d plugins, ConfigInUse=True and Ready=True, referencing both workshop models) and the scheduler’s effective flow-control configuration (utilization-detector with kvCacheUtilThreshold: 0.8, queueDepthThreshold: 5, metrics over https with a 200 ms staleness threshold) — and you can explain what makes the router treat a replica as saturated.

Now that you have seen the configuration the routing stack runs with, you will verify that the deployed model actually uses it.

Exercise 2: Verify the cache-aware routing stack on the deployed model

Your project namespace (abc123-user1) already contains the workshop’s model deployment maas-llmd-demo, deployed with default optimized routing. Rather than creating a new deployment in the dashboard wizard, you will verify — entirely with oc — that the cache-aware routing stack you inspected in Exercise 1 is attached to and running for this model. The same three checks apply to any model you deploy later.

  1. Confirm the routing presets the model references. The baseRefs list names the LLMInferenceServiceConfig presets that this deployment explicitly references:

    oc get llmisvc maas-llmd-demo -n abc123-user1 -o yaml | grep -A 6 baseRefs

    Expected output:

      baseRefs:
  - name: v3-6-0-kserve-config-llm-template-cpu
  model:
    name: maas-llmd-demo
    uri: oci://quay.io/redhat-ai-services/modelcar-catalog:qwen2.5-0.5b-instruct
  router:
    route:

    baseRefs lists the CPU template preset. The KV-cache-aware scheduling preset you read in Exercise 1 is a platform well-known default that the controller combines in automatically: the PresetsCombined=True condition you will see below confirms the combination, and the preset’s own status lists maas-llmd-demo under referencedBy. The flow-control configuration itself is embedded in this resource at spec.router.scheduler.config.inline — the same text you read from the scheduler pod in Exercise 1.

  2. Check that the serving pods are running:

    oc get pods -n abc123-user1 -l app.kubernetes.io/name=maas-llmd-demo

    Expected output (pod-name suffixes and AGE values will differ on your cluster):

    NAME                                                      READY   STATUS    RESTARTS   AGE
maas-llmd-demo-kserve-9cd6b9756-lgmkc                     2/2     Running   0          5h13m
maas-llmd-demo-kserve-router-scheduler-597d95c79b-sbgdd   1/1     Running   0          5h35m

    Both the model server and the router scheduler must be Running — the router scheduler is the pod whose configuration you read in Exercise 1.

  3. Inspect the LLMInferenceService conditions:

    oc get llmisvc maas-llmd-demo -n abc123-user1 \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"\n"}{end}'

    Expected output:

    HTTPRoutesReady=True
InferencePoolReady=True
MainWorkloadReady=False
PresetsCombined=True
Ready=False
RouterReady=True
SchedulerWorkloadReady=True
WorkloadsReady=False

On this workshop cluster the top-level Ready, WorkloadsReady, and MainWorkloadReady conditions report False (reason ReconcileSingleNodeWorkloadError — a Kueue queue-name label immutability conflict during workload reconciliation) even though the model serves normally. Every condition that describes the serving data path — HTTPRoutesReady, InferencePoolReady, PresetsCombined, RouterReady, SchedulerWorkloadReady — is True, and both pods are Running. Do not treat the Ready column on the dashboard’s Models tab as the go signal in this environment; trust the pods, the serving-path conditions, and an actual request, which is the final check below.

  1. The definitive check is a real inference request. Exercise 3 walks through the authenticated request against this model — a curl with a bearer token that returns HTTP 200 and a chat-completion body. Once you see that 200, you have verified the full path: preset combination, router scheduler, and model server.

Verify

Your deployed model references its routing preset in spec.baseRefs, both serving pods are Running, and every serving-path condition (PresetsCombined, RouterReady, HTTPRoutesReady, InferencePoolReady, SchedulerWorkloadReady) is True — and you know why this environment reports Ready=False while serving.

Now that you have verified the routing stack, you will observe the KV cache metrics it produces.

Exercise 3: Observe KV cache behavior with metrics

The Endpoint Picker (EPP), or inference scheduler, exposes Prometheus metrics at the /metrics endpoint on its metrics service, port 9090. The endpoint is protected: it speaks TLS and requires a bearer token, returning 401 Unauthorized without one. Metrics use the llm_d_epp_ prefix. The most useful ones for cache-tiering behavior are:

Metric What to observe

llm_d_epp_average_kv_cache_utilization

Average KV cache utilization across the inference pool (series label name="maas-llmd-demo-inference-pool"); rises while running requests fill the cache

llm_d_epp_std_dev_kv_cache_utilization

Standard deviation of KV cache utilization across endpoints — a growing spread means the load sits unevenly on the pool

llm_d_epp_flow_control_pool_saturation

Flow-control saturation signal, labeled by pipeline stage: stage="prefill" and stage="decode" are per-stage signals, stage="effective" is the max of the two and the value used for gating. 1.0 is the gating set point; values above it mean the pool is oversubscribed

llm_d_epp_flow_control_queue_size

Number of requests currently held in the flow-control queue — the back-pressure mechanism in action

llm_d_epp_request_ttft_seconds

Time-to-first-token histogram (_count, _sum, _bucket series) — the latency signal; on non-streaming requests TTFT equals the total request duration

llm_d_epp_request_total

Counter of processed requests, labeled by model — a sanity check that traffic is flowing through the scheduler (context)

llm_d_epp_ready_endpoints

Number of ready endpoints in the inference pool (context)

  1. Send the same conversational request several times so the pool carries real traffic for the metrics steps. Store the endpoint URL in a shell variable, reading it directly from the LLMInferenceService status (or copy the Inference endpoint URL from your model details page). This URL already ends in /v1, so the request path appends only /chat/completions:

    export INFER_URL=$(oc get llmisvc -n abc123-user1 \
  -o jsonpath='{.items[?(@.metadata.name=="maas-llmd-demo")].status.url}')
export TOKEN=$(oc whoami -t)
curl -k $INFER_URL/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "maas-llmd-demo", "messages": [{"role": "user", "content": "What is Red Hat OpenShift AI?"}]}'

    The Authorization header is required: without the bearer token the same request returns HTTP 401 with {"error": {"message": "Authentication required", …​}}. The model field is the serving name of the workshop’s deployed model, maas-llmd-demo — a qwen2.5-0.5b-instruct CPU modelcar. A successful response returns HTTP 200 with a chat-completion body — JSON with "object": "chat.completion", "model": "maas-llmd-demo", and the generated answer in choices[0].message.content. Repeat the request three or four times without changing the message. If the URL you copied does not end in /v1, append /v1/chat/completions instead.

  2. Fetch the metrics. The EPP publishes them on the maas-llmd-demo-epp-service service in your project, port 9090 — the same TLS + bearer-token protection as the inference route. Try it without a token first, then authenticate and store the output:

    curl -sk https://maas-llmd-demo-epp-service.abc123-user1.svc.cluster.local:9090/metrics
# -> Unauthorized (HTTP 401)

TOKEN=$(oc whoami -t)
curl -sk -H "Authorization: Bearer $TOKEN" \
  https://maas-llmd-demo-epp-service.abc123-user1.svc.cluster.local:9090/metrics \
  > epp-metrics.txt
# -> HTTP 200

    With the token the endpoint returns 200 and the full Prometheus exposition. Filter it for the pool metrics from the table above:

    grep -E "^llm_d_epp_(average_kv_cache_utilization|std_dev_kv_cache_utilization|flow_control_pool_saturation|flow_control_queue_size|request_total|ready_endpoints)" epp-metrics.txt

    On an idle pool you will see utilization and queue-size gauges near 0, ready_endpoints at the number of live model replicas, and llm_d_epp_request_total{model_name="maas-llmd-demo"} incrementing with every request you sent in the previous step.

  3. Interpret what you see against the flow-control thresholds you read off the scheduler in Exercise 1 (kvCacheUtilThreshold: 0.8, queueDepthThreshold: 5):

    • llm_d_epp_request_total and the llm_d_epp_request_ttft_seconds_count / _sum series increment with every processed request — they are proof that the scheduler is routing traffic. On this CPU model a non-streaming chat completion’s TTFT equals its total duration, so the histogram is also your latency story.

    • While requests are in flight, llm_d_epp_average_kv_cache_utilization rises as running requests fill the cache, and llm_d_epp_std_dev_kv_cache_utilization shows how unevenly that load sits across endpoints. On an idle pool both read 0.

    • The flow-control pair is the back-pressure story: when a replica’s KV cache utilization crosses the 80% threshold or five or more requests wait in its queue, the utilization-detector plugin considers the pool saturated — llm_d_epp_flow_control_pool_saturation{stage="effective"} climbs past the 1.0 gating set point, and flow control holds new requests in the queue (llm_d_epp_flow_control_queue_size grows) instead of pushing them onto the busy replica.

The vLLM parameters that shape how quickly the KV cache saturates depend on the deployment’s hardware. This workshop’s model is a CPU modelcar, so its capacity is set by VLLM_CPU_KVCACHE_SPACE (GiB of memory reserved for the KV cache — 4 here) and OMP_NUM_THREADS (CPU threads per replica — 4 here). On GPU deployments the equivalents are --gpu-memory-utilization (fraction of GPU memory for the KV cache: 0.6-0.7 for latency-sensitive workloads, 0.85-0.9 for throughput-optimized ones) and --max-model-len (KV cache memory per request). Adjust these only if you need to tune saturation behavior.

The metrics fetch above resolves the EPP service’s in-cluster DNS name, so run it from an environment that can reach cluster services — the workshop workbench, or any terminal with oc access. From anywhere with oc, you can also read the metrics through a running pod, for example the router scheduler (the $TOKEN variable from the previous step is expanded by your local shell before oc exec runs):

+

oc exec -n abc123-user1 \
  $(oc get pods -n abc123-user1 \
    -l app.kubernetes.io/component=llminferenceservice-router-scheduler \
    -o jsonpath='{.items[0].metadata.name}') \
  -c main -- curl -sk \
  -H "Authorization: Bearer $TOKEN" \
  https://maas-llmd-demo-epp-service.abc123-user1.svc.cluster.local:9090/metrics

Verify

You sent authenticated requests — 401 without the bearer token, 200 with it — fetched the EPP metrics over TLS with the same token, and watched the llm_d_epp_ signals move the way the flow-control configuration predicts: request_total and the TTFT histogram counting every request, KV cache utilization rising while requests run, and flow_control_pool_saturation plus flow_control_queue_size as the back-pressure mechanism once a replica crosses its thresholds.
