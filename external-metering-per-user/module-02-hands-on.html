Module 02: Hands-on Exercise

In this module you run the commands yourself. You inspect the MaaS configuration that turns on per-user usage logging, examine the OpenTelemetry Collector that records usage, read the DSCInitialization configuration that forwards usage records to external metering backends, and query per-user token usage through the user-scoped gateway route.

Learning objectives:

  • Inspect the MaaS Config resource and confirm that usage logging and the usage metrics dashboard are enabled

  • Read the usage-logs OpenTelemetry Collector pipeline: receivers, attribute processors, and the Loki exporter endpoint

  • Describe the DSCInitialization spec.monitoring.usageLogs schema — the external-metering knob — and the dual-write versus forward-only choice it encodes

  • Run per-user LogQL queries through the data-science-usage-logs route and read tokens_total on the Perses usage dashboards

Exercise 1: Inspect the MaaS usage-logging configuration

Everything in this workshop starts from one resource: the MaaS Config named default in the models-as-a-service namespace. Its usageLogging flag turns on the per-user usage-record pipeline you walked in Module 01, and usageMetricsDashboard deploys the Perses usage dashboards.

  1. Check that the two flags are enabled. Because the value fields are nested in spec, query them with a JSONPath expression:

    oc get configs.maas.opendatahub.io default -n models-as-a-service \
  -o jsonpath='{.spec.usageLogging}{" "}{.spec.usageMetricsDashboard}{" "}{.spec.limitadorScrapeInterval}{"\n"}'

Expect exactly:

true true 30s

usageLogging: true means every authorized inference call produces a usage record; usageMetricsDashboard: true deploys the Perses dashboards of Exercise 4; limitadorScrapeInterval: 30s sets how often the gateway’s Limitador call metrics are scraped. There is no per-user opt-in to configure — with usage logging on, usage records carry the caller’s identity by default.

  1. Confirm the resource itself is healthy:

    oc get configs.maas.opendatahub.io default -n models-as-a-service \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" ("}{.reason}{")"}{"\n"}{end}'

Expect both conditions to be True:

Ready=True (AllOperandsReady)
TenantsHealthy=True (AllTenantsHealthy)

Verify

The Config resource reports usageLogging=true, usageMetricsDashboard=true, and Ready=True — the cluster-wide switch for per-user usage logging is on.

With logging switched on, the next step is to see the component that actually writes the records.

Exercise 2: Inspect the collector that records usage

With usage logging enabled, the MaaS controller manages an OpenTelemetry Collector named usage-logs in the redhat-ods-applications namespace. This exercise reads its pipeline so you can name every hop a usage record takes.

  1. Confirm the collector is deployed and managed:

    oc get opentelemetrycollector usage-logs -n redhat-ods-applications

Expect a deployment-mode collector with both replicas ready:

NAME         MODE         VERSION   READY   AGE     IMAGE                                                                                                                             MANAGEMENT
usage-logs   deployment   0.158.0   2/2     4h52m   registry.redhat.io/rhosdt/opentelemetry-collector-rhel9@sha256:b71f75d039eb8bae222f2318fbd781640affdcb7d1a4ed8219576d6b0677a0c7   managed

  1. Read the collector pipeline. The configuration is embedded in the CR under .spec.config:

    oc get opentelemetrycollector usage-logs -n redhat-ods-applications \
  -o jsonpath='{.spec.config}' | python3 -m json.tool | head -60

Expect a logs pipeline shaped like this (abridged):

exporters:
  otlp_http/loki:
    auth:
      authenticator: bearertokenauth
    endpoint: https://usage-gateway-http.${env:NAMESPACE}.svc:8080/api/logs/v1/application/otlp
    tls:
      ca_file: /etc/pki/ca-trust/extracted/pem/service-ca.crt
processors:
  groupbyattrs:
    keys:
    - subscription
    - model
    - response_type
  resource:
    attributes:
    - action: upsert
      key: log_type
      value: application
    - action: upsert
      key: service.name
      value: models-as-a-service
    - action: upsert
      key: kubernetes_namespace_name
      value: ${env:NAMESPACE}
  transform:
    error_mode: ignore
    log_statements:
    - context: log
      statements:
      - replace_pattern(attributes["user_id"], "\"", "")
      - replace_pattern(attributes["subscription"], "\"", "")
      - replace_pattern(attributes["key_name"], "\"", "")
      - replace_pattern(attributes["groups"], "\"", "")
      - replace_pattern(attributes["organization_id"], "\"", "")
      - replace_pattern(attributes["cost_center"], "\"", "")
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317

Walk the pipeline:

  • Receiver — the collector accepts usage records over OTLP gRPC on port 4317; the MaaS controller pushes records there.

  • Attribute processors — the resource processor stamps log_type=application, service.name=models-as-a-service, and the tenant namespace onto every record; the transform processor strips quoting artifacts from the six identity attributes — user_id, subscription, key_name, groups, organization_id, and cost_center — so they can be grouped and labeled; groupbyattrs groups records by subscription, model, and response_type.

  • Exporter — records leave as OTLP/HTTP to https://usage-gateway-http.${env:NAMESPACE}.svc:8080/api/logs/v1/application/otlp, the gateway of the data-science-usage-logs LokiStack, authenticated with the collector’s service-account token and the cluster service CA.

Pipeline state on this cluster — the exporter endpoint name usage-gateway-http is an alias service the facilitator stages through the workshop’s in-tree manifests alongside the data-science-usage-logs LokiStack (set up by the Loki-based showback workshop). Until it resolves, incoming usage records are still received but cannot be exported — the collector log then repeats Exporting failed. Dropping data. with lookup usage-gateway-http.redhat-ods-applications.svc … no such host. You can see the current state yourself: 
oc logs -n redhat-ods-applications deployment/usage-logs-collector --tail=100 | grep -c "Dropping data"

0 means records are exporting cleanly; a positive count means the alias is not staged yet and Exercise 4’s queries will return empty results until your facilitator restores it.

Verify

You can point at the OTLP receiver port, list the six identity attributes the processors normalize, and name the LokiStack gateway endpoint the exporter ships records to.

The collector writes records into the cluster’s local usage store. What you cannot see yet is the external side of the story — the knob this feature is named after.

Exercise 3: Read the external-metering knob: DSCI spec.monitoring.usageLogs

Everything so far stores usage inside the cluster. External metering is the usageLogs stanza in DSCInitialization.spec.monitoring: it configures usage log collection and forwarding to Loki — including backends outside the cluster. This exercise is read-only: you inspect the schema and the current cluster state, and prepare the manifest that a facilitator would apply.

  1. Read the schema straight from the installed CRD:

    oc explain dscinitialization.spec.monitoring.usageLogs

Expect five fields:

FIELD: usageLogs <Object>

DESCRIPTION:
    UsageLogs configures usage log collection and forwarding to Loki.

FIELDS:
  attributes	<map[string]string>
  credentialSecret	<string>
  exporters	<map[string]Object>
  size	<string>
  storage	<Object>

  • exporters — additional usage-log exporters in OpenTelemetry Collector format. Each one forwards a copy of every usage record to an observability backend outside the cluster — typically a LokiStack on a fleet-management hub. The local write stays untouched, which makes this a dual-write; if storage is omitted, the exporters are the only destination (forward-only, and no local LokiStack is deployed). At most 10 exporters, and the exporter name otlphttp/loki is reserved.

  • credentialSecret — name of a Secret in the monitoring namespace holding a bearer token under the key token; an exporter selects it with auth: {authenticator: bearertokenauth/remote}. The token is never written into the collector object, and rotating the Secret reaches a running collector.

  • attributes — resource attributes stamped onto exporter records only (so a cluster identity here cannot disturb the spoke-local pipeline). Set cluster_name and cluster_id to attribute usage records to the cluster that produced them in a multi-cluster fleet. Up to 20 entries.

  • size — LokiStack t-shirt size for the usage-log store. The default, 1x.extra-small, reserves 2 CPU and 8Gi per ingester — on a small cluster the LokiStack then never reports Ready and the collector is never deployed; 1x.pico fits small clusters. Ignored when storage is omitted.

  • storage — the LokiStack object storage backend (type: s3 plus a secretName). When configured, the operator deploys a LokiStack instance and auto-configures the local collector endpoint.

    1. Note the API’s own consistency rule — a usageLogs stanza must configure storage and/or at least one exporter; otherwise the API server rejects the change with usageLogs requires storage and/or at least one exporter.

    2. Check what this cluster currently runs:

      oc get dsci default-dsci -o jsonpath='{.spec.monitoring}'

Expect the monitoring stanza without a usageLogs key — the cluster runs storage-only forwarding (the local data-science-usage-logs LokiStack of Module 01), and no external exporter is configured:

{"alerting":{},"managementState":"Managed","metrics":{"replicas":1,"storage":{"retention":"90d","size":"5Gi"}},"namespace":"redhat-ods-monitoring","traces":{"sampleRatio":"0.1","storage":{"backend":"pv","retention":"2160h0m0s","size":"5Gi"}}}

  1. Compare your state against the dual-write example staged in this workshop’s tree at deploy/50-dsci-usage-logs-hub-exporter.yaml:

apiVersion: dscinitialization.opendatahub.io/v2
kind: DSCInitialization
metadata:
  name: default-dsci
spec:
  applicationsNamespace: redhat-ods-applications
  monitoring:
    managementState: Managed
    namespace: redhat-ods-monitoring
    usageLogs:
      size: 1x.pico
      storage:
        type: s3
        secretName: data-science-usage-logs-s3
      credentialSecret: usage-logs-hub-token
      exporters:
        otlphttp/hub-loki:
          endpoint: https://hub-lokistack-gateway-http-openshift-logging.apps.hub.example.com/api/logs/v1/application/otlp
          auth:
            authenticator: bearertokenauth/remote
          tls:
            ca_file: /etc/pki/ca-trust/extracted/pem/service-ca.crt
      attributes:
        cluster_name: ocp5-m6wl4-2plgg
        cluster_id: 00000000-0000-0000-0000-000000000000

Applying the example changes cluster state: the operator redeploys the usage-logs collector with the extra exporter, and every subsequent usage record is copied to the hub endpoint. Do not apply it with an ad-hoc oc patch — the DSCInitialization is managed by the workshop’s GitOps tree, so the manifest is applied by your facilitator through the workshop’s in-tree manifests/overlay, and the same change must be committed to that tree.

Verify

You can name the five usageLogs fields, explain the difference between dual-write (storage kept, exporters added) and forward-only (storage omitted), and point at the fleet-attribution attributes cluster_name and cluster_id. The cluster itself is still storage-only — which is exactly the "before" state external metering extends.

With the external path understood, the last exercise goes back to the data itself: querying your own usage records.

Exercise 4: Query per-user usage through the gateway route

The data-science-usage-logs LokiStack is not queried directly. Two user-facing access paths sit in front of it:

  • The public route data-science-usage-logs (in the redhat-ods-monitoring namespace) exposes the LokiStack gateway. It authenticates callers with their OpenShift token and scopes queries to the application tenant — this is the path this exercise uses.

  • The usage-logs tenancy proxy (usage-logs-tenancy-proxy service) fronts Loki for the user-scoped dashboard: it validates the caller’s token via a TokenReview, rewrites every query by injecting | user_id="<your-username>" immediately after each stream selector, and forwards it with the application tenant scope — so a query that arrives through the proxy can only ever return your own records.

    1. Query per-user usage through the route. The Loki API path through the gateway is /api/logs/v1/application/loki/api/v1/query_range, you authenticate with your own OpenShift token, and the query groups records by user_id so the result is one series per user:

      ROUTE=$(oc get route data-science-usage-logs -n redhat-ods-monitoring \
  -o jsonpath='{.spec.host}')
curl -sS -H "Authorization: Bearer $(oc whoami -t)" \
  "https://$ROUTE/api/logs/v1/application/loki/api/v1/query_range?query=sum%20by%20(user_id)%20(count_over_time(%7Bservice_name%3D%22models-as-a-service%22%7D%5B24h%5D))"

Expect a successful Loki matrix response, one series per user_id:

{"status":"success","data":{"resultType":"matrix","result":[
  {"metric":{"user_id":"user1"},"values":[[1732740000,"42"]]}
],...}}
Pipeline-restored state required — the query path above is live and returns status: success on this cluster today, but result is empty until records land: the exporter endpoint of Exercise 2 must resolve and a MaaS inference call must have been made first. On a cluster where the usage-gateway-http alias is staged, generate a call against a MaaS model and re-run the query to see one series per user_id.

  1. Ask the same data the dashboards ask: per-user token consumption. The Perses usage dashboards aggregate the tokens_total field of usage records from successful requests (response_type="hit"), grouped by user and organization:

    ROUTE=$(oc get route data-science-usage-logs -n redhat-ods-monitoring \
  -o jsonpath='{.spec.host}')
curl -sS -H "Authorization: Bearer $(oc whoami -t)" \
  "https://$ROUTE/api/logs/v1/application/loki/api/v1/query_range?query=sum%20by%20(user_id%2Corganization_id%2Ccost_center)%20(sum_over_time(%7Bservice_name%3D%22models-as-a-service%22%2Cresponse_type%3D%22hit%22%7D%20%7C%20unwrap%20tokens_total%20%5B24h%5D))"

Expect one result series per user with their accumulated tokens_total, and the organization_id and cost_center labels cost attribution groups on.

  1. Read the same numbers in the Perses dashboards. In the OpenShift AI console, navigate to Observe & monitor → Metrics; the dashboards render as tabs.

    • dashboard-4-maas-usage-logs-admin — the administrator view, backed by the usage-logs-all datasource. Its Token consumption chart and Usage breakdown table run exactly the sum_over_time(…​ | unwrap tokens_total) pattern above, grouped by user_id, model, subscription, organization_id, and cost_center.

    • dashboard-5-maas-usage-logs — the user-scoped view, backed by the usage-logs-multi-tenancy datasource that points at the tenancy proxy. Every panel is filtered to your identity, whatever the panel author wrote — the injected | user_id="<your-username>" stage enforces it.

    • dashboard-3-maas-usage-admin — request and call counts from Limitador (authorized_calls_total, authorized_hits_total, limited_calls_total). These count requests and authorization events, not tokens: authorized_hits_total is a hit counter labeled by user, model, subscription, and limitador_namespace — it is not a token total.

Metric accuracy — token consumption and request counts are different quantities from different pipelines. tokens_total comes from the usage-log pipeline (the records of Exercise 2, surfaced in dashboard-4 and dashboard-5) and is the per-user token consumption external metering bills on. The Limitador metrics come from the gateway’s metric endpoint (surfaced in dashboard-3) and measure how many requests were authorized, limited, or rejected. Never read authorized_hits_total as "total tokens consumed".

Verify

You can run a per-user LogQL query through the data-science-usage-logs route with your own token, state which datasource enforces user scoping (usage-logs-multi-tenancy via the tenancy proxy), and say which metric answers "how many tokens did this user consume" (tokens_total, usage-log pipeline) versus "how many requests did this user make" (Limitador call metrics, dashboard-3).

Module summary

What you accomplished:

  • Inspected the MaaS Config resource and confirmed usage logging, the usage metrics dashboard, and the Limitador scrape interval

  • Read the usage-logs OpenTelemetry Collector pipeline from receiver to LokiStack exporter, including its attribute processors

  • Inspected the DSCInitialization spec.monitoring.usageLogs external-metering schema and compared the cluster’s storage-only state with a dual-write exporter example

  • Ran per-user LogQL queries through the gateway route and distinguished token metrics from request-count metrics

Key takeaways:

  • Per-user usage records flow by default when usageLogging: true — no per-user opt-in is required

  • The external-metering knob is DSCInitialization spec.monitoring.usageLogs.exporters: dual-write keeps local storage, forward-only omits it, cluster_name/cluster_id attribute records to a fleet

  • tokens_total (usage-log pipeline, dashboards 4/5) is the per-user token consumption metric; Limitador metrics (dashboard 3) count requests, not tokens
