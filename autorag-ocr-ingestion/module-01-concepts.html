Module 01: How OCR-based document ingestion works

In this module you will learn how AutoRAG ingests scanned documents — PDFs whose pages are plain raster images with no embedded text layer — into a vector index, and where that OCR ingestion step sits inside an AutoRAG optimization pipeline. The concept sections require no cluster access; the closing exercise verifies the OCR-capable pipelines on the workshop cluster.

Learning objectives:

  • Explain why scanned PDFs need OCR and how AutoRAG detects and extracts their text

  • Describe the AutoRAG document flow: discovery, text extraction (Docling
    RapidOCR), chunking, vectorization, and optimization

  • Verify the managed AutoRAG pipelines that carry this flow on a RHOAI 3.6 cluster

Provenance. This workshop covers feature RHAISTRAT-1860, AutoRAG Support for OCR-Based Document Ingestion, listed as GA in RHOAI 3.6. The enterprise documentation was not reachable from the lab environment while authoring, so the narrative is grounded in two verifiable sources instead:

  • The upstream OpenDataHub sources: github.com/opendatahub-io/odh-dashboard (packages/autorag README and docs/overview.md) and github.com/opendatahub-io/pipelines-components (text_extraction component documentation).

  • The live cluster: the rhods-operator 3.6.0 CSV, the compiled managed pipelines served by the workshop’s DataSciencePipelinesApplication, and the deployed aocr- demo stack.

Quoted strings in this module were read from one of those sources; where a statement could not be grounded, the text says so.

The problem: documents without a text layer

A scanned PDF is a picture of a page. There are no font objects and no text operators in the file, so text extraction tools return nothing:

pdftotext ESB-2026-014-hydraulic-press.pdf - | tr -d '[:space:]' | wc -c
pdffonts ESB-2026-014-hydraulic-press.pdf
pdfimages -list ESB-2026-014-hydraulic-press.pdf

The workshop corpus produces exactly this shape:

0            <- pdftotext: zero characters of text
             <- pdffonts: no embedded fonts
1 image, 1700x2200, 8-bit gray, 200 dpi   <- pdfimages -list

Verify

Zero characters extracted and zero fonts listed means there is no text layer for the file — the only machine-readable content is the single raster image. That is exactly the shape AutoRAG’s OCR path exists for; run the same check on your own corpus to know whether you need it.

Traditional keyword search and naive text extraction are blind to such documents. Optical character recognition (OCR) is the only path to their content — and until recently, AutoRAG could not take that path.

Each page above looks like a legible bulletin, but to software it is a 200 dpi grayscale JPEG wrapped in a PDF container — image-only, no text layer.

Where OCR sits in an AutoRAG pipeline

AutoRAG is the automated RAG optimization feature of RHOAI: it runs experiments over your documents and a test dataset, explores retrieval and generation design choices with the ai4rag engine on Kubeflow Pipelines, ranks the resulting RAG patterns on a leaderboard, and produces deployable RAG pattern artifacts. OCR-based ingestion is what lets a scanned corpus — like the service bulletins in this workshop — participate in that optimization at all.

The flow inside the AutoRAG pipelines is:

  1. Document discovery — documents are discovered in the S3-compatible object storage location you select in the wizard.

  2. Text extraction — the text_extraction component processes every eligible file. In the upstream component documentation (verified verbatim in the compiled pipeline on this cluster):

    "OCR is enabled when the selected corpus contains a PDF or image. For a PDF page with an embedded text layer, Docling extracts that text directly. For a scanned PDF page or an image without embedded text, Docling uses RapidOCR to recognize the text."

    + The extraction result is a DoclingDocument JSON representation of the page — layout, text, and tables — regardless of whether the text came from an embedded layer or from OCR.

  3. Chunking — extracted documents are split into chunks ready for retrieval. The preset defines the search space, as read from the compiled pipeline on this cluster: the Faster preset explores recursive chunking at 128/256/512 tokens; Better quality explores 512/1024 (both with overlap variants).

  4. Vectorization — chunks are embedded with the embedding models registered on your OGX instance and indexed into a remote vector database — Milvus, pgvector (PostgreSQL), or Neo4j. Inline vector databases are not supported.

  5. Optimization — the ai4rag engine explores RAG configurations (chunking, embedding, retrieval, generation) against your evaluation dataset and optimization metric, and emits a leaderboard, pattern artifacts, and notebooks.

On the cluster, the two managed pipelines that implement this flow are visible through the Kubeflow Pipelines API of the workshop’s pipeline server. Their official descriptions, as served by the workshop DSPA:

documents-rag-optimization-pipeline
  "AutoRAG pipeline for building high-quality RAG applications from your
   documents with minimal configuration. Powered by ai4rag, it explores and
   optimizes retrieval and generation design choices against your quality
   goals. Delivers ranked, production-ready patterns, deployment-ready
   settings, and a leaderboard of the best configurations."

documents-indexing-pipeline
  "AutoRAG pipeline for building a production vector index from your
   documents. Powered by ai4rag, it discovers documents, extracts text, and
   indexes chunks into a vector database using settings from an optimized RAG
   pattern. Delivers a named collection, indexing artifacts, and component
   status for Dashboard deploy."

Both are tagged managed: true, rhoai-version: 3.6.0 — you will verify this in the exercise below.

Audio is a sibling capability of the same extraction stage: audio files are transcribed by a Whisper modelcar during ingestion. This workshop focuses on scanned PDFs.

What GA in RHOAI 3.6 means here

  • The feature tracker lists RHAISTRAT-1860 — AutoRAG Support for OCR-Based Document Ingestion — with maturity GA and version_introduced: 3.6.

  • The upstream packages/autorag README states: "Release status: AutoRAG is targeted for GA promotion in RHOAI 3.6."

  • On the workshop cluster, the rhods-operator 3.6.0 CSV carries RELATED_IMAGE_ODH_AUTORAG_IMAGE, and the executor image of the compiled pipeline’s text-extraction component resolves to that same image — the chain CSV → pipeline image → OCR component is closed on-cluster.

For contrast: in the RHOAI 3.5 Technology Preview, the documented limits said that images embedded in documents were not processed and that OCR was not available for PDF documents. The 3.6 text_extraction stage is what removes that limitation for scanned pages and images.

Honest-state caveats, kept visible: the upstream text_extraction component is still marked alpha in the upstream component repository, and upstream notes that dashboard confirmation of Gen AI Studio reaching GA in 3.6 remains tracked separately (RHAI-982). The enterprise documentation chapter and release-note wording for this feature could not be read while authoring this workshop — the docs.gaps are recorded in the workshop overview.

Exercise: Verify the OCR-capable pipelines on your cluster

You need oc access to the workshop cluster with the autorag-ocr-demo project available. If you have not connected yet, see Getting Connected.

List the managed pipelines compiled by the workshop pipeline server:

oc exec -n autorag-ocr-demo deploy/ds-pipeline-aocr-dspa -c ds-pipeline-api-server -- \
  curl -sk 'https://localhost:8888/apis/v2beta1/pipelines?pageSize=50' \
  | python3 -c 'import json,sys
for p in json.load(sys.stdin)["pipelines"]:
    print(p["display_name"], "|", p.get("tags",{}).get("rhoai-version","-"))'

Verify

The output lists the two AutoRAG document pipelines tagged 3.6.0:

autogluon-timeseries-training-pipeline | 3.6.0
autogluon-tabular-training-pipeline | 3.6.0
documents-rag-optimization-pipeline | 3.6.0
documents-indexing-pipeline | 3.6.0

documents-rag-optimization-pipeline and documents-indexing-pipeline are the OCR ingestion flow you just read about. If the list is empty, the DSPA’s spec.apiServer.managedPipelines field is not set — see Module 02 to deploy the stack correctly.

Module summary

What you accomplished:

  • Read the OCR ingestion flow: discovery → text extraction (Docling text layer or RapidOCR) → DoclingDocument JSON → chunking → vectorization → optimization

  • Saw where GA in RHOAI 3.6 is grounded for RHAISTRAT-1860, and what changed versus the 3.5 Technology Preview limits

  • Verified the managed 3.6.0 pipelines on the workshop cluster

Key takeaways:

  • A scanned PDF has no text layer — pdftotext returns nothing — and the AutoRAG text_extraction stage routes such pages through RapidOCR

  • OCR ingestion is not a separate wizard option: it activates automatically when the selected corpus contains a PDF or image

  • The flow runs inside the managed AutoRAG pipelines; a DSPA with managedPipelines enabled is the cluster-side prerequisite
