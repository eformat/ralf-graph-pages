Module 02: Per-user usage dashboards and CSV showback export

In this module you will enable per-user metrics collection, work through the MaaS observability dashboard end to end in the console, and export usage data as CSV for cost attribution and showback reporting to finance teams.

Learning objectives:

  • Enable MaaS usage logging and the usage metrics dashboard with the maasconfig Config

  • Navigate the MaaS observability dashboard: filters, time ranges, and the Token Consumption by User table

  • Export usage data as CSV and interpret its columns

  • Locate the underlying Prometheus metrics and the Loki-based log pipeline behind the dashboard

The MaaS observability dashboard is a Technology Preview feature. APIs and manifests shown here may change between releases.

Exercise 1: Enable usage logging and the usage metrics dashboard

The usage-logs pipeline and the usage metrics dashboard are both controlled by the cluster-scoped maasconfig Config default. Module 01 flipped these switches; this exercise re-checks them from the CLI and confirms the tenant side is reconciled before you walk the dashboard.

Enabling usageLogging writes one structured usage-log entry per MaaS gateway request into the Loki-based pipeline, and per-user attribution stores the authenticated user ID (user_id) on those logs. For a workshop cluster with a handful of users this is fine; on a production cluster, weigh the storage cost and the privacy implications of user-level attribution first.

  1. Confirm the maasconfig Config has both usage switches on (the Config is cluster-scoped, so the command carries no -n namespace flag):

    oc patch configs.maas.opendatahub.io default \
  --type merge \
  -p '{
    "spec": {
      "usageLogging": true,
      "usageMetricsDashboard": true
    }
  }'

    The usageLogging: true switch routes the gateway usage logs into the usage-logs pipeline, and usageMetricsDashboard: true deploys the Perses usage dashboard that Exercise 2 walks through. The patch is idempotent — if Module 01 already enabled the switches, it reports back with no change.

  2. Verify that both switches report true:

    oc get configs.maas.opendatahub.io default \
  -o jsonpath='{.spec.usageLogging}{" "}{.spec.usageMetricsDashboard}'

    Expected output:

    true true

  3. Verify that the per-tenant MaasTenantConfig resource is reconciled:

    oc get maastenantconfigs.maas.opendatahub.io default-tenant -n models-as-a-service

    Expected output shows the tenant config in a ready state:

    NAME             READY   REASON       AGE
default-tenant   True    Reconciled   5d18h

    Per-user attribution rides on the usage-log entries: when the tenant config’s spec.telemetry.logs.captureUser is true, each usage log carries the authenticated user ID (user_id) — the value that populates the User column of the usage views. captureUser defaults to false for privacy reasons; enable it deliberately on the tenant config if your showback needs per-user rows.

  4. Generate some MaaS traffic if your cluster is idle — send a few inference requests through the MaaS gateway with any API key you created in the MaaS workshop, so the usage metrics have data to report.

  5. Verify that the usage-metrics pipeline is reachable. In the OpenShift console, navigate to Observe → Metrics and run:

    curl -sSk -H "Authorization: Bearer $(oc whoami -t)" \
  "https://$(oc get route -n openshift-monitoring prometheus-k8s -o jsonpath='{.spec.host}')/api/v1/query?query=authorized_hits_total" \
  | python3 -m json.tool | head -30

    The command succeeds against the usage-metrics pipeline; the result is empty until MaaS model traffic flows. Once traffic is present, the metric is labeled with limitador_namespace — the subscription namespace that made the requests.

Verify

  • The maasconfig Config reports usageLogging: true and usageMetricsDashboard: true.

  • The MaasTenantConfig resource shows READY: True, REASON: Reconciled.

  • authorized_hits_total appears in Observe → Metrics after MaaS traffic.

With usage logging enabled and the usage metrics deployed, the console dashboard can now render MaaS usage — the next exercise walks it end to end.

Exercise 2: View the MaaS observability dashboard

The observability dashboard is embedded in the OpenShift AI console using Perses and queries its metrics from Prometheus. Access is restricted to cluster administrators. It is designed for showback reporting, not as a billing-grade metering system — for production chargeback workflows that require precise billing data, access the Limitador metrics endpoint directly rather than using Prometheus or the dashboard CSV export.

The Usage (legacy) tab queries Prometheus — the Limitador and Authorino metrics enabled in Exercise 1 — so it renders independently of the LokiStack. The Loki-backed Usage and My Usage tabs, and the usage-log pipeline behind them, require a Running LokiStack.

  1. In the OpenShift AI dashboard, click Observe & monitor → Metrics in the left navigation menu. The RHOAI 3.6 documentation names the menu item Dashboard; on the current build the same observability dashboard page (route /observe-and-monitor/dashboard, titled Observability metrics) is listed as Metrics.

    The page presents the Perses dashboards as a single row of tabs — Cluster, Models, LLM Traffic, LLM Utilization, Usage (legacy), LLM Performance, Usage, and My Usage — rather than the three-tab Cluster/Models/Usage layout the documentation describes.

  2. Click the Usage (legacy) tab (the documentation’s Usage tab) to view Models-as-a-Service usage metrics.

  3. Optional: To change the time range, select a value from the Time period dropdown. Options range from the last 5 minutes to the last 14 days, and you can also specify a custom date range.

  4. Optional: Filter the metrics by user, subscription, or model by selecting values from the User, Subscription, or Model dropdowns. Select All in any dropdown to view metrics for all items in that category.

  5. Review the Overview section, which displays summary metrics:

    Metric Description

    Total Tokens

    The total number of tokens consumed across all requests during the selected time period, including both input tokens (from user prompts) and output tokens (from model responses).

    Total Requests

    The total number of API requests made to MaaS models during the selected time period. Each API call to a model endpoint counts as one request.

    Total Errors

    The total number of failed requests during the selected time period, including model errors, timeout errors, and other server-side issues.

    Success Rate

    The percentage of successful inference requests out of all requests. Calculated from vLLM success and latency counters; rate-limited requests (HTTP 429) are excluded.

    Active Users

    The number of unique users who made at least one request during the selected time period, identified by username from API key ownership or OIDC authentication.

  6. Review the Token Consumption by User table, which shows detailed per-user usage data:

    Column Description

    User

    The username of the user who made the requests — the API key owner, or the user’s OIDC identity for OIDC-authenticated requests.

    Subscription

    The subscription used for the requests. If a user belongs to multiple subscriptions, separate rows appear for each.

    Model

    The model accessed, in the format <endpoint-name>/<model-id> for MaaS models.

    Tokens

    Total tokens consumed by this user for this subscription and model combination. Click the column header to sort by token consumption.

    Requests

    The number of API requests made by this user for this subscription and model combination.

    Rate Limited

    The number of requests rejected due to rate limiting (HTTP 429). Rate-limited requests count toward the request total without consuming tokens.

  7. Optional: Sort by column headers and use the pagination controls at the bottom of the table to navigate multiple pages of results or adjust rows per page.

  8. Optional: Compare the dashboard against the raw Prometheus metrics. In Observe → Metrics, the dashboard queries these metrics collected from the Kuadrant and MaaS components:

    Prometheus metric What it measures

    authorized_hits_total

    Total tokens consumed, labeled by subscription, model, and limitador_namespace. Collected from Limitador; the actual token usage for successful requests.

    authorized_calls_total

    Total API requests made to models, labeled by subscription and limitador_namespace. Counts all successful requests that passed rate limiting and authentication.

    limited_calls_total

    Requests rejected due to rate limiting (HTTP 429), labeled by limitador_namespace. Indicates when users exceed their subscription token limits.

    istio_request_duration_milliseconds_bucket

    Request latency at the API gateway, tagged with the subscription dimension.

    auth_server_authconfig_duration_seconds

    Time spent in Authorino authentication and authorization, labeled by authorization policy.
    The model label displays only on the authorized_hits_total metric due to Kuadrant wasm-shim limitations.

Verify

  • The Overview section shows non-zero values for users with recent activity.

  • The Token Consumption by User table lists users with token consumption in the selected time period.

  • Changing the time period updates the metrics to reflect the new range.

The dashboard answers "how much" on screen — the next exercise turns the same data into a file your finance team can consume.

Exercise 3: Export usage data as CSV for showback

You can export MaaS usage data in CSV format for cost attribution and showback reporting to finance teams. The export requires the Cluster Observability Operator to be installed and configured on the cluster (checked in Module 01).

  1. In the OpenShift AI dashboard, click Observe & monitor → Metrics (the observability dashboard page; the documentation calls the menu item Dashboard).

  2. Click the Usage (legacy) tab (the documentation’s Usage tab).

  3. Optional: Configure filters to export specific usage data:

    • Select a time period from the Time period dropdown to export metrics for a specific timeframe.

    • Select filters for User, Subscription, or Model to export metrics for specific resources.

  4. Hover over the Token Consumption by User table.

  5. Click Export as CSV to download the usage data.

    The system generates a CSV file containing the filtered usage data.

  6. Save the CSV file to your local system.

The exported CSV file contains subscription-level usage data for the selected time period and filters. This data is suitable for showback reporting but might not be billing-grade accurate. For production chargeback workflows, configure external metering and billing tools to consume this data.

Verify

The CSV file downloads to your local system and contains usage data matching your selected filters and time period — one row per user, subscription, and model combination with token and request totals.

Background: the Loki-based log pipeline and user-scoped dashboards

The metrics-based dashboard you used above is one half of MaaS showback. In RHOAI 3.6, MaaS also includes a Loki-based structured log pipeline for showback data in addition to the metrics-based dashboard. The Loki-based pipeline provides 30-day retention on object storage, which better supports monthly billing cycles than short-lived in-cluster metric retention.

This enhancement also introduces user-scoped, read-only dashboards with data isolation: users — including administrators using the scoped view — can see only their own MaaS usage data, while administrators continue to use the existing platform-wide dashboard (the one you exercised above) for broader usage monitoring.

The underlying structured logs already carry the dimensions needed for this scoping: the maas-api structured JSON logs include tenant_name, tenant_namespace, gateway_name, and gateway_namespace fields in each log entry, and when OpenTelemetry tracing is enabled (set the OTEL_EXPORTER_OTLP_ENDPOINT environment variable on the maas-api deployment), traces include span attributes for tenant.name, tenant.namespace, gateway.name, and gateway.namespace.

The RHOAI 3.6 documentation describes the metrics-based dashboard workflow in detail (Govern LLM access with Models-as-a-Service, "Monitor Models-as-a-Service usage by using the observability dashboard"), but does not yet publish step-by-step configuration commands for the Loki-based log pipeline or for enabling the user-scoped dashboards — those are described in the 3.6 release notes as Technology Preview enhancements. The maasconfig switches you enabled in Exercise 1 are the Technology Preview configuration surface; consult the release notes and your Red Hat contact for the current state.

Module summary

What you accomplished:

  • Enabled usage logging and the usage metrics dashboard via the maasconfig Config and confirmed the MaasTenantConfig resource is reconciled

  • Navigated the MaaS observability dashboard: filters, time ranges, overview metrics, and the Token Consumption by User table

  • Exported usage data as CSV for showback reporting and reviewed the Loki-based log pipeline behind it

Key takeaways:

  • The dashboard is showback-grade, not billing-grade — production chargeback needs the Limitador metrics endpoint or external metering

  • The usage switches live on the cluster-scoped maasconfig Config; per-user user_id attribution on the usage logs is governed by the tenant config’s spec.telemetry.logs.captureUser (default false)

  • The Loki-based pipeline adds 30-day object-storage retention and user-scoped read-only dashboards for monthly billing cycles
