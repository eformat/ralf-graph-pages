Module 01: Get started with AutoRAG in French

In this module you will learn what changes when AutoRAG optimizes RAG configurations for a non-English corpus, and you will stage the demo environment the wizard consumes: a pgvector vector database, a tool-calling foundation model plus the multilingual bge-m3 embedding model on CPU model servers, an OGX instance wiring them together, a MaaS facade that exposes both models to the wizard through one OpenAI-compatible endpoint, the project connections the wizard lists, and the French corpus with its evaluation data set.

Learning objectives:

  • Explain what AutoRAG needs from your models, corpus, and evaluation data when the corpus is not English

  • Stage the demo environment from this workshop’s additive deploy/ manifests

  • Upload a French regulatory corpus and a French evaluation data set to S3-compatible storage

  • Verify every layer of the stack before creating an optimization run

This feature is Generally Available in Red Hat OpenShift AI 3.6. Multi-language support for AutoRAG — non-English corpora, multilingual embedding models, and automatic detection of the evaluation questions' language — is GA in 3.6.

Exercise 1: What changes for a non-English corpus

AutoRAG tests combinations of chunking, embedding, retrieval, and generation settings and ranks the resulting RAG patterns on a leaderboard. Every layer of that loop must speak your corpus’s language:

  • Embedding model. The default English-only embedding models produce weak vectors for French text. This workshop deploys BAAI/bge-m3, the multilingual embedding model named in the AutoRAG documentation: 100+ languages, dense and sparse retrieval, ~1.1 GB of memory (fp16). Mind the dimensions — bge-m3 produces 1024-dim vectors, not the 768-dim of the English-only granite-embedding-english-r2 the standard workshop deploys. The OGX defaultEmbeddingModel setting must declare embeddingDimensions: 1024 or vector-store writes fail.

  • Evaluation data set. The questions and expected answers must be written in your target language. AutoRAG detects the language of the evaluation questions automatically; with French questions the LLM-as-judge metrics grade French answers against French ground truth.

  • No language selector. The 3.6 wizard has no evaluation-language setting — verified exhaustively against the live wizard (page text, models dialog, metric dropdown, both presets) and its JavaScript bundles. Language handling is implicit: auto-detection for the judge, your embedding model for retrieval, your data for the ground truth. Do not search the UI for a language dropdown — spend that effort on the models and data instead.

  • Generation model. The foundation model must follow instructions in the target language. This workshop deploys llama-3.2-3b-instruct, a multilingual instruction-tuned model, with tool calling enabled.

Budget one target language per run on a CPU-only cluster: every foundation and embedding model combination the wizard explores runs inference over your whole corpus and evaluation set. This workshop deliberately picks French only — a single, well-scoped language keeps CPU runtimes tractable.

Verify

You can name the multilingual deltas before you touch the cluster: a multilingual embedding model with matching embeddingDimensions, an evaluation data set in the target language, and automatic question-language detection in place of any wizard language setting.

Exercise 2: Stage the vector database

AutoRAG requires a remote vector database — inline vector databases are not supported. The demo stack uses PostgreSQL 16 with the pgvector extension. From the root of the workshop assets repository, apply the pgvector manifest:

cd features/feature-store-automl-autorag/autorag-multilingual/deploy
oc apply -f pgvector.yaml

Expected output:

secret/aml-pgvector-secret created
configmap/aml-pgvector-init created
statefulset.apps/aml-pgvector created
service/aml-pgvector created
persistentvolumeclaim/aml-pgvector created

The PVC mount root contains lost+found, and PostgreSQL’s initdb refuses to initialize into a non-empty directory. The manifest therefore sets PGDATA=/var/lib/postgresql/data/pgdata — a subdirectory of the mounted volume. Removing this setting crash-loops the pod.

Verify

Wait for the statefulset, then list the databases:

oc wait sts/aml-pgvector -n autorag-ml-demo --for=condition=Ready --timeout=300s
oc exec -n autorag-ml-demo sts/aml-pgvector -- psql -U ogx -d ogx -c '\l'

Expected output (abridged — real capture):

                              List of databases
   Name    |  Owner   | Encoding |   Collate   |    Ctype    | Access privileges
-----------+----------+----------+-------------+-------------+-------------------
 ogx       | ogx      | UTF8     | en_US.UTF-8 | en_US.UTF-8 |
 ogx_metadata | ogx      | UTF8     | en_US.UTF-8 | en_US.UTF-8 |

Both databases matter: ogx holds the vector store, ogx_metadata is the OGXServer metadata store created by the init ConfigMap.

Exercise 3: Deploy the models

AutoRAG discovers foundation and embedding models from your OGX instance, and foundation models deployed with vLLM must have tool calling enabled. Deploy the CPU serving runtime first, then the two models, then the connection services:

./setup-runtime.sh autorag-ml-demo
oc apply -f models-toolcalling.yaml
oc apply -f embedding-model-bge-m3.yaml
oc apply -f model-conn-services.yaml

Expected output (abridged):

>> instantiating vllm-cpu-x86-runtime template into project autorag-ml-demo
servingruntime.serving.kserve.io/vllm-cpu-x86-runtime created
inferenceservice.serving.kserve.io/aml-llama32-3b created
inferenceservice.serving.kserve.io/aml-bge-m3 created
service/aml-llama32-3b-conn created
service/aml-bge-m3-conn created

Three teaching points hide in these manifests:

  • Tool calling. models-toolcalling.yaml adds --enable-auto-tool-choice --tool-call-parser=llama3_json (Llama 3.x family) to the model server arguments. Without them the AutoRAG run fails when the pipeline calls model tools.

  • CPU memory. Despite its name, --gpu-memory-utilization controls the fraction of the container memory limit reserved by the vLLM CPU backend. The manifests set it explicitly (0.7 for the LLM, 0.25 for the embedder) — with a small limit and the default 0.92, startup fails with "Available memory on node 0 …​ is less than desired CPU memory utilization".

  • Embedder sizing. The bge-m3 settings in embedding-model-bge-m3.yaml were earned the hard way on this CPU cluster, and they are the sizing recipe to copy: at a 4Gi limit with --gpu-memory-utilization=0.5 the engine crash-looped at startup (ValueError: Available memory on node 0 (1.41/4.0 GiB) is less than desired CPU memory utilization (0.5, 2.0 GiB)); raising only the limit to 6Gi OOMKilled the container three times during weight load (fp32 load spike); 8Gi limit with 0.25 utilization (2 GiB reserved) came up Ready and stayed there.

  • Embedder context window. Keep --max-model-len at the 4096 the manifest ships: the optimization pipeline validates the embedding model’s served context and requires context_length >= 700 (it reads vLLM’s max_model_len minus a small offset). A 512 setting reports 507 and the run fails at search-space preparation with ValueError: Embedding model aml-bge-m3 supports 'context_length' 507. Minimal required value is 700. — a model-serving config defect, not a wizard problem.

  • Connection services. KServe RawDeployment predictor services are headless (ClusterIP None), and podIP:80 is refused — the model servers listen on 8080. model-conn-services.yaml creates the two ClusterIP services (aml-llama32-3b-conn, aml-bge-m3-conn) that translate to pod port 8080; the OGX providers point at these names.

Verify

Wait for both InferenceServices to become Ready (the first modelcar pull plus CPU load takes several minutes):

oc wait inferenceservice/aml-llama32-3b -n autorag-ml-demo --for=condition=Ready --timeout=900s
oc wait inferenceservice/aml-bge-m3 -n autorag-ml-demo --for=condition=Ready --timeout=900s
oc get isvc -n autorag-ml-demo

Expected output:

NAME             URL                                        READY   UPDATED   UPDATING   AVAILABLE   DEGRADED
aml-bge-m3       http://aml-bge-m3.autorag-ml-demo.svc.cluster.local   True
aml-llama32-3b   http://aml-llama32-3b.autorag-ml-demo.svc.cluster.local   True

Deleting the pod bypasses the pull failure rather than fixing it — it relies on another node having already cached the digest. If every node reports manifest unknown, verify the ServingRuntime image digest and registry access instead of rescheduling.

If a predictor pod sits in ImagePullBackOff with manifest unknown for the vLLM CPU runtime digest, it is a node-level registry resolution issue rather than an authoring error — delete the pod so it reschedules onto a node that has the image cached.

Exercise 4: Install the OGX server

The OGXServer wires everything together: the two model endpoints as vLLM inference providers, pgvector as the vector I/O provider, and PostgreSQL as the metadata store. Apply the manifest (it also creates the labeled base ConfigMap and the postgres connection Secret the OGXServer references):

oc apply -f ogxserver.yaml

Expected output:

secret/aml-ogx-postgres-conn created
configmap/aml-ogx-base-config created
ogxserver.ogx.io/aml-ogx created

Three OGX configuration gotchas are baked into this manifest, and all three silently break the AutoRAG wizard when missed:

  • The base ConfigMap and the postgres Secret must carry the ogx.io/watch: "true" label — the operator only watches labeled resources and otherwise reports "failed to find referenced base ConfigMap".

  • The pgvector provider must be declared under providers.vector_io — a top-level vector_io: key is ignored by the runtime, and the wizard’s Vector I/O provider dropdown renders empty.

  • The pgvector persistence must be the flat {backend: kv_default, namespace: pgvector} shape — the nested persistence.reference.* shape fails OGX startup with a PGVectorVectorIOConfig validation error.

Verify

Check the server phase, then confirm the providers the wizard will discover:

oc get ogxserver aml-ogx -n autorag-ml-demo -o jsonpath='{.status.phase}{"\n"}'
oc get svc aml-ogx-service -n autorag-ml-demo

Expected output:

Ready
NAME               TYPE        CLUSTER-IP      PORT(S)
aml-ogx-service    ClusterIP   172.30.x.x      8321/TCP,9464/TCP
oc port-forward svc/aml-ogx-service 18321:8321 -n autorag-ml-demo

In a second terminal:

curl -s http://127.0.0.1:18321/v1/providers | python3 -m json.tool

Expected output (abridged — real capture):

Exercise 5: Register the project connections and routes

The wizard consumes two project connections: a MaaS connection in step 1 (model discovery) and an S3 connection in step 2 (knowledge documents). The MaaS connection is where multilingual model serving meets the wizard, and it needs one component first.

Stage the MaaS facade

The wizard’s step-1 MaaS connection consumes one OpenAI-compatible base URL that serves both model types — the foundation model (chat + responses) and the embedding model (/v1/models must list both; the dashboard probes readiness per model). This OGX build implements only the [inference, models, vector_io] APIs: pointed at OGX, the wizard renders every model ready:false with disabled checkboxes. The raw vLLM model servers serve everything the wizard and the optimization pipeline call, but they are two separate endpoints. maas-facade.yaml bridges the gap — a small stdlib reverse proxy that merges the two model servers behind one endpoint (/v1/models merged listing; chat/completions/responses proxied to the LLM; embeddings proxied to bge-m3):

oc apply -f maas-facade.yaml

Expected output:

configmap/aml-maas-facade created
deployment.apps/aml-maas-facade created
service/aml-maas-facade created
route.route.openshift.io/aml-maas-facade-tls created

The manifest also exposes the facade through the edge-TLS route aml-maas-facade-tls — the wizard’s Add MaaS connection dialog accepts only HTTPS URLs (or localhost HTTP), so in-cluster plain-HTTP service URLs are rejected client-side.

Register the MaaS connection

The wizard’s step-1 dropdown lists the project’s MaaS connections: Secrets with the opendatahub.io/connection-type: maas annotation and MAAS_BASE_URL / MAAS_API_KEY data keys:

oc apply -f maas-connection.yaml

Expected output:

secret/aml-maas-models created

Two Base URL rules hide in aml-maas-models (both learned from the live wizard):

  • The value points at the facade route host and must not end in /v1 — the dashboard backend appends /v1 itself. A /v1-suffixed MAAS_BASE_URL makes it call <host>/v1/v1/models, which returns 404 and the wizard shows "Failed to load MaaS models".

  • Only HTTPS passes the dialog’s client-side validation — hence the edge-TLS route rather than the in-cluster service URL.

Register the S3 connection (and the optional OGX route)

oc apply -f data/s3-connection.yaml
oc apply -f ogx-connection.yaml
oc apply -f ogx-connection-wizard-keys.yaml
oc apply -f ogx-route.yaml

Expected output:

secret/aml-s3-connection created
secret/aml-ogx-connection created
secret/aml-ogx-connection configured
route.route.openshift.io/aml-ogx-tls created

The S3 connection (annotation opendatahub.io/connection-type: s3) is the step-2 knowledge source. The OGX connection files register an OGX-typed Secret for direct OGX API clients — honest note: on this 3.6 build the AutoRAG wizard does not consume OGX-typed Secrets (its step-1 dropdown listed only the MaaS connection while this Secret was present in the project); the files are kept for OGX clients and parity with the parent English workshop. ogx-route.yaml exposes the OGX server through the edge-TLS route aml-ogx-tls for those clients.

Verify

oc get secret aml-maas-models -n autorag-ml-demo \
  -o jsonpath='{.metadata.annotations.opendatahub\.io/connection-type}{"\n"}'
oc get secret aml-maas-models -n autorag-ml-demo \
  -o jsonpath='{.data.MAAS_BASE_URL}' | base64 -d
oc get secret aml-s3-connection -n autorag-ml-demo \
  -o jsonpath='{.data.AWS_S3_BUCKET}{"\n"}' | base64 -d
oc get secret aml-ogx-connection -n autorag-ml-demo \
  -o jsonpath='{.metadata.annotations.opendatahub\.io/connection-type}{"\n"}'

Expected output:

maas
https://aml-maas-facade-tls-autorag-ml-demo.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com
autorag-ml-corpus

The MaaS base URL ends at the route host — no /v1 suffix. Now check the exact endpoint the wizard’s model discovery will call:

curl -sk "https://$(oc get route aml-maas-facade-tls -n autorag-ml-demo \
  -o jsonpath='{.spec.host}')/v1/models" | python3 -m json.tool

Expected output (abridged — real capture):

{
    "object": "list",
    "data": [
        { "id": "aml-llama32-3b", "object": "model", "owned_by": "vllm", "ready": true },
        { "id": "aml-bge-m3", "object": "model", "owned_by": "vllm", "ready": true }

The S3 connection manifest also declares AWS_DEFAULT_REGION — without that key the wizard’s storage filter fails with Required key "AWS_DEFAULT_REGION" is not set and Create run stays disabled.

Exercise 6: Enable the pipeline server

AutoRAG launches the optimization run as a Kubeflow pipeline in the project’s pipeline server, so the project needs a DataSciencePipelinesApplication with the AutoML and AutoRAG managed pipelines enabled (spec.apiServer. managedPipelines: {}):

oc apply -f dspa.yaml

Expected output:

datasciencepipelinesapplication.datasciencepipelinesapplications.opendatahub.io/aml-dspa created

The DSPA stores its pipeline artifacts in MinIO (bucket aml-pipelines, credentials in the aml-minio-creds secret) — stage that secret and bucket before the first run. The French corpus bucket autorag-ml-corpus from the next exercise is a different, wizard-facing bucket.

Verify

oc wait dspa/aml-dspa -n autorag-ml-demo --for=condition=Ready --timeout=600s
oc get dspa -n autorag-ml-demo

Expected output:

NAME       READY   AGE
aml-dspa   True    5m

Exercise 7: Upload the French corpus and evaluation data set

The Knowledge documents live in the autorag-ml-corpus bucket under the fed-aura-fr/ folder prefix (multiple documents belong in a single folder):

  • banque-aura-politique-reglementaire.md — a French regulatory policy compendium for the fictive Banque Aura Fédérale S.A.: six parts covering DORA, MiFID II product governance, CSRD ESG data collection, third-party ICT providers, risk appetite, and AML/KYC, with ACPR/AMF French-regulatory detail and threshold tables.

  • eval-dataset-fr.json — ten French questions in the wizard format, each with expected answers verbatim-derivable from the corpus.

The upload script reads MinIO credentials at runtime (never printed), port-forwards to the object storage service, uploads both files, lists the prefix, and round-trip-verifies each object byte-for-byte:

cd data
./upload-data-fr.sh

Expected output (abridged — real capture):

=== upload to s3://autorag-ml-corpus/fed-aura-fr/ ===
uploading fed-aura-fr/banque-aura-politique-reglementaire.md  (82522 bytes local)
uploading fed-aura-fr/eval-dataset-fr.json  (8132 bytes local)
=== listing s3://autorag-ml-corpus/fed-aura-fr/ ===
fed-aura-fr/banque-aura-politique-reglementaire.md
fed-aura-fr/eval-dataset-fr.json
=== round-trip verification (GET each object, compare byte length) ===
  OK       fed-aura-fr/banque-aura-politique-reglementaire.md  HTTP 200  remote 82,522 B / local 82,522 B
  OK       fed-aura-fr/eval-dataset-fr.json  HTTP 200  remote 8,132 B / local 8,132 B
fed-aura-fr upload complete: FRENCH corpus + eval dataset in s3://autorag-ml-corpus/fed-aura-fr/

Verify

Validate the evaluation data set is well-formed JSON and that every document key matches the uploaded corpus file name exactly:

python3 -m json.tool data/eval-dataset-fr.json | head -12
python3 -c "import json;print({q['correct_answer_document_keys'][0] for q in json.load(open('data/eval-dataset-fr.json'))})"

Expected output:

[
    {
        "question": "Quelles sont les clauses contractuelles obligatoires exigées par l'article 30 de DORA ...",
        "correct_answers": [...],
        "correct_answer_document_keys": ["banque-aura-politique-reglementaire.md"]
    },
    ...
]
{'banque-aura-politique-reglementaire.md'}

A json.decoder.JSONDecodeError means the file has a syntax error to fix, and any document key that does not match the uploaded file name exactly will not score.

The 3.6 evaluation-data schema is strict: each record must contain exactly the keys question, correct_answers, and correct_answer_document_keys. The parent English workshop’s dataset uses the older correct_answer_document_ids key — on this build that fails the run at the load-benchmark stage with TestDataLoaderError: Incorrect or incomplete keys in test data record at index 0. Each record must contain exactly: ['correct_answer_document_keys', 'correct_answers', 'question']. If you adapt the parent dataset, rename the key first.

With the environment staged and the French data in place, you are ready to create the optimization run that consumes it.

Module summary

What you accomplished:

  • Staged pgvector with the PGDATA subdirectory setting, a tool-calling foundation model, the multilingual bge-m3 embedding model, the OGX server wiring them together, and the MaaS facade exposing both models to the wizard

  • Registered the wizard-shaped MaaS and S3 connections, exposed the facade and OGX through edge-TLS routes, and enabled the project pipeline server

  • Uploaded the French corpus and the French evaluation data set and verified them end to end

Key takeaways:

  • Multilingual AutoRAG starts at the embedding layer: bge-m3 (1024-dim, 100+ languages) replaces the English-only default, and embeddingDimensions must match

  • The wizard is strict about shapes: ogx.io/watch labels, providers.vector_io, flat pgvector persistence, opendatahub.io/connection-type annotations (maas with MAAS_BASE_URL, s3), and AWS_DEFAULT_REGION each gate a dropdown or button in the UI

  • The evaluation data set is the language contract: French questions, French expected answers, and the exact correct_answer_document_keys document keys

Next steps:

Continue to Module 02 to create the French optimization run in the wizard and evaluate the leaderboard.
