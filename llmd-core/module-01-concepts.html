Module 01: Core Concepts

In this module you will understand what Distributed Inference with llm-d is, how its serving stack fits into Red Hat OpenShift AI, and which custom resources back it.

Learning objectives:

  • Explain how llm-d fits into the unified generative model serving entry point in RHOAI 3.6

  • Describe the four validated deployment topology patterns and when to use each

  • Inspect the LLMInferenceService, LLMInferenceServiceConfig, and Gateway API resources that back the feature in your cluster

Exercise 1: Where Distributed Inference with llm-d fits

Distributed Inference with llm-d deploys and serves large language models (LLMs) at scale on Red Hat OpenShift AI. It is built on the llm-d project and replaces the single-model serving platform’s one-pod-per-model KServe flow with a distributed inference stack: a Gateway API gateway routes requests through an inference scheduler (the endpoint picker) to vLLM workers that can run as single pods or as multi-node LeaderWorkerSets.

In RHOAI 3.6, all generative AI models deploy through a single Deploy model entry point. The deployment wizard guides you through five steps — Preconfigure deployment, Model details, Model deployment, Advanced settings, and Review:

  • In Model details you pick the Model type — Predictive model or Generative AI model — and tell the wizard where the model lives: S3 object storage, OCI compliant registry, URI, or NVIDIA NIM

  • In Model deployment you name the deployment and choose the Deployment method: LLM inference service, LLM inference service with llm-d, or Inference service. The llm-d method adds distributed serving with advanced routing techniques such as cache-aware routing and disaggregated prefill and decode

  • Selecting the llm-d deployment method surfaces the Accelerator configuration presets — under Manual selection you pick from the built-in, global-scoped LLMInferenceServiceConfig configurations that your administrator enabled

  • In Advanced settings you can require token authentication, attach gateways, and set model capabilities; Review summarizes the deployment before it is created

The wizard has no topology radio buttons: the serving pattern follows from the accelerator configuration and hardware you select. The shipped presets scope themselves to the workload topologies they support — single-node, multi-node data-parallel, and the prefill/decode disaggregate variants — through their opendatahub.io/supported-topologies annotations, and platform administrators control which configurations are available through LLMInferenceServiceConfig template management (see Module 03).

The four validated deployment topology patterns:

Pattern What it does Use when

Single-node

All model components on a single GPU or set of GPUs within one pod

The model fits in the GPUs of a single node; development, testing, and production for models up to about 30B parameters

Multi-node data-parallel

Replicates the complete model across many worker nodes

High request throughput for mid-size models (7B-70B); request-level parallelism

Single-node prefill/decode disaggregate

Separates prompt processing (prefill) from token generation (decode) on different GPUs within one node

Latency optimization for 30B+ models with at least 2 GPUs and RDMA-capable networking

Multi-node prefill/decode disaggregate

Distributes prefill and decode phases across many nodes

Largest models (70B+) requiring 8+ GPUs across nodes with InfiniBand or RoCE v2 networking

A fifth pattern, Wide expert parallelism (WideEP), distributes Mixture of Experts model experts across GPU nodes for very large MoE models such as DeepSeek-R1. It is a Developer Preview feature in RHOAI 3.6.

Each LLMInferenceService deployment creates a per-namespace inference stack consisting of:

  • An HTTPRoute for gateway traffic

  • An InferencePool and a scheduler deployment that reconciles it

  • A decode workload variant, deployed as a Deployment or a LeaderWorkerSet

  • For prefill/decode disaggregation, an additional prefill workload variant

  • ServiceMonitor resources for prefill and decode monitoring

The Gateway itself is shared across inference stacks (or omitted in gatewayless deployments). A namespace can contain only one inference stack.

  1. Locate the feature in the RHOAI dashboard: open Red Hat OpenShift AI and navigate to AI hub > Models > Deployments.

  2. Set the Project filter to your project and scan the Deployment resource column — llm-d deployments show Distributed inference with llm-d there.

  3. Click Deploy model and observe the Deployment method radio buttons in the Model deployment step: LLM inference service with llm-d appears alongside LLM inference service and Inference service. Do not deploy yet — you will complete the wizard in the next module.

Verify

You can name the four validated topology patterns, the model-size band each serves, and where llm-d deployments live in the RHOAI dashboard — AI hub > Models > Deployments, with Distributed inference with llm-d in the Deployment resource column.

Now that you know where the feature lives, inspect the custom resources and operators that back it in your cluster.

Exercise 2: Inspect the cluster

The feature is backed by custom resources from three API groups: LLMInferenceService and LLMInferenceServiceConfig from serving.kserve.io, and Gateway API resources (GatewayClass, Gateway, HTTPRoute) from gateway.networking.k8s.io. The llmisvc-controller-manager and kserve-controller-manager controllers, enabled through the kserve component of the DataScienceCluster CR, reconcile them.

  1. Confirm the KServe and LLMISVC controller managers are enabled in the DataScienceCluster resource:

oc get datasciencecluster default-dsc -o jsonpath='{.spec.components.kserve.managementState}'

The command returns Managed.

  1. Verify the controller pods are running. The controller managers run in the redhat-ods-applications namespace:

oc get pods -n redhat-ods-applications \
  -l 'app.kubernetes.io/name in (kserve-controller-manager, llmisvc-controller-manager)'

Expected output (plain ---- block):

NAME                                          READY   STATUS    RESTARTS   AGE
kserve-controller-manager-957445747-t7kmm     1/1     Running   48         31h
llmisvc-controller-manager-5d57579f75-fpppl   1/1     Running   64         3d17h

  1. Verify the inference Gateway exists. RHOAI expects a GatewayClass and a Gateway named openshift-ai-inference in the openshift-ingress namespace:

oc get gatewayclass openshift-ai-inference
oc get gateway openshift-ai-inference -n openshift-ingress -o wide

Wait until PROGRAMMED shows True for the Gateway.

  1. List any LLMInferenceService deployments already on the cluster:

oc get llminferenceservice -A

  1. List the LLMInferenceServiceConfig configurations that back the wizard’s Accelerator configuration list:

oc get llminferenceserviceconfigs -A

The redhat-ods-applications namespace ships 43 of them: 15 accelerator presets labeled opendatahub.io/config-type=accelerator — the only config-type value in RHOAI 3.6 — for vLLM serving on CPU, NVIDIA CUDA (single-node, multi-node, and prefill/decode variants), AMD ROCm, IBM Spyre, and Intel Gaudi hardware, plus scheduler and platform configurations. Each preset declares the workload topologies it supports through the opendatahub.io/supported-topologies annotation: workload-single-node, workload-multi-node-data-parallel, and their -pd prefill/decode variants.

Administrators view and enable the presets in the RHOAI dashboard under Settings > Model resources and operations > Model deployment settings > LLM accelerator configurations — Module 03 walks through that page.

Verify

The kserve component reports Managed, the controller pods are Running, and the openshift-ai-inference Gateway shows PROGRAMMED: True. If the Gateway is missing or not programmed, ask your facilitator to complete the cluster setup before continuing.

Module summary

What you accomplished:

  • Mapped the llm-d serving stack to RHOAI’s unified generative model serving entry point

  • Compared the four validated deployment topology patterns and their hardware requirements

  • Verified the KServe and LLMISVC controllers, the inference Gateway, and the serving CRDs

Key takeaways:

  • LLMInferenceService deploys a model; LLMInferenceServiceConfig accelerator presets define the serving configurations behind the wizard’s Accelerator configuration list

  • Every preset scopes itself to the workload topologies it supports through the opendatahub.io/supported-topologies annotation; disaggregated patterns additionally need RDMA-class hardware

  • A namespace holds one inference stack, and the Gateway is shared across stacks
