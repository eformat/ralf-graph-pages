Module 02: Hands-on Exercise

In this module you will work through the core Distributed Inference with llm-d workflow on RHOAI 3.6 using the workshop’s live deployment. You will locate llm-d model deployments in the dashboard’s AI hub > Models > Deployments view, read the underlying LLMInferenceService resources from the CLI with oc get llmisvc, and send live OpenAI-compatible chat completion requests to the Ready model cpu-demo-llm in the abc123-user1 project.

Learning objectives:

  • Locate llm-d model deployments in AI hub > Models > Deployments and read the deployment list and the expanded row panel

  • Inspect an LLMInferenceService from the CLI to obtain the model, template, and endpoint ground truth that the dashboard does not display for llm-d deployments

  • Send OpenAI-compatible chat completion and models-list requests to the live internal inference endpoint

Exercise 1: Explore model deployments in the dashboard

In RHOAI 3.6, deployed-model management lives in AI hub > Models > Deployments. The view lists every model deployment across your projects — both llm-d deployments and deployments that use a classic serving runtime — with a Deploy model button above the table.

In RHOAI 3.6 the LLM deployment topology selector is generally available (GA). The topology selector and the llm-d serving stack it drives are both fully supported with Red Hat production service-level agreements (SLAs) in RHOAI 3.6.
Prerequisites

  • You are logged in to the RHOAI dashboard as a workshop user

  • Distributed inference with llm-d is enabled on the cluster (see Module 03)

  • A model deployment exists in your project (the workshop pre-deploys cpu-demo-llm)

Procedure

  1. In the RHOAI dashboard, click AI hub in the left navigation, click Models, then click Deployments. The deployments page opens with the Internal models sub-tab active.

  2. Review the table columns: Model deployment name, Project, Deployment resource, Inference endpoints, Hardware profile, Capabilities, Last deployed, and Status.

  3. Find the cpu-demo-llm row. It shows Distributed inference with llm-d in the Deployment resource column — every deployment backed by an LLMInferenceService carries this label — an Internal endpoint button in the Inference endpoints column, and a Ready status.

  4. Click the chevron at the start of the cpu-demo-llm row to expand it. The panel shows:

    1. Model server replicas — 1

    2. Model server size — 100m CPUs, 2GiB Memory requested and 6 CPUs, 8GiB Memory limit

    3. Hardware profile — Unknown (this CPU deployment has no hardware profile; the table column shows No hardware profile)

    4. Users and Availability — who can discover the endpoint and where it is accessible

    5. Token authentication — Token name and Token secret fields, which stay empty until token authentication is enabled for the deployment

      llm-d deployments have no dedicated detail page in the dashboard. The expanded row panel is the detail view, and it does not display the model name or the serving runtime. Use oc get llmisvc from the CLI for that ground truth (Exercise 2). Deployments that use a classic serving runtime, such as a vLLM CPU ServingRuntime for KServe, do show the runtime name and a version chip in their row.

  5. Optional: click Deploy model to open the deployment wizard. The wizard walks through five steps — Preconfigure deployment (project), Model details (Model location: S3 object storage, OCI compliant registry, URI, or NVIDIA NIM; Model type: Predictive model or Generative AI model), Model deployment (Model deployment name, Deployment method, Hardware profile, Accelerator configuration, Replica count), Advanced settings, and Review. Selecting LLM inference service with llm-d as the Deployment method deploys the llm-d serving stack: distributed serving with advanced routing techniques such as cache-aware routing and disaggregated prefill and decode. You do not need to deploy a new model for this module — click Cancel to leave the wizard.

Verify

  1. The deployments page shows all eight table columns listed above.

  2. The cpu-demo-llm row shows Distributed inference with llm-d, an Internal endpoint button, and Ready status.

  3. The expanded row panel shows Model server replicas 1 and the Model server size requests and limits.

  4. The deployment wizard’s Model deployment step lists LLM inference service with llm-d as a Deployment method.

Exercise 2: Read the LLMInferenceService from the CLI

Every llm-d deployment is backed by an LLMInferenceService custom resource. Because the dashboard’s expanded row panel does not display the model name or serving runtime for llm-d deployments, the CLI is your ground truth for what is actually deployed.

Prerequisites

  • oc is logged in to the workshop cluster

  • You can view resources in the abc123-user1 project

Procedure

  1. List the LLMInferenceService resources in the workshop project:

oc get llmisvc -n abc123-user1

The project contains the Ready cpu-demo-llm deployment plus a second llm-d deployment that runs the full distributed topology. Both rows report READY=True: the distributed deployment serves through the complete llm-d control plane — its router, endpoint-picker scheduler, and inference pool are all Ready in front of its model replicas. This module uses cpu-demo-llm as the primary demo object and reads the distributed deployment with the same commands to contrast the two topologies.

  1. Read the model ground truth — the model location URI and the model name to use in inference requests:

oc get llmisvc cpu-demo-llm -n abc123-user1 \
  -o jsonpath='{.spec.model.uri}{"\n"}{.spec.model.name}{"\n"}'

The output shows the Hugging Face URI and name of the workshop model, HuggingFaceTB/SmolLM2-135M-Instruct. This is the value the dashboard hides for llm-d deployments, and it is what you must pass as the model field of a chat completion request.

  1. Read the template wiring. The baseRefs field stacks validated LLMInferenceServiceConfig templates onto the deployment:

oc get llmisvc cpu-demo-llm -n abc123-user1 -o jsonpath='{.spec.baseRefs}'

The output references v3-6-0-kserve-config-llm-template-cpu — the vLLM CPU accelerator configuration that ships with RHOAI 3.6. Module 03 covers these templates and the cluster-side LLMInferenceServiceConfig objects behind them.

  1. Confirm the deployment is ready:

oc get llmisvc cpu-demo-llm -n abc123-user1 \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'

The output should be True.

  1. Confirm the model server pod is running:

oc get pods -n abc123-user1 -l app.kubernetes.io/name=cpu-demo-llm

  1. Read the endpoint service. The llm-d controller creates a ClusterIP service for the workload:

oc get svc cpu-demo-llm-kserve-workload-svc -n abc123-user1

The service exposes port 8000/TCP.

  1. Read the internal inference endpoint URL — the URL behind the Internal endpoint button in the dashboard:

oc get llmisvc cpu-demo-llm -n abc123-user1 \
  -o jsonpath='{.status.addresses[0].url}'

The output is https://cpu-demo-llm-kserve-workload-svc.abc123-user1.svc.cluster.local.

  1. Compare the readiness of both llm-d deployments, including their distributed control plane conditions:

oc get llmisvc -n abc123-user1 \
  -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,REASON:.status.conditions[?(@.type=="Ready")].reason,ROUTER:.status.conditions[?(@.type=="RouterReady")].status,SCHEDULER:.status.conditions[?(@.type=="SchedulerWorkloadReady")].status'

Both deployments report READY=True and ROUTER=True. The distributed deployment also reports SCHEDULER=True: its endpoint-picker scheduler runs as part of the full distributed control plane that fronts its model replicas. The CPU deployment shows <none> under SCHEDULER — that condition belongs to the endpoint-picker scheduler workload that the full distributed topology adds.

  1. Optional: list the InferencePool objects in the project. A distributed llm-d deployment also creates an InferencePool, an HTTPRoute, and gateway wiring for its model replicas:

oc get inferencepool -n abc123-user1

Verify

You can print the model name, template reference, readiness, and internal endpoint of cpu-demo-llm entirely from the CLI, and the endpoint URL matches the dashboard’s Internal endpoint button. oc get llmisvc is the ground-truth companion to the dashboard for llm-d deployments.

Exercise 3: Send inference requests to the live endpoint

The cpu-demo-llm deployment serves an OpenAI-compatible API on its internal cluster endpoint over HTTPS on port 8000. Because this endpoint is cluster-local, you send requests from inside the cluster — for example from a workload pod or a terminal with cluster network access.

Prerequisites

  • Exercise 2 confirmed cpu-demo-llm reports Ready=True and its pod is Running

  • Your shell can reach the abc123-user1 namespace over the cluster network

Procedure

  1. Export the internal endpoint URL:

export MODEL_ENDPOINT=$(oc get llmisvc cpu-demo-llm -n abc123-user1 \
  -o jsonpath='{.status.addresses[0].url}')

  1. Send an OpenAI-compatible chat completion request. The internal service uses a cluster-internal TLS certificate, so pass -k to curl, and append the service port 8000:

curl -sk "$MODEL_ENDPOINT:8000/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "HuggingFaceTB/SmolLM2-135M-Instruct",
    "messages": [{
      "role": "user",
      "content": "What is Red Hat OpenShift AI?"
    }],
    "max_tokens": 64
  }'

A successful response is a chat.completion object whose model field matches HuggingFaceTB/SmolLM2-135M-Instruct and whose choices[0].message.content contains the generated answer.

  1. List the models served by the endpoint:

curl -sk "$MODEL_ENDPOINT:8000/v1/models"

The response lists the served model IDs, including HuggingFaceTB/SmolLM2-135M-Instruct.

The internal endpoint of this workshop deployment does not require a bearer token. For deployments that are reachable from outside the cluster, the deployment wizard’s Advanced settings step offers Require token authentication with a service account name. The tokens are created and displayed when the model server is configured, and the expanded row panel in AI hub > Models > Deployments then shows the Token authentication token name and secret to send in the Authorization: Bearer header.

Verify

Both requests return HTTP 200 with OpenAI-compatible JSON bodies, and the model ID in the chat completion response matches spec.model.name from Exercise 2. If you receive a connection error, confirm the :8000 port suffix and that the deployment still reports Ready=True.

You have now completed the core llm-d workflow: you located the deployment in the dashboard, read its ground truth from the CLI, and talked to the live model. The next module builds on it with KV-cache-aware router configurations and cluster-side configuration templates.

Module summary

What you accomplished:

  • Located llm-d model deployments in AI hub > Models > Deployments and read the expanded row panel — the detail view for llm-d deployments

  • Read the model name, accelerator template, readiness, and internal endpoint of the LLMInferenceService from the CLI with oc get llmisvc

  • Sent OpenAI-compatible chat completion and models-list requests to the live internal endpoint

Key takeaways:

  • In RHOAI 3.6, llm-d deployments appear in AI hub > Models > Deployments with Deployment resource set to Distributed inference with llm-d; they have no detail page, so oc get llmisvc is the ground truth for model and runtime

  • spec.model.name is the model ID to pass in chat completion requests, and status.addresses[0].url plus port 8000 is the internal OpenAI-compatible endpoint

  • spec.baseRefs wires validated LLMInferenceServiceConfig accelerator presets into the deployment

  • llm-d reports its distributed control plane (RouterReady, SchedulerWorkloadReady) separately from the model workload, so you can read each plane’s readiness on its own
