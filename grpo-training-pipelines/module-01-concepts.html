Module 01: Core Concepts

In this module you will understand what Group Relative Policy Optimization (GRPO) is, how the RHOAI AI Pipelines architecture runs it, and how the full fine-tuning and LoRA training modes compare.

Learning objectives:

  • Explain the GRPO reinforcement-learning loop and its group-relative advantage

  • Describe how the pipeline server (DSPA), DSPO, and Argo workflows fit together in RHOAI 3.6

  • Choose between full fine-tuning and LoRA for a GRPO training workload

Exercise 1: What is GRPO?

Group Relative Policy Optimization is a reinforcement-learning fine-tuning algorithm for large language models. Instead of supervised fine-tuning — where the model imitates a fixed dataset of prompt/response pairs — GRPO improves the model against a reward signal: the model generates responses, a reward function scores them, and the model’s weights are updated to make higher-scoring responses more likely.

GRPO gets its name from how it computes the advantage — the "how much better was this response" signal that drives the update:

  1. For each training prompt, the current policy samples a group of candidate responses (for example 8 or 16 completions of the same prompt).

  2. A reward function scores every response in the group. With verifiable rewards (RLVR), the reward is computed by checking the response itself — exact-match answer checks, unit tests, format rules — so no separate reward model is trained.

  3. Each response’s advantage is its reward normalized relative to the group: subtract the group mean and divide by the group spread. Responses that outscore the group average are reinforced; responses that underscore it are suppressed.

  4. The policy is updated with a clipped surrogate objective plus a KL penalty that keeps the model anchored to the reference policy.

Because the baseline comes from the group itself, GRPO does not need a learned critic (value) model the way PPO does — you train the policy model and nothing else. That halves the model memory that the training step must hold and is the main reason GRPO became the workhorse of reasoning-model fine-tuning.

Exercise 2: The RHOAI AI Pipelines architecture

RHOAI names its Kubeflow Pipelines distribution AI Pipelines (the component was renamed from Data Science Pipelines). Three layers cooperate:

Layer Role

Pipeline server (DataSciencePipelinesApplication, DSPA)

The namespaced pipeline engine. The DSPO operator reconciles the DSPA into a ds-pipeline API server deployment, a MariaDB metadata database on a PVC, and a persistence agent that tracks run state. Pipeline definitions and runs are stored in the database; large artifacts go to S3 object storage.

DSPO operator

The opendatahub-managed operator that watches DataSciencePipelinesApplication resources and provisions the pipeline server components, including the Argo Workflows controllers that execute runs.

Argo Workflows

The workflow engine under a pipeline run. Each pipeline run becomes an Argo workflow; the Executions view in the Pipelines UI shows the underlying Argo execution graph of every run.

  • MLflow integration is autodetected by default: the pipeline server injects MLflow tracking into compatible workloads without extra configuration.

Exercise 3: How a GRPO pipeline runs on RHOAI 3.6

A GRPO fine-tuning pipeline is a Kubeflow Pipelines (KFP) v2 definition — a graph of components — imported into your project’s pipeline server. When you create a run, the pipeline server compiles the definition into an Argo workflow and executes it:

  1. Prepare — the pipeline loads the prompt dataset and the base model.

  2. Generate — for each prompt the pipeline samples a group of candidate responses from the current policy. On GPU-backed steps the pipeline launches training work as TrainJob resources (Kubeflow Trainer v2) against a Training Hub runtime, and the GPU is attached through a DRA ResourceClaim.

  3. Reward — the reward function scores every response in the group.

  4. Update — the advantage (reward relative to the group mean) drives the policy update: every weight of the model in full fine-tuning mode, or only the low-rank adapter matrices in LoRA mode.

  5. Export — the updated model and metrics are written to the object-storage bucket as run artifacts.

You drive all of this from the dashboard’s Pipelines UI (Develop & train → Pipelines), which has four views:

View What it shows

Pipeline definitions

The imported pipeline graphs available in your project, with versions

Runs

Every execution of a pipeline definition, with status, duration, and parameters

Artifacts

The files and metrics the runs produced, traced to their producing run

Executions

The underlying Argo execution graph — every step a run performed

Verify

In the dashboard, click Develop & train → Pipelines. With a pipeline server configured in your project, the Pipeline definitions view opens with an Import pipeline button instead of a Configure a pipeline server empty state. You will use it in Module 02.

Full fine-tuning or LoRA?

GRPO pipelines in RHOAI 3.6 support two training modes:

Full fine-tuning LoRA matrix When to choose

What is updated

Every weight of the model

Only low-rank adapter matrices (A·B) injected into target layers; base weights stay frozen

LoRA for adaptation on a budget; full fine-tuning when the behavior change is large

Trainable parameter memory

Optimizer state for all weights — the dominant memory cost

A small fraction of the weights (the adapter rank times the layer shapes)

LoRA fits larger models (or larger GRPO groups) on the same GPU

Artifact size

A full model copy per export

A small adapter file per export; the base model is referenced at load time

LoRA exports are cheap to store, version, and merge

Quality profile

Maximum capacity to change behavior

Near-full-FT quality for style, format, and domain adaptation

Start with LoRA; move to full fine-tuning if adapter-only updates plateau

In LoRA mode the pipeline trains the adapter matrices — the "LoRA matrix" of the feature name — while the frozen base model is loaded read-only. The LoRA hyperparameters (adapter rank, alpha scaling, target modules) are pipeline run parameters; Module 03 runs the LoRA variant and compares it with the full fine-tuning run of Module 02.
