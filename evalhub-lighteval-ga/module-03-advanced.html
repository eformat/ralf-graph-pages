Module 03: Advanced Usage

In this module you will go beyond the UI: drive evaluation runs through the EvalHub REST API, control pass criteria with thresholds and primary scorers, choose between suites and individual benchmarks, and interpret scores honestly — especially the low scores a small CPU-only model produces.

Learning objectives:

  • Discover providers and benchmarks through the EvalHub REST API and submit an evaluation job

  • Configure pass criteria: benchmark thresholds, primary scorer metrics, and weights

  • Choose between multi-task suites and individual benchmarks, and pass custom benchmark parameters

  • Interpret low CPU-model scores without over-claiming

Exercise 1: API-driven runs

Everything the AI Evaluations UI does is available through the EvalHub REST API. The API listens inside the cluster on port 8444 of the evalhub pod in redhat-ods-applications; requests are authorized with the X-Tenant, X-User, and X-Groups headers that the dashboard normally injects for you.

  1. Discover providers and benchmarks. Define a helper that calls the API through the evalhub pod, then use it for the provider and benchmark listings:

    exec_api() {
  oc exec -i deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s \
    -H "X-Tenant: ai-tenants" -H "X-User: $(oc whoami)" \
    -H "X-Groups: system:authenticated" "$@"
}
exec_api http://127.0.0.1:8444/api/v1/evaluations/providers \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(i["resource"]["id"], len(i.get("benchmarks") or [])) for i in d["items"]]'
exec_api http://127.0.0.1:8444/api/v1/evaluations/providers/lighteval \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(b["id"], "-", b["name"], "| metrics:", ",".join(b["metrics"]), "| threshold:", b["pass_criteria"]["threshold"]) for b in d["benchmarks"]]'

    Expected output lists the six providers (with lighteval 28) and then the LightEval catalog, including:

    hellaswag - Everyday activity completion | metrics: hellaswag.em | threshold: 0.25

  2. Submit an evaluation job with the simplified benchmark schema (POST /api/v1/evaluations/jobs). This example runs hellaswag on the staged endpoint over a small subset via the limit parameter:

    cat > job.json <<'EOF'
{
  "name": "hellaswag-qwen-api-demo",
  "model": {
    "url": "http://qwen25-05b.ai-tenants.svc.cluster.local:8080/v1",
    "name": "qwen25-05b"
  },
  "benchmarks": [
    {
      "id": "hellaswag",
      "provider_id": "lighteval",
      "primary_score": { "metric": "hellaswag.em" },
      "pass_criteria": { "threshold": 0.25 },
      "parameters": { "limit": 20 }
    }
  ]
}
EOF
oc exec -i deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s -X POST \
  -H X-Tenant:ai-tenants -H X-User:$(oc whoami) \
  -H X-Groups:system:authenticated -H "Content-Type: application/json" \
  --data-binary @- http://127.0.0.1:8444/api/v1/evaluations/jobs < job.json

    The response contains the created job with its id and state pending or running.

exec_api is a shell function defined in step 1 — if you open a new terminal, paste the function definition again before using it in later steps.

  1. Track the job:

    exec_api http://127.0.0.1:8444/api/v1/evaluations/jobs/ | python3 -m json.tool

    Replace <job_id> with the identifier from the submission response. The job document reports the overall state, per-benchmark status, and the hellaswag.em score once the benchmark reaches a terminal state.

Verify

GET /api/v1/evaluations/providers returns the six providers, the providers/lighteval detail lists 28 benchmarks, and the submitted job transitions to a terminal state with a hellaswag.em score or an explicit error message. The same job appears on the dashboard Runs tab — the UI and the API read the same job store.

Exercise 2: Thresholds, primary scorers, and weights

Every LightEval benchmark declares a primary scorer — the metric it is judged on — and a default pass threshold. For hellaswag the primary scorer is hellaswag.em (rendered Hellaswag.em in the UI) and the default threshold is 0.25, which is exactly the random-guess baseline for its four-way multiple-choice format. The math suite is judged on all.maj@4 (majority-of-4 voting), the GLUE suite on acc with matthews_correlation and f1 as secondary metrics.

Job and benchmark pass criteria resolve at three levels, most specific first: benchmark level, then collection level, then provider level. In the simplified job schema you set them per benchmark:

  • pass_criteria.threshold — the score the benchmark must meet to pass

  • primary_score.metric — which metric decides the pass/fail outcome, with lower_is_better for metrics such as perplexity

  • weight — the relative weight of a benchmark when one job runs several benchmarks

    1. Compare two benchmark definitions from the catalog:

      exec_api http://127.0.0.1:8444/api/v1/evaluations/providers/lighteval \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(b["id"], "| primary:", b["primary_score"]["metric"], "| threshold:", b["pass_criteria"]["threshold"], "| dataset:", b["dataset_size"]) for b in d["benchmarks"] if b["id"] in ("hellaswag","math")]'

      Expected output:

      hellaswag | primary: hellaswag.em | threshold: 0.25 | dataset: 10042
math | primary: all.maj@4 | threshold: 0.25 | dataset: 0

Verify

You can state hellaswag’s primary scorer and threshold, and explain why the `0.25 default is meaningful for a four-choice benchmark (it is the random baseline).

Exercise 3: Suites, individual benchmarks, and custom parameters

Suites and individual benchmarks answer different questions:

  • Suites (math, knowledge, truthfulness, language_understanding, commonsense_reasoning, scientific_reasoning, physical_commonsense) aggregate related tasks and report aggregate scores such as all.maj@4 or Math: average.maj@4. Use them for breadth.

  • Individual benchmarks (hellaswag, gsm8k, mmlu, winogrande, openbookqa, piqa, triviaqa, gpqa:diamond, aime24, aime25, and the rest) run one task. Use them for depth and speed.

Custom benchmark parameters tune a run’s cost and coverage. The simplified job schema accepts a parameters object per benchmark — for example num_fewshot (few-shot examples) and limit (cap the dataset subset, as in Exercise 1). The UI exposes the same capability through the optional Benchmark parameters checkbox on the start form.

  1. Inspect a benchmark’s dataset size before choosing a limit:

    exec_api http://127.0.0.1:8444/api/v1/evaluations/providers/lighteval \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(b["id"], "dataset_size:", b["dataset_size"], "few_shot:", b["num_few_shot"]) for b in d["benchmarks"] if b["id"] in ("hellaswag","mmlu","gsm8k")]'

    hellaswag ships 10,042 examples — on a CPU-only model you will want a limit subset or you will wait a very long time.

Verify

You can name the seven suites, pick an individual benchmark for a quick smoke test, and explain what limit changes about a run (coverage and wall-clock time, not the scoring formula).

Exercise 4: Interpreting low scores honestly

The workshop’s qwen25-05b endpoint is a 0.5-billion-parameter model running on two CPUs. Expect low scores, and read them for what they are:

  • hellaswag.em near 0.25 is the random baseline. A tiny model scoring 0.25–0.30 is performing at close to chance on four-choice questions. That is an honest result about the model, not a failure of the evaluation platform.

  • The pipeline is the product. A completed run with a recorded score proves the whole chain — endpoint validation, job scheduling, the LightEval runner image, scoring, and MLflow tracking. The score value is a property of the model; the run completing is a property of the platform.

  • Failed runs are evidence too. A run that ends Failed shows its error text on the Runs tab and in GET /api/v1/evaluations/jobs/<job_id> — record it exactly as shown. An auth mismatch, an unreachable endpoint, or an incompatible model name are all diagnosable from that error.

  • Scale for signal. To get decision-grade scores, use a larger model on a GPU-backed endpoint, a higher limit, and multiple benchmarks or suites — then compare runs in MLflow.

Verify

You can explain to a colleague why a hellaswag.em of 0.26 from the workshop model is a correct and useful result, and what you would change to get more signal.

Module summary

What you accomplished:

  • Drove provider discovery and job submission through the EvalHub REST API

  • Configured pass criteria with thresholds, primary scorers, and weights

  • Chose between suites and individual benchmarks and tuned runs with benchmark parameters

  • Interpreted low CPU-model scores honestly, including failed-run error text

Key takeaways:

  • The UI is a thin layer over the REST API — headers X-Tenant/X-User/X-Groups authorize the same operations

  • Scores describe the model; a completed run describes the platform — report both honestly
