Module 02: Hands-on Exercise

In this module you enable the Inspect AI provider on the EvalHub custom resource (CR) with a one-line GitOps change, stage a small CPU-only vLLM evaluation target, and run your first Inspect AI benchmark — inspect/strong-reject — against it end to end. Everything here runs on a CPU-only cluster: no GPUs are needed to evaluate a 0.5B model.

Learning objectives:

  • Log in to the workshop cluster and the dashboard Develop & train → Evaluations UI without tripping the keycloak credentials gotcha

  • Enable a shipped-but-disabled evaluation provider by appending one line to spec.providers on the EvalHub CR — and verify it via the provider ConfigMap mechanism, never oc patch

  • Stage an OpenAI-compatible evaluation target from the workshop’s additive deploy/ manifests (oc apply -k)

  • Start an Inspect AI benchmark from the dashboard catalog and the REST API, with job.model.url pointing at the staged endpoint and no API key

Status of the evidence in this module. The before numbers (6 providers, no Inspect AI; the vLLM target absent) were captured live from the workshop cluster while this module was authored. The after outputs are what your cluster shows once you perform each step — the workshop production run (demo evalhub-inspect-ai-ga-steps.json, VALIDATE phase) records the live captures of the end-to-end run. Wherever a value depends on your own run (job id, timestamps, scores), treat the printed values as placeholders that your run will replace.

Before you start: access and prerequisites

You need:

  • A checkout of the workshop assets repository — every command below runs from its root.

  • oc (OpenShift CLI) logged in to the workshop cluster:

oc login https://api.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com:6443
# username: prelude  (password: the OCP_PASSWORD value — see the gotcha below)
oc whoami

Expected output of oc whoami is prelude.

The keycloak login gotcha (read this before opening the dashboard)

The dashboard’s Log in with OpenShift flow redirects through keycloak at keycloak-keycloak.apps.sno.sandbox1254.opentlc.com. The workshop secret ralf-graph (namespace openshift-config) carries two credential pairs, and only one of them works there:

  • KEYCLOAK_USER / KEYCLOAK_PASSWORD (temp-admin) — FAIL. These keycloak admin credentials do not authenticate the dashboard SSO (single sign-on) login page. Do not debug them; they are admin-plane credentials, not workshop-login credentials.

  • OCP_USER=prelude / OCP_PASSWORD — use these. The same pair that logs in to the cluster with oc login also logs in to the dashboard’s keycloak page.

Fetch the working credentials (namespace openshift-config):
oc -n openshift-config get secret ralf-graph \
  -o jsonpath='{.data.OCP_USER}' | base64 -d; echo
oc -n openshift-config get secret ralf-graph \
  -o jsonpath='{.data.OCP_PASSWORD}' | base64 -d > /tmp/ocp-password && echo "password staged"

Verify

You are logged in (oc whoami prints prelude), and the dashboard at https://rh-ai.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com opens Develop & train → Evaluations (path /evaluation) after you complete the keycloak redirect with prelude + OCP_PASSWORD — not with the KEYCLOAK_USER temp-admin pair, which fails by design on that page. Keep the dashboard tab open; Exercise 3 uses it.

Exercise 1: Enable the Inspect AI provider (one GitOps line)

The Inspect AI provider ships with RHOAI (Red Hat OpenShift AI) 3.6 as ConfigMap trustyai-service-operator-evalhub-provider-inspect (label trustyai.opendatahub.io/evalhub-provider-name=inspect) in namespace redhat-ods-applications — 79 benchmarks covering the Petri alignment audits, Bloom, GDM, and 36 curated inspect-evals safety/reasoning benchmarks. But it is not enabled: the GitOps-owned EvalHub CR pins the six legacy providers.

Confirm the shipped-but-disabled state (the honest "before" numbers):
oc get cm -n redhat-ods-applications \
  -l trustyai.opendatahub.io/evalhub-provider-name=inspect --no-headers
oc get evalhub evalhub -n redhat-ods-applications -o jsonpath='{.spec.providers}{"\n"}'

Expected output: the …evalhub-provider-inspect ConfigMap exists, while spec.providers still lists six names — ["lm-evaluation-harness","garak","garak-kfp","guidellm","lighteval","ibm-clear"] — with inspect absent. This is exactly what the in-pod providers API reports at this point: total_count: 6.

Enable it with the shipped handoff patch — never with oc patch:
cd <assets repo root>   # eformat/ralf-graph-assets
git apply features/evaluation/evalhub-inspect-ai-ga/deploy/0001-evalhub-add-inspect-provider.patch
git diff cluster/overlays/prelude-36-ea/evalhub.yaml   # exactly one added line: "    - inspect"
git add cluster/overlays/prelude-36-ea/evalhub.yaml && git commit -m "Enable Inspect AI provider on EvalHub (GA 3.6)"

cluster/overlays/prelude-36-ea/evalhub.yaml is a GitOps-owned overlay. The only supported enablement vehicle is this commit (picked up by the GitOps sync — the EvalHub CR carries an ArgoCD sync-wave-3 annotation). Never oc patch or oc apply the EvalHub CR against the cluster: it is GitOps-owned, a direct patch drifts the overlay, and it gets reverted. On the workshop cluster this commit is performed by the platform owner — the patch file and deploy/README-HANDOFF.md are the handoff artifacts they need.

The change is purely data-driven. The trustyai operator mounts one provider ConfigMap per spec.providers entry into the projected volume evalhub-providers at /etc/evalhub/config/providers, and the EvalHub config-watcher serves them — no image change, no reinstall. The commit adds the seventh ConfigMap on the operator’s reconcile.

Watch the operator mount the seventh provider ConfigMap:
oc -n redhat-ods-applications get deploy evalhub -o json \
  | jq '.spec.template.spec.volumes[] | select(.name=="evalhub-providers") | .projected.sources | length'

Expected output after the sync: 7 (up from 6).

Verify

Check the in-pod providers API (the same call the dashboard makes):
oc exec -i deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s \
  -H "X-Tenant: ai-tenants" -H "X-User: prelude" -H "X-Groups: admin" \
  http://127.0.0.1:8444/api/v1/evaluations/providers \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print("total_count:", d["total_count"]); [print("-", i["resource"]["id"], len(i.get("benchmarks") or []), "benchmarks") for i in d["items"]]'

Expected output — total_count: 7 with inspect now present and its 79 benchmarks (the other six rows match the live before-state: 167, 28, 1, 7, 9 and 9 benchmarks):

total_count: 7
- lm_evaluation_harness 167 benchmarks
- lighteval 28 benchmarks
- ibm-clear 1 benchmarks
- guidellm 7 benchmarks
- garak-kfp 9 benchmarks
- garak 9 benchmarks
- inspect 79 benchmarks

Second verification, UI-side: in the dashboard Evaluations page, the Framework filter on the Benchmark collections tab now lists Inspect AI.

If the API still reports total_count: 6 after the sync, the running pod has not hot-reloaded the new ConfigMap — run oc -n redhat-ods-applications rollout restart deploy/evalhub and re-check. Whether the config-watcher hot-reloads or needs a restart is a known residual; verify before forcing.

With the provider enabled, you now need an evaluation target for your benchmarks to run against.

Exercise 2: Stage the CPU vLLM evaluation target

This cluster has zero GPUs and no pre-staged models, so the workshop ships an additive manifest set under features/evaluation/evalhub-inspect-ai-ga/deploy/: a CPU-only vLLM server (Red Hat’s vllm-cpu-rhel9 image) serving Qwen/Qwen2.5-0.5B-Instruct — a ~1 GB instruct model — as a Deployment
Service + Route plus a 5Gi model PVC (persistent volume claim) in namespace ai-tenants. Nothing here touches GitOps-owned resources.

Apply the manifests (the kustomization pins the namespace — do not pass -n):
oc apply -k features/evaluation/evalhub-inspect-ai-ga/deploy/

Expected output creates four resources in ai-tenants — the model PVC first: persistentvolumeclaim/vllm-qwen25-05b-model, deployment.apps/vllm-qwen25-05b, service/vllm-qwen25-05b, and route.route.openshift.io/vllm-qwen25-05b.

Wait for the rollout. The pod has nothing to download: the model-verify

initContainer is verify-only — it checks that the ~1 GB of Qwen2.5-0.5B-Instruct weights are already baked into the PVC vllm-qwen25-05b-model and fails fast until they are. Runtime model download inside ai-tenants is impossible in this sandbox (huggingface.co egress is cluster-blocked, and the private-models-workbench "mirror" is an empty Jupyter workbench), so the claim is filled ONCE out-of-band via the Model staging procedure in deploy/README.md. After that one-time fill, every rollout is a no-download path of ~2-3 minutes (the startupProbe budgets 15 minutes):

oc -n ai-tenants rollout status deployment/vllm-qwen25-05b --timeout=900s

Verify

The endpoint must speak the OpenAI API. Check /v1/models and one chat

completion from inside the cluster (the same path the EvalHub job uses):

oc -n ai-tenants run curl-check --rm -i --restart=Never --image=curlimages/curl -- \
  curl -s http://vllm-qwen25-05b.ai-tenants.svc:8080/v1/models
oc -n ai-tenants run curl-chat --rm -i --restart=Never --image=curlimages/curl -- \
  curl -s http://vllm-qwen25-05b.ai-tenants.svc:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-0.5B-Instruct","messages":[{"role":"user","content":"Say hello in one word."}],"max_tokens":16}'

Expected output: a model list whose id is exactly Qwen/Qwen2.5-0.5B-Instruct, followed by a chat completion containing text — a 0.5B model’s answer will be brief and may be odd; it only needs to be text.

{"object":"list","data":[{"id":"Qwen/Qwen2.5-0.5B-Instruct","object":"model",...}]}
Grab the browser-facing route host (the dashboard’s External endpoint flow

validates an https URL, so the UI path uses the Route while the API path uses the Service):

oc -n ai-tenants get route vllm-qwen25-05b -o jsonpath='{.spec.host}{"\n"}'

Expected route host (fetch yours — this is the cluster’s apps domain): vllm-qwen25-05b-ai-tenants.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com.

No API key anywhere. The staged vLLM endpoint enforces no authentication — the Inspect AI provider configuration states its global api_key parameter is "Not required for unauthenticated vLLM". The evaluation job’s api_key stays null and the UI’s authentication field stays empty. Teardown when you are done: oc -n ai-tenants delete deploy,svc,route vllm-qwen25-05b pvc/vllm-qwen25-05b-model (this also drops the baked ~1 GB model — re-run the Model staging fill to restore it on the next run).

With the target serving, you are ready to run a real Inspect AI benchmark against it.

Exercise 3: Run your first Inspect AI benchmark

The recommended first benchmark is inspect/strong-reject (StrongREJECT): a safety benchmark that measures refusal quality — it tests both over-refusal and under-refusal, so it exercises an instruct model’s safety behavior, not just its accuracy. It has no required parameters. If it is unavailable on your build, the same flow works with the reasoning benchmarks inspect/arc (metric accuracy/accuracy) or inspect/gsm8k (primary metric match/accuracy).

From the dashboard (UI catalog)

  1. Open https://rh-ai.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com → Develop & train → Evaluations (path /evaluation), logging in per the keycloak gotcha. Make sure the project selector shows ai-tenants.

  2. On the Benchmark collections tab, set the Framework filter to Inspect AI (Exercise 1 made it appear) and click Select benchmark on the StrongREJECT card.

  3. Fill the Start evaluation run form with exactly these values:

Form field Value

Evaluation name

Keep the pre-filled timestamped name, or set your own (for example strong-reject-qwen-demo)

Model

Other (External endpoint) — an info alert confirms: "This model must expose an OpenAI-compatible chat/completions endpoint."

Model name

Qwen/Qwen2.5-0.5B-Instruct — the exact HuggingFace ID the server was loaded with; the provider documentation requires vLLM model names to match the served ID (/v1/models above shows it)

Endpoint URL

The route host from Exercise 2 with /v1 appended: https://vllm-qwen25-05b-ai-tenants.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com/v1

Authentication

Leave unset — the endpoint is unauthenticated by design; the job’s api_key stays null

  1. Click Validate connection, then Start evaluation run once it succeeds. The dashboard navigates to the Runs tab where your evaluation appears with state Queued or Running.

From the REST API

The same job through the EvalHub API — POST /api/v1/evaluations/jobs with job.model.url pointing at the staged in-cluster Service (this is the URL the job runtime itself calls, so it must be the Service DNS name, not the Route):

cat > strong-reject-job.json <<'EOF'
{
  "name": "strong-reject-qwen-demo",
  "model": {
    "url": "http://vllm-qwen25-05b.ai-tenants.svc:8080/v1",
    "name": "Qwen/Qwen2.5-0.5B-Instruct"
  },
  "benchmarks": [
    {
      "id": "inspect/strong-reject",
      "provider_id": "inspect"
    }
  ]
}
EOF
oc exec -i deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s -X POST \
  -H X-Tenant:ai-tenants -H X-User:$(oc whoami) \
  -H X-Groups:system:authenticated -H "Content-Type: application/json" \
  --data-binary @- http://127.0.0.1:8444/api/v1/evaluations/jobs < strong-reject-job.json

The response contains the created job with its id and state pending or running. The benchmark entry needs only id and provider_id: the catalog’s own primary score applies (the Inspect AI catalog declares accuracy/accuracy for strong-reject), and no parameters are required.

Track the job to a terminal state:
oc exec -i deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s \
  -H X-Tenant:ai-tenants -H X-User:$(oc whoami) -H X-Groups:system:authenticated \
  http://127.0.0.1:8444/api/v1/evaluations/jobs/<job_id> | python3 -m json.tool

Replace <job_id> with the identifier from the submission response. On the cluster side, each Inspect AI benchmark executes as a Kubernetes job in the EvalHub namespace, its pod running the odh-eval-hub-inspectai-rhel9 image (requesting 8–32Gi memory — it coexists with the 5Gi vLLM target on the 121Gi nodes):

oc -n redhat-ods-applications get jobs,pods -l app.kubernetes.io/part-of=evalhub --sort-by=.metadata.creationTimestamp | tail -5

Verify

Your run reaches a terminal state on the dashboard Runs tab (and in the GET /api/v1/evaluations/jobs/<job_id> response): Completed runs show the StrongREJECT score, and Failed runs show the error text — both are honest terminal outcomes. A CPU-only 0.5B run takes minutes, not seconds, and low scores are expected results of a small model, not of a broken setup.

What a passing check looks like on the workshop cluster: the Framework filter lists Inspect AI (Exercise 1), the run’s Model resolves to Qwen/Qwen2.5-0.5B-Instruct at the staged endpoint, and the run’s scores land in the MLflow experiment you selected. The workshop production run captures these live (dashboard screenshots of the filtered catalog and the run detail page, plus the job log) — your own run produces equivalent evidence with its own job id, timestamps, and scores.

Module summary

What you accomplished:

  • Logged in to the cluster and dashboard with the working OCP_USER=prelude credentials, avoiding the keycloak KEYCLOAK_USER temp-admin trap

  • Enabled the shipped Inspect AI provider with one committed line in the EvalHub CR spec.providers — verified through the projected provider ConfigMap mount (6→7) and the in-pod providers API (total_count: 7, 79 inspect benchmarks)

  • Staged a CPU-only vLLM OpenAI-compatible target (vllm-qwen25-05b serving Qwen/Qwen2.5-0.5B-Instruct) from the workshop’s additive deploy/ manifests

  • Ran inspect/strong-reject end to end from the dashboard catalog and the REST API, with no API key

Key takeaways:

  • Providers ship as labeled ConfigMaps and activate via spec.providers — a data-driven, one-line enablement with no image change; GitOps-owned CRs change only through a commit, never oc patch

  • The evaluation target needs exactly three things: an OpenAI-compatible endpoint URL (Service DNS for the API path, Route host for the UI path), the exact served model name, and — for an unauthenticated vLLM endpoint — no credentials at all

  • inspect/strong-reject needs no parameters; the catalog’s declared primary score applies by default. Fallbacks inspect/arc and inspect/gsm8k follow the same flow

  • Watch your strong-reject run on the dashboard Runs tab and find its score in the MLflow experiment you selected

  • Try the fallback benchmarks inspect/arc and inspect/gsm8k — the job shape is identical, only the benchmark id changes
