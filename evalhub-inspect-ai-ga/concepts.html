Module 01: Core Concepts

In this module you will understand what the Inspect AI provider is, how Red Hat ships and enables it in the EvalHub evaluation stack, and what its 79-benchmark catalog covers — before you enable it and run your first benchmark in Module 02.

Learning objectives:

  • Explain what Inspect AI is (the UK AI Security Institute’s evaluation framework) and where it fits in the EvalHub architecture

  • Describe how the provider ships: 17 system provider ConfigMaps, one per evaluation framework

  • Map the Inspect AI benchmark landscape: 36 Petri alignment audits, Bloom, Google DeepMind capability suites, and 38 curated inspect-evals tasks

  • Trace the enablement path from one line in the EvalHub custom resource (CR) to a mounted provider ConfigMap inside the EvalHub pod

Exercise 1: What Inspect AI is and where it fits

EvalHub is the evaluation orchestration service for large language models (LLMs) in OpenShift AI. It exposes a REST API for submitting evaluation jobs, manages benchmark providers, and tracks results in MLflow. Providers are evaluation framework adapters; benchmarks are the individual tasks a provider can run; collections group benchmarks into reusable suites; jobs execute benchmarks against a model endpoint.

Inspect AI is the open-source LLM evaluation framework built by the UK AI Security Institute (UK AISI). The provider ConfigMap on your cluster describes it verbatim as: "UK AISI Inspect AI framework — Petri/Bloom alignment auditing and inspect-evals benchmarks". Three capabilities define the provider:

  • Petri — an auditor/target/judge alignment-audit pipeline: a second model drives adversarial multi-turn conversations with your target model, and a third model grades the transcripts on 38 alignment dimensions

  • Bloom — automated scenario generation from behavior descriptions, so you can evaluate behaviors without hand-writing prompts

  • inspect-evals — the curated UK AISI benchmark library spanning safety, coding, math, knowledge, and agent evaluation

Red Hat packages the framework as a provider runtime image (odh-eval-hub-inspectai-rhel9) that EvalHub schedules as a Kubernetes job per benchmark run. Each Inspect AI job pod requests 500m CPU / 8Gi memory and is limited to 2 CPU / 32Gi — an evaluation runtime that needs no GPU, only an OpenAI-compatible endpoint to talk to.

The concepts that matter for Inspect AI runs:

  • Provider — inspect (display name Inspect AI)

  • Benchmarks — 79 tasks, from one-line refusal checks to three-model alignment audits (Exercise 3)

  • Model endpoint — an OpenAI-compatible chat/completions endpoint such as vLLM; the adapter talks to it with the exact HuggingFace model ID the server was loaded with

  • Model roles — beyond the target, Petri benchmarks accept per-role overrides (auditor_model, judge_model, plus per-role base_url/api_key) so each role can use a different endpoint

  • Primary score — the metric a benchmark is judged on; accuracy metrics read higher-is-better, while Petri’s concerning/mean reads lower-is-better (a high score means the audit found concerning behavior)

  • MLflow experiment — where scores land; the UI creates or reuses an MLflow experiment per run

Verify

You can explain the EvalHub building blocks (provider, benchmark, collection, job, MLflow), name the three Inspect AI capabilities (Petri, Bloom, inspect-evals), and state the job pod’s resource shape (500m/8Gi request, 2 CPU/32Gi limit).

Key facts about the Inspect AI ConfigMap (trustyai-service-operator-evalhub-provider-inspect):

  • It carries the label trustyai.opendatahub.io/evalhub-provider-name: inspect and trustyai.opendatahub.io/evalhub-provider-type: system — the label, not the name, is how the operator knows what it is

  • Its single data key, inspect.yaml, holds the complete provider declaration: identity (id: inspect, name: Inspect AI, the UK AISI description), the runtime job spec (image, entrypoint, requests/limits), all 79 benchmark definitions with their metrics and primary scores, and the provider-wide parameters

  • Shipping as a ConfigMap is what makes providers hot-pluggable: enabling one is a volume change, not an image build (Exercise 4)

Note what is not in the ConfigMap: any maturity or lifecycle field. Whether a provider is GA (Generally Available), Developer Preview, or Technology Preview is established by the release documentation and the dashboard banner — the provider declaration itself carries no maturity metadata.

Picking a benchmark is only half the story — the next exercise shows how a shipped provider actually gets enabled on the cluster.

Exercise 4: How enablement works: from one CR line to a mounted ConfigMap

Shipping a provider ConfigMap is not the same as enabling it. The EvalHub pod only sees the providers listed in the EvalHub custom resource (spec.providers). The path from CR line to running provider has four steps:

  1. You declare — spec.providers in the EvalHub CR lists the enabled provider names. On this cluster it currently reads lm-evaluation-harness, garak, garak-kfp, guidellm, lighteval, ibm-clear — six providers, with inspect not yet among them.

  2. The operator assembles — the TrustyAI Operator watches the CR and builds a projected volume evalhub-providers on the EvalHub deployment, with one ConfigMap source per enabled provider.

  3. The pod mounts — that volume mounts read-only at /etc/evalhub/config/providers; every provider the pod can see is one .yaml file in that directory.

  4. The service hot-loads — the EvalHub service loads each file into its provider registry; /api/v1/evaluations/providers reports what is live.

See the mounted side yourself — inside the EvalHub pod, the directory holds exactly the six enabled providers:

oc exec deploy/evalhub -c evalhub -n redhat-ods-applications -- ls /etc/evalhub/config/providers

Expected output:

garak-kfp.yaml
garak.yaml
guidellm.yaml
ibm-clear.yaml
lighteval.yaml
lm_evaluation_harness.yaml

And the API agrees — six providers, no Inspect AI yet:

oc exec deploy/evalhub -c evalhub -n redhat-ods-applications -- curl -s \
  -H "X-Tenant: ai-tenants" -H "X-User: $(oc whoami)" \
  -H "X-Groups: system:authenticated" \
  http://127.0.0.1:8444/api/v1/evaluations/providers \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print("total_count:", d["total_count"]); [print(i["resource"]["id"], len(i.get("benchmarks") or [])) for i in d["items"]]'

Expected output:

total_count: 6
lm_evaluation_harness 167
lighteval 28
ibm-clear 1
guidellm 7
garak-kfp 9
garak 9

The EvalHub CR is GitOps-owned. Enabling Inspect AI means appending one line — - inspect — to spec.providers in the GitOps overlay, committed and synced like any other cluster declaration. Never oc patch or oc apply the CR directly. Module 02, Exercise 1 walks the exact one-line change and how to verify it landed (provider count 6 → 7).

Once the change syncs, the operator adds a seventh ConfigMap source to the projected volume, inspect.yaml appears in /etc/evalhub/config/providers, and the API reports total_count: 7 with inspect 79 — no EvalHub pod rebuild required, because the provider was a volume away all along.

Verify

You can trace the four-step enablement path (CR spec.providers → operator projects a ConfigMap per provider → read-only mount at /etc/evalhub/config/providers → config-watcher hot-loads it), explain why the fix belongs in GitOps rather than oc patch, and predict what changes after the sync (7 ConfigMap sources, 7 total_count, inspect 79).
