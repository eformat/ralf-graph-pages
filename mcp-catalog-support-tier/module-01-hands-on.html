Module 01: MCP Catalog support tiers in action

In this module you enable the MCP Lifecycle Operator that powers the AI Hub MCP Catalog, learn to read the support-tier labels on every catalog card, deploy an MCP server from the catalog into your working project, and verify the resulting workload from the CLI.

Learning objectives:

  • Explain what the Red Hat supported, Partner supported, and Community supported tiers mean on MCP server cards

  • Enable MCP server lifecycle management with the DataScienceCluster and OdhDashboardConfig resources

  • Deploy an MCP server from the AI Hub MCP Catalog and confirm its ACCEPTED, AVAILABLE, and VERIFIED conditions

  • Monitor and remove an MCPServer custom resource from the CLI

This feature is a Technology Preview. Technology Preview features are not supported with Red Hat production service-level agreements (SLAs) and might not be functionally complete. Red Hat does not recommend using them in production. The MCPServer custom resource API version is v1beta1 (the CRD also serves a legacy v1alpha1 API); CRD types and fields can change in a future release without a migration path, so the commands and manifests shown here may change between releases.

Before you start: the pieces behind the catalog

The AI Hub MCP Catalog is a federated plugin in the Red Hat OpenShift AI dashboard, pre-loaded with MCP servers from Red Hat, technology partners, and the open source community. The catalog data — including each server’s support tier — is delivered by the AI Hub Catalog custom resource, whose catalog workload runs the registry.redhat.io/rhai/ai-hub-catalog-rhel9 image. The support-tier information is part of this catalog payload; the gen-ai-aa-mcp-servers and mcp-catalog-sources configmaps in the dashboard namespaces do not carry tier data.

The support tier is a badge shown on every server card alongside the server name, description, and supported tools. The badge text tells you who maintains and supports that server:

Support tier Description

Red Hat supported

Fully supported by Red Hat.

Partner supported

Supported by the technology partner who maintains the server.

Community supported

Best-effort support from the open source community.

The mcplifecycleoperator component is the deployment runtime behind the catalog. It watches for MCPServer custom resources and provisions the required Deployment, Service, and NetworkPolicies automatically. On this workshop cluster the component ships enabled — managementState: Managed in the DataScienceCluster — so the catalog’s deploy action works out of the box. On a cluster where the component has not been enabled yet, an administrator must set it to Managed explicitly before the catalog’s deploy action works; the exercise below walks through that step.

Additional Technology Preview limitations to be aware of: the operator manages MCP servers within a single cluster only (multi-cluster management is not validated), and it includes no governance or policy enforcement. Rate limiting and access control for MCP servers live in the separate MCP Gateway Operator, part of Red Hat Connectivity Link, which must be installed independently if your scenario requires it.
Deploying MCP servers from the MCP Catalog requires the MCP Lifecycle Operator to be enabled (managementState: Managed). If it is not, a cluster administrator must enable it first; until then, the Deploy MCP server button on the server details page is disabled.

Exercise 1: Enable MCP server lifecycle management

In this exercise you act as the cluster administrator: you enable the mcplifecycleoperator component in the DataScienceCluster resource and turn on the mcpCatalog feature flag in the dashboard configuration.

  1. Identify the name of your DataScienceCluster object:

    oc get datasciencecluster

  2. Enable the MCP Lifecycle Operator by patching the DataScienceCluster object. Replace default-dsc with the name from the previous step if different:

    oc patch datasciencecluster default-dsc --type=merge \
  -p '{"spec":{"components":{"mcplifecycleoperator":{"managementState":"Managed"}}}}'

    You can also enable the MCP Lifecycle Operator from the OpenShift web console, as described in Installing and uninstalling OpenShift AI in the RHOAI documentation.

  3. Enable the MCP lifecycle feature in the dashboard by patching the OdhDashboardConfig custom resource. This is what makes the MCP Catalog UI and its support-tier labels visible to developers:

    oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications \
  --type=merge -p '{"spec":{"dashboardConfig":{"mcpCatalog":true}}}'

Verify

Confirm that the MCP Lifecycle Operator pod is running:

oc get pods -n redhat-ods-applications -l app.kubernetes.io/name=mcp-lifecycle-operator

You should see at least one pod in Running status, for example:

NAME                                          READY   STATUS    RESTARTS   AGE
mcp-lifecycle-operator-7c9d6b5f4d-xk2vq       1/1     Running   0          2m

Confirm that the component is reported as installed in the DataScienceCluster status:

oc get datasciencecluster default-dsc \
  -o jsonpath='{.status.installedComponents.mcplifecycleoperator}'

The expected output is true.

With lifecycle management enabled, the catalog is live — next you browse it as a developer and put the support-tier labels to work.

Exercise 2: Read the support tiers and deploy a server from the catalog

In this exercise you browse the AI Hub MCP Catalog in the dashboard, use the support tier to choose a server, and deploy it into your working project.

  1. In the Red Hat OpenShift AI dashboard, navigate to AI hub → MCP servers.

  2. Browse the available MCP servers. Each card displays the server name, a description, the supported tools, and the support tier badge (Red Hat supported, Partner supported, or Community supported).

  3. Filter the catalog by deployment mode or supported transport protocols to find a server that meets your requirements. For the smoothest start, pick a server carrying the Red Hat supported tier badge whose deployment mode is Local to cluster — this lab deploys com.redhat/insights-mcp-server, the Red Hat Lightspeed MCP server: a Red Hat supported server that runs inside your own project.

    Not every catalog server can be deployed this way. Some servers — for example com.redhat/openshift-mcp-server — require an MCP gateway. When the cluster has no gateway available, their Deploy MCP server button is disabled and the page shows the reason instead:

    +

    This MCP server requires an MCP gateway, and none is available. Ask your cluster administrator to set up an MCP gateway.

    In the RHOAI 3.6 catalog, 8 of the 9 servers — all with deployment mode Local to cluster — deploy without a gateway, so pick one of those, as this lab does with com.redhat/insights-mcp-server. Setting up an MCP gateway is optional and out of scope for this workshop.

  4. Click the server you want to deploy to open its details page. Review the server metadata: the tools it exposes, the Provider (Red Hat), the supported transport types (http-streaming, SSE), the deployment mode (Local to cluster), and the README. For com.redhat/insights-mcp-server, the README Prerequisites section lists what the server needs: service account credentials from console.redhat.com and a Kubernetes secret named insights-credentials with client-id and client-secret keys.

  5. Before deploying, create the insights-credentials secret in your working project. The deploy dialog references these keys through secretKeyRef entries but does not create the secret itself. Use your own service account credentials from console.redhat.com in place of the placeholder values:

    oc create secret generic insights-credentials \
  --from-literal=client-id= \
  --from-literal=client-secret= \
  -n abc123-user1

    The command confirms with secret/insights-credentials created.

  6. Click Deploy MCP server.

    The Deploy MCP server button stays disabled if the MCP Lifecycle Operator is not enabled on the cluster. Recheck Exercise 1 if the button is greyed out. It is also disabled for servers that require an MCP gateway, as described above.

  7. In the Deploy MCP server dialog, review the fields:

    • Deployment name — free text; as you type, the dialog shows the resulting resource name (The resource name will be <name>.). Enter insights-mcp-demo.

    • OCI image — prefilled from the catalog metadata (ghcr.io/redhatinsights/red-hat-lightspeed-mcp:latest) and read-only.

    • Project — select your working project, abc123-user1.

    • YAML configuration — an editable YAML snippet prefilled from the server’s catalog metadata, with the note: "This YAML has been prefilled from the selected server’s metadata in the catalog. Edit as needed."

  8. Edit the YAML configuration: add the arguments list under config:. The container image starts the MCP server in stdio mode by default, which suits local process transports; inside Kubernetes there is no stdin, so with the default arguments the container starts, exits immediately (exit code 0), and restarts in a loop without ever becoming available. The arguments override switches the server to the HTTP transport that matches the catalog’s streamable-http metadata and the dialog’s port and path values:

    config:
  port: 8000
  path: /mcp
  arguments:
    - http
    - --host
    - 0.0.0.0
  env:
    - name: LIGHTSPEED_CLIENT_ID
      valueFrom:
        secretKeyRef:
          name: insights-credentials
          key: client-id
    - name: LIGHTSPEED_CLIENT_SECRET
      valueFrom:
        secretKeyRef:
          name: insights-credentials
          key: client-secret

    When arguments is not set, the container image’s own default arguments (its CMD/ENTRYPOINT) apply. Here the override starts the server with the http transport listening on 0.0.0.0:8000, matching port: 8000 and path: /mcp.

    Troubleshooting: if you deploy without this edit, the pod never becomes ready: oc get pods shows the container exiting with STATUS Completed (exit code 0) and climbing RESTARTS, oc logs returns no container logs, and the MCPServer stays AVAILABLE=False. The fix is the same arguments override — either edit the YAML in the dialog and redeploy, or patch the existing resource:

    +

    oc patch mcpserver insights-mcp-demo -n abc123-user1 --type=json \
  -p '[{"op":"add","path":"/spec/config/arguments","value":["http","--host","0.0.0.0"]}]'

  9. Confirm the deployment by clicking Deploy in the dialog. The MCP Catalog submits the deployment request to the MCP Lifecycle Operator, which creates an MCPServer custom resource (apiVersion: mcp.x-k8s.io/v1beta1, annotated with the catalog server it came from) in your namespace and provisions the required Deployment and Service. The dashboard redirects to the Deployments tab, where a row for insights-mcp-demo appears immediately with status Initializing and changes to Available within about 30 seconds.

Verify

Confirm that the MCPServer custom resource is accepted, available, and verified:

oc get mcpservers -n abc123-user1

The output shows your MCP server with ACCEPTED, AVAILABLE, and VERIFIED all True, plus the in-cluster service ADDRESS, for example:

NAME                ACCEPTED   AVAILABLE   VERIFIED   IMAGE                                                  PORT   ADDRESS                                                            AGE
insights-mcp-demo   True       True        True       ghcr.io/redhatinsights/red-hat-lightspeed-mcp:latest   8000   http://insights-mcp-demo.abc123-user1.svc.cluster.local:8000/mcp   43s

Confirm the pod is Running and the server started its HTTP transport:

oc get pods -n abc123-user1
insights-mcp-demo-59958dc6dc-j77gd                          1/1     Running   0          43s
oc logs deployment/insights-mcp-demo -n abc123-user1

Look for the transport lines in the log output:

Starting Insights MCP server with args: Namespace(readonly=True, transport=http, host=0.0.0.0, port=8000)
Running HTTP transport on host: 0.0.0.0, port: 8000

The MCPServer custom resource uses the mcp.x-k8s.io/v1beta1 API version. Run oc explain mcpserver.spec --api-version=mcp.x-k8s.io/v1beta1 to view all available configuration fields (such as the required spec.config section) for the CRD version installed on your cluster.

In the dashboard, return to AI hub → MCP servers — the page has the Catalog, Registry, and Deployments tabs — and open the Deployments tab. The row for insights-mcp-demo lists com.redhat/insights-mcp-server as the MCP server, the creation time, the status Available, and a View link to the running service.

With a real MCPServer running in your project, the last step is to read its health conditions and clean it up again.

Exercise 3: Monitor server health and remove the server

In this exercise you inspect the status conditions of your deployed MCP server, then delete it and confirm the operator cleans up after it.

  1. Check the status of all MCP servers in your project:

    oc get mcpservers -n abc123-user1

  2. Review the status conditions for your server. Replace insights-mcp-demo with your server name:

    oc describe mcpserver insights-mcp-demo -n abc123-user1

    Look for the Accepted, Available, and Verified conditions with status: True (for example, Available=True (Available)) to confirm the server is running, verified by the operator handshake, and ready to accept connections at the service address reported by oc get mcpservers.

  3. Remove the server:

    Deleting the MCPServer custom resource is destructive. The MCP Lifecycle Operator automatically cleans up the associated Deployment, Service, and other managed resources, and the server is no longer available to your agents.

    		 
    oc delete mcpserver insights-mcp-demo -n abc123-user1

Verify

Confirm no MCPServer resources remain in your project:

oc get mcpservers -n abc123-user1

The expected output is No resources found in abc123-user1 namespace. — an empty MCPServer list confirms the operator cleaned up the workload.

Module summary

What you accomplished:

  • Enabled the MCP Lifecycle Operator and the mcpCatalog dashboard feature flag on the cluster

  • Read the support-tier badges (Red Hat supported, Partner supported, Community supported) on MCP server cards in the AI Hub MCP Catalog

  • Deployed com.redhat/insights-mcp-server from the catalog gateway-free, watched it reach Available, and verified its ACCEPTED/AVAILABLE/VERIFIED conditions from the CLI

Key takeaways:

  • The support tier tells you who stands behind each catalog server: Red Hat fully, the technology partner, or best-effort from the community

  • Most catalog servers — 8 of 9, all with deployment mode Local to cluster — deploy without an MCP gateway; servers that require one keep their Deploy MCP server button disabled until an administrator provides a gateway

  • The mcplifecycleoperator component must be set to Managed in the DataScienceCluster for the catalog’s deploy action to be available; this workshop cluster ships the component already enabled

  • The deploy dialog prefills YAML from the catalog metadata; server images that default to stdio transport need config.arguments (here http --host 0.0.0.0) to serve HTTP inside the cluster

  • The operator turns catalog cards into MCPServer custom resources and provisions the Deployment and Service for you

Next steps:

To upgrade or scale a deployed server, or to route MCP traffic through the governed entry point of the MCP Gateway Operator, see the Working with the MCP catalog chapter in the RHOAI 3.6 documentation linked from the conclusion.
