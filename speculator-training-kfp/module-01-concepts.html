Module 01: Core Concepts

In this module you will learn what speculative decoding is and what a speculator model is, how RHOAI 3.6 stages Kubeflow Pipelines (Phase 2 KFP) per project, how Kubeflow Trainer executes the training work, and which tooling the Red Hat AI model-optimization image ships.

Learning objectives:

  • Explain speculative decoding, speculator (draft) models, and how vLLM serves them

  • Describe the Phase 2 KFP stack: DataSciencePipelinesApplication → DSPO → KFP v2 on Argo Workflows, all inside your project

  • Map the pipeline stages to the two shipped ClusterTrainingRuntimes and their invocation contracts

  • Use the speculators CLI surface the way the pipeline stages invoke it

Every factual claim in this module is bound to an evidence capture from this workshop’s build run (capture ids are listed inline, e.g. log-6a2367b3a89d70b2).

Exercise 1: Speculative decoding and speculator models

Speculative decoding accelerates LLM inference by letting a draft model — the speculator — propose several tokens at once, which the large verifier model then accepts or rejects in a single forward pass. When the speculator is well matched to the verifier, accepted lengths of 2–4 tokens per step are common, cutting latency without changing the output distribution.

  1. A speculator model is a small transformer trained on the verifier’s hidden states to predict the verifier’s next tokens. The EAGLE3 method (the one the Red Hat recipes use) trains the speculator against the verifier’s intermediate-layer hidden states, which is why the training pipeline extracts and stores those states as hs_<i>.safetensors files (upstream tutorial, capture log-c275d3393b7734f4).

  2. Red Hat AI publishes ready-made speculators on Hugging Face — the RedHatAI/speculator-models collection includes Qwen3-8B-speculator.eagle3, Llama-3.1-8B-Instruct-speculator.eagle3, Llama-3.3-70B-Instruct-speculator.eagle3, gpt-oss-20b-speculator.eagle3, and others (verified via the Hugging Face API, capture log-c275d3393b7734f4).

  3. Serving is plain vLLM: the checkpoint’s config.json carries a speculators_config that vLLM reads to enable speculative decoding, so vllm serve ./checkpoints/checkpoint_best — or vllm serve RedHatAI/Qwen3-8B-speculator.eagle3 — is all it takes (capture log-c275d3393b7734f4).

Verify

You can answer, without looking back: why does the training pipeline need the verifier’s hidden states? (Because the EAGLE3 speculator learns to map the verifier’s intermediate-layer hidden states to next-token predictions; the pipeline’s extraction stage exists to produce and store exactly those states.)

Exercise 2: Phase 2 KFP — pipelines in your project

In 3.6 the pipelines experience is "Phase 2": Kubeflow Pipelines v2 on Argo Workflows, staged per data science project by a pipeline server. The dashboard’s Configure a pipeline server flow creates a namespaced DataSciencePipelinesApplication (kind DSPA, group datasciencepipelinesapplications.opendatahub.io, name dspa); the data-science-pipelines-operator (DSPO) then reconciles the full KFP stack into the project namespace (verified against the dashboard frontend bundle and live reconciliation, captures command-75fc00f5951bc1f4, screenshot-0c975ceaf561e1f8).

  1. Inspect the pipeline server in ai-tenants:

oc get dspa dspa -n ai-tenants

  1. List the stack DSPO reconciled — every component is a plain pod in your project:

oc get pods -n ai-tenants | grep -E "ds-pipeline|mariadb"

You should see ds-pipeline-dspa (the KFP v2 API server, 3/3), ds-pipeline-metadata-grpc + envoy (ML Metadata), persistenceagent, scheduledworkflow, workflow-controller (the Argo Workflows controllers that execute pipeline runs), and mariadb-dspa (the pipeline store).

  1. The KFP v2 API is reachable in-cluster at http://ds-pipeline-dspa.ai-tenants.svc.cluster.local:8888 (https on 8443, fronted by a kube-rbac-proxy). Pipeline runs surface in the project as Argo Workflows:

oc get workflows.argoproj.io -n ai-tenants

  1. On the dashboard, Pipelines → Pipeline definitions for ai-tenants lists the uploaded pipeline definitions; Runs, Artifacts, and Executions pages are backed by the same API and MLMD store.

Verify

ds-pipeline-dspa is 3/3 Running in ai-tenants, and the Pipeline definitions page of the project does not show the Configure a pipeline server empty state. The BEFORE/AFTER of that page is captured in this workshop’s evidence (screenshot-0f289d26 before, screenshot-0c975ceaf561e1f8 after).

The pipeline server is additive demo-runtime state in ai-tenants. It is the same object the dashboard’s configure modal creates — this workshop stages it from deploy/20-pipeline-server-dspa.yaml so that every cluster change corresponds to a tree file. No GitOps-owned resource is touched.

Exercise 3: Kubeflow Trainer and the shipped runtimes

The pipeline’s heavy stages are training workloads. RHOAI 3.6 installs Kubeflow Trainer with two ClusterTrainingRuntime objects purpose-built for speculator training (both live-fetched during the workshop build, capture command-c6d453656cfb37a6):

ClusterTrainingRuntime Role Invocation contract

speculator-model-opt-cuda

The trainer. A torch MLPolicy runtime wrapping the model-optimization image; the container command is the torchrun -m speculators.train module form.

Step args = speculators train flags (--verifier-name-or-path, --data-path, --save-path, --draft-vocab-size, --epochs, --total-seq-len, --hidden-states-path/--hidden-states-backend file for offline mode, --vllm-endpoint/--on-missing generate for online mode)

vllm-extract-cuda

The extraction server. Its vllm-sidecar initContainer runs vLLM configured for hidden-states extraction — the ExampleHiddenStatesConnector kv-producer serving the verifier with method extract_hidden_states on :8234.

Env knobs: SPECULATOR_VERIFIER_MODEL, SPECULATOR_HS_PATH (/data/hidden_states), SPECULATOR_TARGET_LAYER_IDS, SPECULATOR_VLLM_GPU_COUNT, SPECULATOR_GPU_MEM_UTIL; shared storage mounted at /data (capture command-c6d453656cfb37a6)

  1. See both runtimes as the platform installed them:

oc get clustertrainingruntimes speculator-model-opt-cuda vllm-extract-cuda

  1. TrainJobs are the workload objects the dashboard’s Jobs page shows under "TrainJobs". This workshop’s pipeline/trainjobs/ directory stages the standalone Trainer path with a shared /data PVC (additive demo state — see the project’s current jobs):

oc get trainjobs -n ai-tenants

Verify

You can name, without looking back, which runtime executes speculators train and which one serves the vLLM hidden-states extraction endpoint on :8234. (Trainer: speculator-model-opt-cuda. Extraction: vllm-extract-cuda.)

Exercise 4: The model-optimization tooling — the speculators CLI

The training image registry.redhat.io/rhaii/model-opt-cuda-rhel9 ships the Red Hat vendored vllm-project/speculators CLI (version 0.8.1 at 3.6) alongside llmcompressor, compressed-tensors, auto-round, and torchrun/accelerate in one environment (image inspection, capture log-b7ad187694b72412). There is no model-opt binary — the tooling is the speculators CLI (capture log-6a2367b3a89d70b2).

The speculators pipeline command group defines the stages this workshop’s pipeline wraps:

Command What it does

speculators prepare-data

Tokenize the dataset, build loss/assistant masks, emit output/{data-*.arrow, dataset_info.json, state.json, token_freq.pt} — runs on CPU.

speculators generate-offline-data

Pull hidden states from a vLLM extraction endpoint (--endpoint) into hs_<i>.safetensors files (--max-samples, --concurrency, --validate-outputs; multi-node split with --world-size/--rank; backends file or mooncake).

speculators regenerate-responses

Optional data-regeneration step against a serving endpoint.

speculators train

The training stage (executed as torchrun -m speculators.train): --verifier-name-or-path --data-path --save-path --draft-vocab-size --epochs --total-seq-len; offline mode adds --hidden-states-path/--hidden-states-backend file; online mode adds --vllm-endpoint --on-missing generate. Also supports --config run.yaml, --dump-config, and smoke paths --dry-run / --max-steps.

speculators stitch-mtp / speculators convert

Post-training conversions (MTP stitching, checkpoint conversion).

  1. The image tag matters — the shipped runtimes pin a digest that the registry does not serve (verified node-side and against the registry v2 API, captures command-c6d453656cfb37a6, log-199e4a8563625b06), so this workshop’s pipeline pins the verified tag:

oc get clustertrainingruntime speculator-model-opt-cuda -o jsonpath='{.spec.template.spec.replicatedJobs[0].template.spec.template.spec.containers[0].image}' | head -c 120; echo
The digest sha256:eeddf028… returns 404 MANIFEST_UNKNOWN from registry.redhat.io even though the repository itself is accessible; tag 3.6.0 resolves and pulls (verified: an 11 GB one-shot pod ran to completion on it). Module 03 documents the fix.

Verify

The image field of the shipped runtime shows the pinned digest, and you can explain why this workshop’s pipeline overrides it with :3.6.0. (Because the digest is not served by the registry — a TrainJob or pipeline step using it verbatim sits in ImagePullBackOff regardless of GPUs.)
