Module 03: Advanced — Model Registry + Troubleshooting

In this module you learn the optional Model Registry path for the trained speculator, the GPU-vs-CPU profile guidance, and the failure patterns the RHAISTRAT-2546 build surfaced in the workshop factory — each with a diagnosis, a workaround, and an escalation rule.

Learning objectives:

  • Decide whether and how to register a trained speculator in a model registry

  • Choose the right pipeline profile for your cluster’s GPU capacity

  • Diagnose the image-digest, scheduling, CUDA-startup, and Create-run-form failures this build verified, plus the ModelRegistry namespace constraint

  • Choose the right escalation severity with ask_operator

Exercise 1: OPTIONAL — register the trained speculator in a model registry {#model-registry}

The core demo ends at the pipeline artifacts: the trained speculator checkpoint and the run’s MLMD artifacts live in the DSPA object store, fully inspectable from the dashboard’s Artifacts page. Registration in a Model Registry is an optional extension — useful when other teams should discover and reuse your speculator.

  1. A Model Registry is itself an instance you create first. This feature stages one additively with deploy/40-modelregistry.yaml (an optional manifest — not applied by the core flow). NOTE the platform constraint, verified live during this workshop’s build: the model-registry admission webhook REJECTS instances outside the dedicated namespace (namespace must be rhoai-model-registries) — a per-project registry in ai-tenants is impossible, so the manifest targets rhoai-model-registries with a distinct name:

oc apply -f features/distributed-training/speculator-training-kfp/deploy/40-modelregistry.yaml

  1. Wait for the registry to become available and read its REST route (the reference build reached Available=True in ~75 seconds, with the operator-managed PostgreSQL and registry pods Running alongside):

oc get modelregistry speculator-model-registry -n rhoai-model-registries
oc get route -n rhoai-model-registries speculator-model-registry-https

The model-registry operator creates the registry REST/GRPC services, an operator-managed PostgreSQL deployment, and the reencrypt route (verified live: Available=True, pods 2/2 + 1/1, REST endpoint answering 401 unauthenticated — RBAC-protected as expected).

  1. Register the trained speculator either from the dashboard (Model registry → your registry → Register model) or through the registry REST API (/api/model_registry/v1alpha1/registered_models → model version → artifact). Point the artifact at the checkpoint object in the pipeline’s object store (the run’s checkpoints/ path from the VALIDATE step).

A shared registry instance (model-registry-demo in rhoai-model-registries) exists on some workshop clusters, owned by a different feature’s demo. This workshop stages its own registry with a distinct name — additive only, no shared mutable state — because the platform requires registries to live in that namespace.

Verify

The modelregistry object reports Available, the route resolves, and the dashboard’s Model Registry page lists your registry. If you skip this step, the core demo is still complete — registration is explicitly optional.

Exercise 3: Troubleshooting patterns

Pattern 1: image digest not served {#image-digest}

Symptom: TrainJob or pipeline pod stuck in ImagePullBackOff — reading manifest sha256:eeddf028…​ : manifest unknown — even on clusters with GPUs.

  1. Diagnose:

oc get pod -n ai-tenants | grep -E "ImagePullBackOff|ErrImagePull"

  1. Root cause: both shipped ClusterTrainingRuntimes pin digest sha256:eeddf028…, which registry.redhat.io does not serve (404 MANIFEST_UNKNOWN, verified node-side and via the registry v2 API with the cluster pull secret — captures command-c6d453656cfb37a6, log-199e4a8563625b06). The repository itself is accessible; tag 3.6.0 resolves and pulls (amd64 digest sha256:85f9eb6fef5b…).

  2. Fix: pin the verified tag — this workshop’s pipeline and TrainJob manifests already do:

oc get trainjob  -n ai-tenants -o jsonpath='{.spec.trainer.image}'; echo

Expected: registry.redhat.io/rhaii/model-opt-cuda-rhel9:3.6.0. NOTE: the TrainJob controller re-asserts the runtime’s own image on pods — the fix that sticks is spec.trainer.image on the TrainJob, not a container-image patch.

Pattern 2: GPU unschedulable (0-GPU cluster) {#gpu-unschedulable}

Symptom: extraction/training pods stay Pending with FailedScheduling: 0/3 nodes are available: 3 Insufficient nvidia.com/gpu.

  1. Diagnose — this is the honest state on a cluster without GPU nodes:

oc get pod -n ai-tenants -o custom-columns='NAME:.metadata.name,STATUS:.status.phase' | grep speculator
oc get events -n ai-tenants --field-selector reason=FailedScheduling | tail -5

  1. Interpret: Insufficient nvidia.com/gpu is a capacity fact, not a bug. The reference build deliberately leaves this state captured (the extraction TrainJob Pending in ai-tenants) as the honest demo evidence.

  2. Remediate only by adding capacity: GPU nodes are a cluster resource request, which goes to the operator with severity high (Exercise 4). Use the tiny-cpu profile meanwhile — its data-preparation stage completes on CPU.

Pattern 3: CUDA required at startup (no CPU training path) {#cuda-required}

Symptom: the training stage fails within seconds of starting — RuntimeError: No CUDA GPUs are available — before any config, data, or model work.

  1. Read the failure directly:

oc logs -n ai-tenants  --all-containers --tail=50 | grep -E "RuntimeError|torch._C"

  1. Root cause (verified live by running the standalone TrainJob on the 0-GPU cluster, capture log-26d8943fa7461404): speculators 0.8.1’s speculators/train/distributed.py maybe_setup_distributed() calls torch.accelerator.set_device_index() → torch._C._cuda_init() first. The documented --dry-run / --max-steps smoke paths do NOT avoid it.

  2. Consequence: there is no CPU training path in this tooling version. The tiny-cpu profile keeps the stage on purpose so the demo shows the real requirement — a fast, cheap, honest failure. Do not "fix" it by removing the stage; the dashboard and the content document it.

Pattern 4: DSPA apiVersion skew {#dspa-apiversion}

Symptom: applying the pipeline-server manifest copied from the dashboard bundle fails with no matches for kind "DataSciencePipelinesApplication".

  1. Root cause: the 3.6 dashboard frontend still references apiVersion v1alpha1, but the cluster CRD serves v1 only (verified by CRD query and by the honest failed apply in the reference build, capture command-75fc00f5951bc1f4).

  2. Fix: use apiVersion: datasciencepipelinesapplications.opendatahub.io/v1 (as deploy/20-pipeline-server-dspa.yaml does).

Pattern 5: runtimePatches nesting + snapshot ConfigMap race {#trainjob-gotchas}

Symptom 1: a TrainJob runtimePatches entry is silently ignored.

Cause: pod-spec patches live at trainingRuntimeSpec.template.spec.replicatedJobs[].template.spec.template.spec (Job → Pod double template); patching one level up is stripped. Allowed container keys: env, resources, volumeMounts, securityContext — no image key (verified live, capture log-26d8943fa7461404).

Symptom 2: deleting + recreating a TrainJob in quick succession fails with invalid runtime snapshot: a snapshot configmap exists but is owned by another object.

Fix: remove the orphaned <name>-runtime-snapshot ConfigMap before recreating.

Pattern 6: ModelRegistry namespace constraint {#mr-namespace}

Symptom: applying a ModelRegistry manifest into a data science project fails with admission webhook "vmodelregistry.opendatahub.io" denied the request: …​ metadata.namespace: Invalid value: "<project>": namespace must be rhoai-model-registries.

  1. Root cause (verified live during this workshop’s build — the honest failed apply is in the capture log): the platform constrains ModelRegistry instances to the dedicated rhoai-model-registries namespace. A per-project registry is not possible.

  2. Fix: create the registry in rhoai-model-registries with a distinct name — exactly what deploy/40-modelregistry.yaml does; it reconciled to Available=True in ~75 seconds on this cluster.

Pattern 7: KFP caching silently skips executors

Symptom: a re-run of identical parameters completes instantly and the run graph shows tasks skipped as cached — no executor ran.

Cause/fix: task caching reuses identical parameter runs. This workshop’s pipeline disables caching on every stage on purpose so a demo run executes its steps for real (observed live on this cluster family during the reference build).

Pattern 8: Create-run form coerces the string parameter lr {#lr-coercion}

Symptom: submitting the dashboard Create run form fails with Failed to generate the ExecutionSpec: invalid pipeline job inputs: Invalid input error: input parameter lr requires type string, but the input parameter is not of string value type.

  1. Root cause (verified live in the reference build, captures screenshot-7de767e98f0a2a97, command-bbce9f401ba55e9a): the pipeline DSL declares lr: str = '1e-4', but the form pre-fills the field with the coerced decimal 0.0001 and submits it as a JSON number — the KFP v2beta1 API rejects the run because the declared type is string.

  2. Fix: retype the lr field with the literal string 1e-4 before submitting — the run then creates normally and the API shows parameters.lr == "1e-4" as a string (captures screenshot-8e43edf76ff6989b, command-bbce9f401ba55e9a). A one-keystroke workaround; runs created via the API/SDK are unaffected.

Verify

Given a symptom, you can name the pattern and its fix from memory: image digest not served (pin :3.6.0), GPU unschedulable (capacity ask, high severity), CUDA-required startup (no CPU training path — tiny-cpu documents it honestly), DSPA apiVersion skew (use v1), runtimePatches nesting + snapshot ConfigMap race (patch the double template; remove the orphaned snapshot ConfigMap), the ModelRegistry namespace constraint (rhoai-model-registries only), KFP caching (disabled on purpose in this pipeline), and the Create-run lr coercion (retype the value as the literal string 1e-4).

Exercise 4: Operator escalation with ask_operator

Every pattern above has an escalation, and the factory has exactly one channel: the ask_operator MCP tool.

  1. Pick the severity honestly:

Situation Severity

Cluster capacity or resource requests (GPU nodes, scale-ups, node pools)

high — always, no exceptions. This build’s GPU ask (Q162) is the model.

Ordinary blockers (missing credentials, unclear decision, stale state)

normal — the planner routes around them

  1. Write the ask with the evidence attached: the pattern name, the exact observed state, the captures that prove it, and the decision you need.

  2. Route capacity questions only through the tool — never by editing cluster resources out of band, and never by patching GitOps-owned platform objects with oc (cluster-level platform changes belong to the assets repo cluster/ directory and are committed by the engine).

Verify

Given a new failure, you can classify it: worker-fixable, planner-routable, or operator-ask — and for operator-asks you can name the severity and the decision required.
