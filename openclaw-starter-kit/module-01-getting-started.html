Module 01: Getting Started

In this module you will take a guided tour of the OpenClaw agent starter kit — a Developer Preview feature of Red Hat OpenShift AI 3.5 that lets you deploy and manage OpenClaw, an open-source general-purpose agent, on OpenShift AI from validated Kustomize manifests and an automated installer. Because this is a Developer Preview, this module is a guided tour of what the kit provides and how it fits together, not a deployment walkthrough.

Learning objectives:

  • Explain what OpenClaw is and what the starter kit provides in RHOAI 3.5

  • Compare the two deployment options: validated Kustomize manifests and the automated installer

  • Describe how the agent connects to self-hosted models through vLLM via the OGX gateway

This feature is a Developer Preview. It is provided as-is with no support and no guarantee of future availability, so focus on the concepts in this tour rather than on memorizing specific commands — the deployment interface may change between releases.

Exercise 1: What the starter kit provides

OpenClaw is a general-purpose agent, and the starter kit is Red Hat’s validated path for running it on OpenShift AI. Per the RHOAI 3.5 release notes, the kit includes the following capabilities:

  • Deployment: deploy OpenClaw by using validated Kustomize manifests or the automated OpenClaw installer — no bespoke image builds or hand-written YAML required.

  • Model connection: connect to self-hosted models through vLLM by using the OGX inference gateway with an OpenAI-compatible API.

  • Observability: capture model calls, tool executions, and context assembly spans in MLflow by using native OpenTelemetry tracing through the diagnostics-otel plugin.

  • Access control: enforce browser-based access control backed by OpenShift role-based access control (RBAC) through OAuth proxy integration.

  • Persistence: workspace storage is maintained across pod restarts.

  • Validation: validate your environment by using an included model compatibility matrix and troubleshooting guide.

  • Security: workloads run securely under the OpenShift restricted-v2 security context constraint (SCC).

    1. Confirm that you are still connected to your workshop environment and working in your own project:

oc whoami && oc project

The first line shows your workshop username and the second shows your project from Getting Connected. Everything in this workshop happens in your own namespace, which is exactly the kind of boundary the restricted-v2 SCC enforces for the agent itself.

OpenClaw established the agent onboarding pattern that other starter kits on OpenShift AI follow. Per the 3.5 release notes, OpenCode is the first coding agent validated to follow the pattern established by OpenClaw, so what you learn here generalizes to the wider agent starter kit family.

Exercise 2: Deploy the OpenClaw agent

The kit ships with two deployment options. Both converge on the same validated deployment — choose based on how you want to manage the definitions:

Deployment option What it does When to choose it

Validated Kustomize manifests

Declarative manifests you apply to your cluster and can inspect or customize

You want reviewable, version-controlled deployment definitions

Automated OpenClaw installer

An automated installer that manages runtime concerns and optimizes workspace persistence

You want the fastest path to a running OpenClaw instance

  1. Before deploying, confirm your working project is the current namespace:

oc project

  1. The agent invokes tools through the model, so tool calling must be enabled on the model server. Check whether the --enable-auto-tool-choice and --tool-call-parser arguments are set on the model deployment:

oc get inferenceservice qwen25-05b -n abc123-user1 \
  -o jsonpath='{.spec.predictor.model.args}'
If the arguments are missing, patch the model server. The --tool-call-parser value depends on the model family — hermes for Qwen2.5 models: 
oc patch inferenceservice qwen25-05b -n abc123-user1 --type merge \
  -p '{"spec":{"predictor":{"model":{"args":["--dtype=bfloat16","--max-model-len=8192","--enable-auto-tool-choice","--tool-call-parser=hermes"]}}}}'

The model server rolls out with the new arguments. Wait for the deployment to report READY 1/1 before continuing.

  1. The model endpoint requires token authentication. Mint a long-lived token for the model-caller ServiceAccount and store it in a Secret:

cat <<'EOF' | oc apply -f - -n abc123-user1
apiVersion: v1
kind: Secret
metadata:
  name: qwen25-05b-caller-token
  annotations:
    kubernetes.io/service-account.name: qwen25-05b-caller
type: kubernetes.io/service-account-token
EOF

Option A: deploy from the validated Kustomize manifests

The starter kit deploys two components: the OpenClaw agent backend (which talks the OpenAI-compatible protocol) and the agent UI (browser access through an OAuth proxy backed by OpenShift RBAC). The backend manifest wires the agent to the model endpoint through a Secret:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: openclaw-agent-be
  labels:
    app: openclaw-agent-be
    app.kubernetes.io/part-of: openclaw
spec:
  replicas: 1
  selector:
    matchLabels:
      app: openclaw-agent-be
  template:
    metadata:
      labels:
        app: openclaw-agent-be
    spec:
      containers:
        - name: openclaw-agent-be
          image: quay.io/rcarrata/agentic-app-be:v3 (1)
          ports:
            - containerPort: 8080
          env:
            - name: API_URL (2)
              valueFrom:
                secretKeyRef:
                  name: openclaw-be-secret
                  key: API_URL
            - name: API_KEY (3)
              valueFrom:
                secretKeyRef:
                  name: openclaw-be-secret
                  key: API_KEY
            - name: MODEL_NAME (4)
              valueFrom:
                secretKeyRef:
                  name: openclaw-be-secret
                  key: MODEL_NAME
1 image — the validated OpenClaw agent backend image; no bespoke image builds required.
2 API_URL — the OpenAI-compatible base URL of your OGX inference gateway.
3 API_KEY — the API key for the gateway. Leave empty for gateways without auth.
4 MODEL_NAME — the model ID the agent requests on every call.

  1. Create the Secret that wires the agent to your OGX gateway. The gateway exposes an OpenAI-compatible API on port 8321 — note the URL has no /v1 suffix, because the agent appends it. The API key is the model-caller token from the previous step, which the OGX gateway forwards to the token-authenticated model server:

 
OGX_TOKEN=$(oc get secret qwen25-05b-caller-token -n abc123-user1 \
  -o jsonpath='{.data.token}' | base64 -d)
oc create secret generic openclaw-be-secret -n abc123-user1 \
  --from-literal=API_URL="http://lsd-genai-playground-service.abc123-user1.svc.cluster.local:8321" \
  --from-literal=API_KEY="${OGX_TOKEN}" \
  --from-literal=MODEL_NAME="vllm-inference-1/qwen25-05b"

  1. Apply the validated Kustomize manifests for both components:

oc apply -k https://github.com/redhat-ai-dev/agentic-examples/agentic-apps/agentic-app-langgraph/deploy-demo -n abc123-user1

  1. Confirm both deployments roll out:

oc get deployments -n abc123-user1

Verify

Both the agent backend and the agent UI deployments show READY 1/1, and the openclaw-be-secret carries your OGX gateway URL:

oc get deployment openclaw-agent-be -n abc123-user1 -o jsonpath='{.status.readyReplicas}'

Expected output is 1.

Exercise 3: Verify the running agent

  1. Open the agent UI route in a browser:

oc get route -n abc123-user1

The UI lists the API status, the model in use, and the agent’s enabled tools. When you open the route for the first time, log in with OpenShift and approve the agentic-sa service account — the OAuth proxy enforces this.

  1. Send a prompt through the agent chat. The agent forwards the request to the OGX gateway, which routes it to the self-hosted vLLM model, and the response streams back into the chat UI.

Verify

The agent responds in the chat UI with a completion from the self-hosted model, and the backend logs show the upstream model call:

oc logs -n abc123-user1 deploy/openclaw-agent-be --tail=5

On the model side, the kit connects OpenClaw to self-hosted models through vLLM by using the OGX inference gateway with an OpenAI-compatible API. Notice what this implies: the agent talks the OpenAI-compatible protocol, and OGX fronts your vLLM servers, so you can run OpenClaw against models you host in your own cluster without any external model subscription.
