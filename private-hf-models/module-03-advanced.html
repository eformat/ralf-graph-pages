Module 03: Advanced — Troubleshooting patterns

In this module you learn the four failure patterns the RHAISTRAT-1258 pilot surfaced in the workshop factory, how to diagnose each from the CLI, and when to escalate to the operator. These are recurring patterns, not one-off incidents — each one has a name (GAP-1 through GAP-4), a diagnosis, a workaround, and an escalation rule.

Learning objectives:

  • Diagnose the DSC TrustyAI patch loop and its type-skew root cause

  • Recognize model-catalog scale-to-zero and its RBAC/escalation path

  • Identify engine write-pipe constraint failures from SQLSTATE 23514 ck_node_state

  • Choose the right escalation severity with ask_operator

Exercise 1: DSC TrustyAI patch loop {#trustyai-patch-loop}

Pattern: the DataScienceCluster reports False/NotReady while the dashboard and the TrustyAI custom resource themselves look healthy.

  1. Reproduce the symptom:

oc get dsc default-dsc
oc get trustyai -A

The DSC shows False / NotReady; the TrustyAI CR shows Ready.

  1. Find the loop in the operator logs — the controller retries the component apply roughly every two minutes:

oc logs -n redhat-ods-operator deploy/rhods-operator --tail=200 | grep -i trustyai | tail -10

  1. The root cause is a type skew: the DSC spec carries string enum values for eval.lmeval.permitCodeExecution (for example "deny"), while the controller writes a boolean into the TrustyAI CR field — the apply fails with expected string, got false — the spec never reconciles, the DSC status stays False, and the cycle repeats.

  2. The workaround is to fix the spec values so the controller’s write matches the CR schema. The platform remains functional meanwhile — the DSC status is the symptom, not the outage.

The DSC is not ArgoCD-managed in this environment, so there is no GitOps revert path — changes go through the spec directly, and the fix-vs-suppress decision belongs to the platform owner (operator question Q156).

Verify

You can distinguish the two sides of the skew — the DSC spec value and the value the controller writes into the TrustyAI CR — and you know the platform is usable while the loop continues.

Exercise 2: model-catalog scale-to-zero {#scale-to-zero}

Pattern: the model-catalog deployment sits at 0/0 READY with its database fine — every private-model validation gates on it.

  1. Diagnose the state:

oc get deploy -n rhoai-model-registries model-catalog -o jsonpath='{.spec.replicas}{"\t"}{.status.readyReplicas}{"\n"}'
oc get pods -n rhoai-model-registries

spec.replicas=0 with model-catalog-postgres at 1/1 is the scale-to-zero pattern: the metadata database is healthy, the API tier is scaled down.

  1. Understand the constraint before reaching for oc scale: the deployment is owned by the Catalog CR (aihub.opendatahub.io/v1alpha1, name catalog, owned by the AIHub component), and the aihub-controller reconciles it every 15 seconds. Scale-down to zero is the operator’s containment mode while the Catalog activation is Failed — the CRD says so explicitly ("Deployment scale-down is temporary containment", pending RHOAIENG-97414). A manual oc scale (or patch of spec.replicas) succeeds against the API server and is reverted within seconds — no RBAC grant can win that race.

  2. Read the actual root cause from the CR before touching anything:

oc get catalog catalog -n rhoai-model-registries -o jsonpath='{.status.activation.state}{"\t"}{.status.activation.reason}{"\n"}'

Failed + DataImageInitializationFailed means the operator contained the workload after a failed data-image initialization — the replica state is a symptom, not the disease.

  1. The working remediation is the one the CR itself prints in its status ("Correct spec.catalogDataImageStream or spec.benchmarkDataImageStream and retry the selected images"): pin the digest the operator already resolved and imported successfully. That is a real spec change (generation bump) but semantically the same images, so the controller re-runs activation and, on success, scales the deployment up itself. The full runbook lives in deploy/31-catalog-activation-retry.yaml in this feature’s tree. Re-apply the HF credential env afterwards (deploy/30-model-catalog-hf-env.yaml) — the operator strips custom env on every activation attempt.

  2. Operator escalation remains the fallback when the activation retry fails, or when the fix belongs to the platform owner: scaling the catalog tier is a cluster resource request, so it goes to the operator with severity high (see Exercise 4). The pilot’s ask is logged as Q154.

  3. Until the scale-up lands, downstream steps record honest blocked states with captures of the probe output — the demo flow completes with a blocked verdict rather than a fabricated pass.

Verify

You can read the replica state, explain that spec.replicas is operator-owned (containment while the Catalog activation is Failed), and name both remedies in the right order: the Catalog activation retry (worker-grade, reversible, makes the operator scale up itself) and the operator escalation.

Exercise 3: Engine write-pipe constraint failures {#write-pipe}

Pattern: the engine’s MCP write-back tools fail on every insert with SQLSTATE 23514 ck_node_state on exploration_nodes — the evidence pipe degrades to capture-only.

  1. Recognize the signature from the tool error:

Error: insert into exploration_nodes ... SQLSTATE 23514 ck_node_state

23514 is a PostgreSQL check-constraint violation: the node state the insert path passes does not satisfy the ck_node_state constraint on the exploration_nodes table.

  1. Narrow the blast radius by probing the tools individually. During the pilot, record_fact recovered after an engine restart while add_hint kept failing — the constraint violation lives in the hint-insert path only, which narrowed the fix to one code path.

  2. Work with the degraded pipe:

    • submit_capture keeps working — evidence continues to accumulate even when fact writes fail.

    • Retry record_fact after a restart; the fact then cites the capture captured during the outage window.

    • The engine fix is Go code: per the factory charter it is queued as a commit and a task for the operator (Q153), never auto-edited on-cluster.

Verify

You can read the constraint name out of the error, map it to the failing insert path, and describe which tools stay usable in the degraded state.

Exercise 4: Operator escalation with ask_operator

Every pattern above has an escalation, and the factory has exactly one channel: the ask_operator MCP tool, which queues a question at /api/operator-questions and notifies the operator.

  1. Pick the severity honestly:

Situation Severity

Cluster capacity or resource requests (scale-ups, node pools, GPU requests)

high — always, no exceptions

Ordinary blockers (missing credentials, unclear decision, stale state)

normal — the planner routes around them

  1. Write the ask with the evidence attached: the pattern name (GAP-2 …), the exact observed state, the captures that prove it, and the decision you need. The pilot’s four asks are the model — Q153 (engine fix), Q154 (scale model-catalog 0→>=1), Q155 (real token vs placeholder contract), Q156 (TrustyAI type-skew owner decision).

  2. Route capacity questions only through the tool — never by editing cluster resources out of band, and never by assuming the operator is watching the same graph you are.

Verify

Given a new failure, you can classify it: worker-fixable, planner-routable, or operator-ask — and for operator-asks you can name the severity and the decision required.

Module summary

What you accomplished:

  • Diagnosed the TrustyAI patch loop, the catalog scale-to-zero, and the write-pipe constraint failures from live cluster and engine evidence

  • Mapped each pattern to its constraint — spec type skew, worker RBAC, and check-constraint validation — and its workaround

  • Classified escalations by severity and routed the capacity ones through ask_operator

Key takeaways:

  • A red DSC status with healthy components is a diagnosis, not necessarily an outage — read the loop before paging anyone

  • Blocked is an honest outcome: record it with captures and escalate instead of patching what your RBAC forbids

  • Cluster capacity requests always travel as high severity through the operator question queue
