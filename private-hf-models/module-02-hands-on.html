Module 02: Hands-on — the Mode 4 demo flow

In this module you drive the kitchensink Mode 4 demo flow end to end for the RHAISTRAT-1258 feature: one step per section, each with concrete commands and the evidence capture expected at that step. Mode 4 is the workshop factory’s locked recipe for producing feature demos as self-correcting units — every step leaves evidence, and every claim in the final content is bound to a capture.

Learning objectives:

  • Stage the RHAISTRAT-1258 environment and verify it is demo-ready

  • Record evidence with capture discipline at every step of the flow

  • Author the catalog entry and feature YAML carrying the RHAISTRAT-1258 slug

  • Build the change: apply the staging manifests, the features tree, and the matrix

  • Validate the flow: backend enumeration plus the UI showing private models

  • Integrate: files land in the assets repo, pages publish, the daily digest records the run

The six-point demo contract

Step Goal Evidence captured

ENV

Factory and staging environments up; model-catalog READY >= 1; token Secret injected

command/log — resource states

RECORD

Capture-first discipline at every subsequent step

screenshot/video/ffprobe/log — per-step captures

AUTHOR

Catalog entry + feature YAML with the RHAISTRAT-1258 slug

log — file tree of the authored files

BUILD

Manifests applied; features tree and matrix updated

command — apply + verify output

VALIDATE

Backend enumerates private models; UI shows them; platform status noted

command + screenshot — enumeration and UI

INTEGRATE

Files land in the assets repo; pages publish; digest recorded

log — commit/page-tree proof

The flow is idempotent: re-running any step against an already-satisfied state is a no-op that still records evidence.

Exercise 1: ENV — stage and verify the environment

The environment has two layers: the factory (the engine and worker that record evidence) and the staging environment (the demo namespace with the workbench and the catalog changes).

  1. Confirm the factory namespace is healthy — engine, worker, and its PostgreSQL backend running:

oc get pods -n ralf-graph

  1. Confirm the RHAISTRAT-1258 staging namespace is up — the workbench notebook pod Running and its PVC Bound:

oc get pods,pvc -n private-hf-models-demo

  1. The non-negotiable gate: the model-catalog backend must be READY >= 1. Record the exact replica state:

oc get deploy -n rhoai-model-registries model-catalog -o jsonpath='{.spec.replicas}{"\t"}{.status.readyReplicas}{"\n"}'

  1. Confirm the token Secret is injected (checksum only — never print the value):

oc get secret hf-token -n private-hf-models-demo -o jsonpath='{.data.token}' | base64 -d | sha256sum | cut -c1-12

Capture (ENV)

Submit one capture for the environment state — kind log — containing the four command outputs above with a UTC timestamp header:

# date -u
# factory / staging / model-catalog / token-shape
<output of steps 1-4>

If model-catalog is 0/0, the VALIDATE step later will block: record the ENV capture anyway and continue — Module 03 explains the scale-to-zero pattern and the operator escalation path.

Verify

model-catalog READY >= 1, workbench pod Running, PVC Bound, and the token Secret present. The staging namespace is additive demo state — nothing here patches a GitOps-owned resource.

Exercise 2: RECORD — capture-first discipline

Every subsequent step produces evidence before any claim is written down. The factory evidence pipe accepts captures of these kinds:

Kind Used for

screenshot

UI states (the dashboard showing private models)

video

End-to-end walkthroughs (the arcade demo recording)

frame

Single extracted frames from a recording

ffprobe

Recording format proof (resolution, duration, codec)

log

Command output bundles, page trees, digests

command

Single command + output pairs

validator

Automated check results (PSNR, session-guard, link checks)

The discipline rules:

  1. Capture before you claim. A fact without a capture ID is refused by the engine — and a claim without a fact is invisible to the graph.

  2. One step, one capture. The capture content is the raw command output or screenshot, timestamped; summaries stay one line.

  3. Never fabricate. If a step fails, capture the failure — a blocked state with honest evidence is a valid outcome; a fabricated pass is the cardinal sin.

  4. Checksums over values. Secrets are evidenced by length and SHA-256 prefix, never by printing them.

Capture (RECORD)

Practice the discipline once: submit a command capture of the catalog sources endpoint probe from Module 01, Exercise 2 (the authenticated curl returning 200).

Verify

Your capture exists and carries real content — the exact command and its output, not a description of what you saw.

Exercise 3: AUTHOR — the catalog entry and feature YAML

Author two artifacts, both from the in-tree manifests of this feature so that "every cluster change corresponds to a tree file".

  1. The catalog credential Secret — a reference, not a token (deploy/10-catalog-source-secret.yaml):

apiVersion: v1
kind: Secret
metadata:
  name: catalog-private-hf-models-apikey
  namespace: rhoai-model-registries
  labels:
    app.kubernetes.io/part-of: private-hf-models-workshop
type: Opaque
stringData:
  # Learner contract: replace the placeholder with your own fine-grained
  # READ-ONLY token (see Module 01, Exercise 4). Never commit a real token.
  apiKey: "__HF_TOKEN_CATALOG_CREDENTIAL__"

  1. The private catalog source — the private_hf_models entry (deploy/20-model-catalog-sources.yaml). The source is gated by the saved-credential reference, the allowed organization, and the include patterns:

apiVersion: v1
kind: ConfigMap
metadata:
  name: model-catalog-sources
  namespace: rhoai-model-registries
  labels:
    app.kubernetes.io/part-of: private-hf-models-workshop
data:
  sources.yaml: |
    catalogs:
      - name: Workshop Private Models
        id: private_hf_models
        type: hf
        enabled: true
        labels:
          - Workshop private models
        properties:
          # Saved-credential reference: NAME of the Secret in this namespace.
          # Never put a token value here — the catalog backend resolves the
          # credential from the Secret.
          apiKey: catalog-private-hf-models-apikey
          allowedOrganization: eformat
        includedModels:
          - rhoai-private-demo  # auto-prefixed with the org (HF search does not glob)
        excludedModels: []

  1. The feature YAML — this workshop’s Antora component descriptor carries the RHAISTRAT-1258 slug (private-hf-models, maturity GA, 3.6) in content/antora.yml, and the feature matrix gains the matching row:

# feature-matrix.yml (excerpt) — the RHAISTRAT-1258 row
- name: "Private Hugging Face models in the model catalog"
  slug: private-hf-models
  maturity: GA
  scaffolded: true
  enriched: true
  modules_estimate: 3
  description: "Retrieve PRIVATE models from Hugging Face through the model catalog"
  prerequisites: ["RHOAI 3.6 installed", "model-catalog deployment READY >= 1",
                  "Fine-grained READ-ONLY HF token"]
  version_introduced: "3.6"
  tags: [model-catalog, hugging-face, private-models]

Capture (AUTHOR)

Submit a log capture of the authored file tree:

find features/model-registry/private-hf-models -type f | sort

Verify

Every cluster object the flow will create corresponds to a file in the tree, the Secret manifests hold placeholders only, and the slug private-hf-models traces back to RHAISTRAT-1258 in the matrix.

Exercise 4: BUILD — apply the manifests

Apply the staging manifests in dependency order, verifying each step.

  1. Namespace first, then the runtime Secret, then the workbench:

oc apply -f features/model-registry/private-hf-models/deploy/00-namespace.yaml
oc apply -f features/model-registry/private-hf-models/deploy/01-hf-token-secret.yaml
oc apply -f features/model-registry/private-hf-models/deploy/02-private-models-workbench.yaml

  1. Then the catalog-side objects — credential Secret and the private source ConfigMap in rhoai-model-registries:

oc apply -f features/model-registry/private-hf-models/deploy/10-catalog-source-secret.yaml
oc apply -f features/model-registry/private-hf-models/deploy/20-model-catalog-sources.yaml

  1. Verify the merge landed — the ConfigMap data carries the private_hf_models entry:

oc get cm model-catalog-sources -n rhoai-model-registries -o jsonpath='{.data.sources\.yaml}' | grep -A2 private_hf_models

  1. Verify the workbench is consuming the injected token — its pod spec references the Secret:

oc get sts -n private-hf-models-demo private-models-workbench -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="HF_TOKEN")]}' | grep -o hf-token

Capture (BUILD)

Submit a command capture bundling the apply outputs and both verifications.

Verify

All five manifests apply cleanly (an unchanged object reports unchanged — the flow is idempotent), the ConfigMap data shows the gated source, and the workbench env references secret/hf-token.

Exercise 5: VALIDATE — enumerate and see the models

Validation has two halves: the backend API enumerates the private models, and the dashboard UI shows them. Both need model-catalog READY >= 1.

  1. Backend enumeration from inside the cluster — list the sources, then the models of the private source:

CATALOG_URL="https://$(oc get route -l app=model-catalog -n rhoai-model-registries -o jsonpath='{.items[0].spec.host}')"
curl -sk -H "Authorization: Bearer $(oc whoami -t)" "$CATALOG_URL/api/model_catalog/v1alpha1/sources" | python3 -m json.tool | head -20
curl -sk -H "Authorization: Bearer $(oc whoami -t)" "$CATALOG_URL/api/model_catalog/v1alpha1/models?source=private_hf_models" | python3 -m json.tool | head -40

The sources list includes private_hf_models, and the models call returns the token-visible repositories the credential can read (real enumeration: the private eformat/rhoai-private-demo demo repo — set private: true on the Hugging Face side so the retrieval genuinely requires the credential).

  1. UI check — open the dashboard, AI hub → Models → Catalog, select the Workshop private models category, and confirm private models appear with their provider labels.

  2. Note the platform status alongside your validation — the DSC reports component health and this pilot surfaced a TrustyAI status quirk:

oc get dsc default-dsc

A False/NotReady DSC with a healthy dashboard and TrustyAI CR is the known patch-loop pattern — see Module 03 before treating it as your blocker.

Capture (VALIDATE)

Submit a command capture of the backend enumeration and a screenshot capture of the dashboard showing the private models category populated.

Verify

The enumeration returns at least one model from private_hf_models and the UI shows it. If the deployment is still scaled to zero or the enumeration returns empty, record the blocked state honestly with both captures — the flow is still complete; the content simply documents the blocked verdict.

Exercise 6: INTEGRATE — land the files, publish, digest

Integration is where the flow closes: files land in the assets repo, the site rebuilds, and the factory’s daily digest records the run.

  1. Check the working tree is exactly the set of files you intended — nothing else:

git status --short

  1. The integration contract for this workshop factory:

    • The engine owns git — the engine’s git writer commits the staged files to the assets repo; workers never run git commit or git push.

    • The engine builds pages — after meaningful content commits the publisher runs the Antora build and pushes the site; the component appears in the catalog once its content source is registered in the site playbook.

    • The graph carries outcomes — facts, findings, and captures record what happened; transcripts are disposable.

  2. Record the run in the daily digest — the factory meta-task receives one fact per day summarizing runs, commits, publishes, and blockers:

factory digest 2026-11-26: i642 workshop pages staged (3 modules + Mode 4 flow),
captures: page-tree log, deploy apply output; blockers: model-catalog 0/0 (Q154).

Capture (INTEGRATE)

Submit a log capture of the published page tree — the component’s pages/ directory listing plus the head of one page — as the integration proof.

Verify

The page tree lists index.adoc, getting-connected.adoc, the three module pages, and conclusion.adoc; the page head renders the title and :navtitle:. That listing is also this workshop’s own completion evidence.

Module summary

What you accomplished:

  • Staged the RHAISTRAT-1258 environment and verified model-catalog readiness

  • Drove all six Mode 4 steps — ENV, RECORD, AUTHOR, BUILD, VALIDATE, INTEGRATE — with a capture at each

  • Authored and applied the private catalog source, credential Secret, workbench, and feature YAML

Key takeaways:

  • The Mode 4 flow is evidence-first: every step’s claim is bound to a capture, and blocked states are recorded as honestly as passing ones

  • Cluster changes always correspond to in-tree manifest files, secrets hold placeholders, and the learner injects real credentials

  • The engine owns integration — git commits, page builds, and digests are engine steps, while the worker stages files and records evidence
