Module 01: Core Concepts

In this module you will learn what the model catalog is, where it runs in an OpenShift AI 3.6 cluster, how private-model gating restricts which Hugging Face repositories can be enumerated, and the token contract you follow as a learner in this workshop.

Learning objectives:

  • Explain what the model catalog is and which backend components serve it

  • Locate the model-catalog deployment and its config in the rhoai-model-registries namespace

  • Describe how the private_hf_models catalog entry gates private-model enumeration

  • Apply the Hugging Face token contract: one fine-grained READ-ONLY token, injected by you at two points

Exercise 1: What the model catalog is

The model catalog is the discovery layer of the RHOAI dashboard: data scientists and AI engineers browse it to find gen AI models available to their organization before registering them in a model registry and deploying them to a model serving runtime.

  1. Open the OpenShift AI dashboard.

  2. Click AI hub → Models → Catalog.

  3. Browse the categories in the menu bar: All models, Red Hat AI models, Red Hat AI validated models, and any custom categories your administrator configured.

Every catalog entry the page shows comes from a catalog source. Sources are declared as YAML in ConfigMaps that the catalog backend reads at startup:

  • default-catalog-sources — the Red Hat-provided catalogs (validated models, other models) shipped with the operator

  • model-catalog-sources — user-declared catalogs, where the private Hugging Face source from this workshop is registered

The catalog types include yaml (a static catalog file) and hf (live enumeration from the Hugging Face hub API — the type this feature uses).

Verify

You are viewing the Catalog page under AI hub → Models and can see at least one category of models. On the cluster side, confirm the source ConfigMaps exist:

oc get cm -n rhoai-model-registries default-catalog-sources model-catalog-sources

Exercise 2: Where the catalog runs

The catalog backend is a plain Kubernetes deployment owned by the model registry operator, running in the rhoai-model-registries namespace.

  1. Inspect the backend and its database:

oc get deploy -n rhoai-model-registries model-catalog model-catalog-postgres -o wide

The model-catalog deployment serves the REST API; model-catalog-postgres is its metadata database.

  1. Find the route that exposes the API outside the cluster:

oc get route -l app=model-catalog -n rhoai-model-registries

The model-catalog-https route is reencrypted through a kube-rbac-proxy sidecar — every request needs a Bearer token.

  1. Probe the API the way the workshop tooling does (this is the same endpoint the model_catalog_export.py script uses):

CATALOG_URL="https://$(oc get route -l app=model-catalog -n rhoai-model-registries -o jsonpath='{.items[0].spec.host}')"
curl -sk -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $(oc whoami -t)" "$CATALOG_URL/api/model_catalog/v1alpha1/sources"

An authenticated request returns 200; the same request without the token returns 401 — the RBAC proxy gating in action.

Verify

The model-catalog deployment exists in rhoai-model-registries, the model-catalog-https route resolves, and the sources endpoint answers 200 with your token. If the deployment shows 0/0 READY, continue anyway — Module 03 covers the scale-to-zero pattern — but note it: the VALIDATE step of Module 02 depends on the backend being up.

Exercise 3: Private-model gating

Private and gated Hugging Face repositories are enumerated through a dedicated catalog source of type hf. The source is gated three ways: the credential it uses, the organization it restricts enumeration to, and the include/exclude patterns applied on top.

  1. Read the user catalog sources ConfigMap:

oc get cm model-catalog-sources -n rhoai-model-registries -o jsonpath='{.data.sources\.yaml}'

The private_hf_models entry is the workshop’s private source. Walk its fields:

Field Purpose

id: private_hf_models

Stable source ID the API and UI use to address the catalog.

type: hf

Live enumeration against the Hugging Face hub API, not a static YAML file.

properties.apiKey

Name of the Secret holding the credential (catalog-private-hf-models-apikey). Never a token value — the backend resolves the credential from the Secret.

allowedOrganization

Restricts enumeration to one Hugging Face organization; includedModels patterns are auto-prefixed with it.

includedModels / excludedModels

Repository patterns (rhoai-private-demo under the demo account expands to the matching token-visible model); patterns are auto-prefixed with the configured organization, the Hugging Face search API does not glob, and the result is refined by the exclusions list.

  1. Confirm the credential Secret the source points at:

oc get secret catalog-private-hf-models-apikey -n rhoai-model-registries

Verify

You can explain, without looking back: why does properties.apiKey hold a Secret name instead of a token value? (Because secrets and config must never mix — the catalog backend resolves the credential from the Secret at enumeration time, and the ConfigMap stays committable.)

Exercise 4: The Hugging Face token contract

Private-model enumeration authenticates to Hugging Face with a fine-grained READ-ONLY user access token. This workshop runs on a strict token contract:

  • You inject your own token. The manifests shipped in this lab carry literal placeholder values — the factory that produced this workshop never distributes real credentials.

  • One token, two injection points: the runtime workbench reads it as the HF_TOKEN environment variable from secret/hf-token in private-hf-models-demo, and the catalog backend reads it from secret/catalog-private-hf-models-apikey in rhoai-model-registries.

  • READ-ONLY, fine-grained. Create the token at huggingface.co → Settings → Access Tokens with Repositories: Read only, scoped to the demo account (eformat). No write scopes, no inference quota, no billing access.

    1. Check the shape of the placeholder secrets — print only length and checksum, never the value:

oc get secret hf-token -n private-hf-models-demo -o jsonpath='{.data.token}' | base64 -d | wc -c

  1. Replace the placeholder with your token when you reach the BUILD step of Module 02 — the manifests show exactly where:

oc get secret hf-token -n private-hf-models-demo -o jsonpath='{.data.token}' | base64 -d

The factory placeholder is the literal string HF_TOKEN_RUNTIME_VALUE. If you see it, the token has not been injected yet.

Verify

You hold a fine-grained READ-ONLY token scoped to the demo account, you know the two Secrets it must be injected into, and you never print or commit a real token value. This is the learner contract recorded for this feature: the workshop documents the placeholder-vs-real-token decision — the factory ships placeholders, learners inject real tokens.

Module summary

What you accomplished:

  • Located the model catalog in the dashboard and its backend deployment in rhoai-model-registries

  • Read the private_hf_models catalog source and explained its gating fields

  • Created a fine-grained READ-ONLY Hugging Face token and identified both injection points

Key takeaways:

  • The model catalog is source-driven: default-catalog-sources holds Red Hat catalogs, model-catalog-sources holds user-declared catalogs such as the private hf source

  • Private-model gating is threefold — a saved-credential Secret reference, an allowed organization, and include/exclude repository patterns

  • Credentials live only in Secrets; config holds references; and the learner, not the factory, supplies the real token
