Module 03: Advanced Usage

In this module you will explore advanced configuration for the Feature Store: tuning the online store and feature server workers for latency and throughput, scaling for high availability with static replicas and a horizontal pod autoscaler, and choosing a client access pattern. You will also try the Ray compute engine for distributed feature pipelines.

Learning objectives:

  • Tune the online store and feature server workers in the FeatureStore configuration

  • Scale the instance with static replicas and horizontal pod autoscaling

  • Choose the right client access pattern for inference and training workloads

  • Configure the Ray compute engine for distributed materialization

Exercise 1: Tune the online store and workers

The online store is the single largest factor in get_online_features() latency. SQLite, the default for the local provider, does not support concurrent access and is unsuitable for production. For production on OpenShift, use Redis when your p99 (99th percentile) latency budget is under 10 ms, or PostgreSQL with connection pooling when you need transactional consistency or already run PostgreSQL infrastructure.

The following example shows a PostgreSQL online store configuration with connection pooling:

online_store:
  type: postgres
  host: 
  port: 5432
  database: feast
  user: 
  password: 
  conn_type: pool <1>
  min_conn: 4 <2>
  max_conn: 20 <2>
  keepalives_idle: 30 <3>
  sslmode: require <4>
1 conn_type: pool — enables connection pooling. Without it, each request opens and closes a new TCP (Transmission Control Protocol) connection, which increases latency.
2 min_conn / max_conn — steady-state and burst connection limits. max_conn must not exceed PostgreSQL max_connections divided by the total worker processes.
3 keepalives_idle — TCP keep-alive interval that prevents idle connections from being closed by firewalls or load balancers.
4 sslmode: require — mandates TLS (Transport Layer Security) encryption; required for production deployments.

In an operator deployment you do not edit feature_store.yaml by hand. The operator reads the store configuration from Kubernetes Secrets in the same namespace as the FeatureStore CR and writes it into the deployment’s feature_store.yaml. Each Secret key is named after a store type — postgres for the PostgreSQL stores, sql for the registry — and its value is the YAML you would place under that section of feature_store.yaml, without the type: key (the operator injects it from the CR).

  1. Save the data-store Secret to feast-data-stores.yaml and apply it in your working project:

cat > feast-data-stores.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: feast-data-stores
stringData:
  postgres: |
    host: 
    port: 5432
    database: feast
    db_schema: public
    user: 
    password: 
    sslmode: require
  sql: |
    path: postgresql+psycopg://:@:5432/feast
    cache_ttl_seconds: 60
    sqlalchemy_config_kwargs:
      echo: false
      pool_pre_ping: true
EOF
oc apply -f feast-data-stores.yaml -n abc123-user1

postgres — connection parameters for the PostgreSQL online and offline stores. Both services reference this key because both use type: postgres. sql — the SQLAlchemy URL and pool settings for the DB-backed registry.

  1. Save the FeatureStore manifest to production-feature-store.yaml and apply it. This is the instance you tune here and scale for high availability in Exercise 2:

cat > production-feature-store.yaml <<'EOF'
apiVersion: feast.dev/v1
kind: FeatureStore
metadata:
  name: production-feature-store
spec:
  feastProject: my_project
  services:
    registry:
      local:
        persistence:
          store:
            type: sql
            secretRef:
              name: feast-data-stores
    offlineStore:
      persistence:
        store:
          type: postgres
          secretRef:
            name: feast-data-stores
    onlineStore:
      persistence:
        store:
          type: postgres
          secretRef:
            name: feast-data-stores
      server:
        workerConfigs:
          workers: 4
          workerConnections: 2000
          maxRequests: 5000
          maxRequestsJitter: 500
          keepAliveTimeout: 30
          registryTTLSeconds: 300
        resources:
          requests:
            cpu: "2"
            memory: 2Gi
          limits:
            cpu: "4"
            memory: 4Gi
EOF
oc apply -f production-feature-store.yaml -n abc123-user1

persistence.store — DB-backed persistence: type selects the store and secretRef points at the Secret whose key matches the type; the registry uses the SQLAlchemy URL under the sql key. DB-backed persistence on every enabled service is a prerequisite for scaling in Exercise 2. workerConfigs — Gunicorn worker tuning for the online feature server. workers — number of worker processes; balance against your connection budget when scaling horizontally. resources — CPU and memory requests and limits for the feature server pod.

The production instance does not carry the feature-store-ui: enabled label — your Module 02 instance keeps it, and only one Feature Store instance may carry that label.

Keep a record of the values you change so you can restore them. Apply worker changes to your FeatureStore CR and watch the feature server pods roll out with oc get pods -w.

Verify

After applying the Secret and the CR, the operator deploys the Feature Store and writes the store configuration from the Secret into its feature_store.yaml. Confirm the FeatureStore reconciles to a ready state:

oc get feast production-feature-store

The STATUS column shows Ready once the operator has reconciled the change. The operator creates a single deployment named feast-production-feature-store for the CR — one container per enabled service server; with this CR that is the online feature server, which reads the PostgreSQL stores and the SQL registry through its feature_store.yaml:

oc get deployments

You should see feast-production-feature-store among the deployments. The Kubernetes services in front of the deployment follow the feast-<CR-name>-<service-type> naming convention.

With the configuration tuned, you now scale the instance for high availability.

Exercise 2: Scale for high availability

The Feature Store Operator deploys a single replica by default, which supports development but is a single point of failure in production. You can choose static replicas (fixed count, high availability, predictable footprint) or horizontal pod autoscaling (variable traffic patterns).

To scale horizontally, use database-backed persistence for all enabled services — online store, offline store, and registry. Do not use file-based persistence such as SQLite, DuckDB, or registry.db with multiple replicas; those backends do not support concurrent access from multiple pods. The operator enforces this at the CRD level: it rejects replicas > 1 (and autoscaling) until every enabled service carries DB-backed persistence — persistence.store for the online and offline stores, and a DB-backed or remote registry. The production-feature-store CR you created in Exercise 1 already meets the requirement.

  1. Scale to three static replicas with oc scale:

oc scale featurestore/production-feature-store --replicas=3

  1. The operator scales the feast-production-feature-store deployment and rolls out the additional feature server pods. Confirm that three pods are running:

oc get pods

You should see three feast-production-feature-store-<hash> pods in the Running state (for example, feast-production-feature-store-5d8f7c6b5-2xk9p), all sharing the PostgreSQL online store, the PostgreSQL offline store, and the SQL registry you configured in Exercise 1.

Alternatively, set spec.replicas in the FeatureStore CR. The operator automatically switches the deployment strategy to RollingUpdate and injects soft pod anti-affinity (node-level) and topology spread (zone-level) constraints.

For variable traffic, configure an autoscaler with services.scaling.autoscaling in the CR:

spec:
  feastProject: my_project
  services:
    scaling:
      autoscaling: <1>
        minReplicas: 2 <2>
        maxReplicas: 10 <3>
        metrics:
          - type: Resource
            resource:
              name: cpu
              target:
                type: Utilization
                averageUtilization: 70 <4>
    podDisruptionBudgets:
      maxUnavailable: 1 <5>
1 autoscaling — instructs the operator to create and manage an HPA for the feature server.
2 minReplicas — minimum number of replicas kept running.
3 maxReplicas — upper bound for scale-out.
4 averageUtilization: 70 — CPU target for scaling; omit metrics to default to 80% CPU.
5 podDisruptionBudgets — maximum pods allowed unavailable during disruptions; the key lives at the services level as a sibling of scaling, not inside autoscaling.

Autoscaling is mutually exclusive with spec.replicas > 1. Set one or the other, not both.

Verify

Verify that the operator created the HorizontalPodAutoscaler resource:

oc get hpa

You should see output similar to the following:

NAME                             REFERENCE                                   TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
feast-production-feature-store   Deployment/feast-production-feature-store   cpu: 1%/70%   2         10        2          8m37s

The HPA is named feast-<CR-name> — the CR name is preserved as written, dashes included (for the production-feature-store CR, the HPA and the feature server deployment are both named feast-production-feature-store). The output shows the configured MINPODS/MAXPODS bounds. The TARGETS column initially displays cpu: <unknown>/70% for a minute while the metrics server begins scraping, then resolves to a live value.

With scaling in place, the last step is choosing how clients reach the feature server.

Exercise 3: Client access patterns and the Ray compute engine

Feature Store supports three client access patterns, each with a different performance profile:

  • Direct REST API (client → feature server → store): lowest client-side resource usage. Recommended for production inference services in any language, and for deployments behind a load balancer. You used this pattern in Module 02 with curl.

  • SDK with remote store (client → feature server → store): full Python SDK API with centralized serving. Point the client configuration at the feature server with online_store: type: remote and a connection pool size.

  • SDK direct (client → store): Python clients talking straight to the store. Avoid this in a typical operator deployment — each client pod opens its own database connections, multiplying connection load. Restrict it to development.

For large feature pipelines, you can offload transformations, aggregations, joins, and materializations to the Ray compute engine, which executes feature computation as distributed directed acyclic graphs (DAGs) with point-in-time joins, broadcast join selection, and lazy evaluation.

  1. Enable the Ray compute engine in feature_store.yaml:

offline_store:
  type: ray <1>
  storage_path: data/ray_storage
batch_engine:
  type: ray.engine <2>
  max_workers: 4 <3>
  broadcast_join_threshold_mb: 100
  target_partition_size_mb: 64
  ray_address: localhost <4>
1 type: ray — selects the Ray offline store for historical feature retrieval.
2 type: ray.engine — the batch engine that runs materialize() and get_historical_features() on Ray.
3 max_workers — caps the Ray worker processes; unset uses all cores.
4 ray_address — address of a running Ray cluster.

  1. Try the retrieval-augmented generation (RAG) template, which parallelizes embedding generation across workers:

 
feast init -t ray_rag my_rag_project
cd my_rag_project/feature_repo

Verify

feast init creates the new repository with a feature_repo directory containing feature_store.yaml and example.py. The output starts with a line similar to:

Creating a new Feast repository in /projects/my_rag_project.

If you configured Ray in feature_store.yaml, feast configuration displays the ray.engine batch engine settings you applied.

Explore: Production topologies and authentication

The FeatureStore CR you tuned in Exercise 1 maps to one of three documented production topologies:

  • Minimal production — single namespace, no high availability, TLS, or role-based access control (RBAC); small teams only.

  • Standard production — the recommended topology: high availability (HA) registry, HPA autoscaling, TLS via OpenShift route, Kubernetes RBAC.

  • Enterprise production — namespace-per-team isolation, OpenID Connect (OIDC) and Feast permissions, Prometheus metrics with distributed tracing.

For enterprise multitenant environments, the operator can authenticate and authorize requests against an OIDC identity provider such as Keycloak or Dex. Selecting OIDC alone is not enough: authz: { oidc: {} } passes CRD validation, but without provider settings the operator has nothing usable to configure the feature server with. Point spec.authz.oidc at a Secret in the FeatureStore’s namespace that carries the provider settings:

apiVersion: v1
kind: Secret
metadata:
  name: feast-oidc
stringData:
  auth_discovery_url: https://keycloak.example.com/realms/feast/.well-known/openid-configuration
  client_id: feast
  client_secret: <CLIENT_SECRET>
---
apiVersion: feast.dev/v1
kind: FeatureStore
metadata:
  name: production-feature-store
spec:
  authz:
    oidc:
      secretRef:
        name: feast-oidc

The Secret keys are the OIDC properties themselves: auth_discovery_url (the provider’s discovery endpoint), client_id, and client_secret — plus username and password when the server needs the client-credentials flow. Alternatively, set spec.authz.oidc.issuerUrl directly and the operator derives the discovery endpoint by appending /.well-known/openid-configuration; issuerUrl takes precedence over the Secret’s auth_discovery_url.

By default — when the CR has no authz section — the operator configures Kubernetes authentication on every deployed service, which is what your workshop instance uses. With OIDC enabled, Feast validates incoming bearer tokens against the provider’s published keys and maps token claims — username, roles, groups — onto Feast permission policies; tokens carrying a Kubernetes claim are validated through TokenReview, which also enables namespace-based policies.

If you enable OIDC on an instance, verify that the operator applied the authorization configuration:

oc get feast production-feature-store \
  -o jsonpath='{.status.conditions[?(@.type=="Authorization")]}' | python3 -m json.tool

A successful configuration reports "type": "Authorization" with "status": "True".

Module summary

What you accomplished:

  • Tuned the online store (PostgreSQL) and feature server workers

  • Wired DB-backed persistence for the online store, offline store, and registry through a Secret

  • Scaled the Feature Store with static replicas and a horizontal pod autoscaler

  • Compared client access patterns and enabled the Ray compute engine

Key takeaways:

  • The online store dominates get_online_features() latency; pool connections and use TLS

  • Store configuration travels in Secrets whose keys match the store type — postgres, sql — referenced from persistence.store in the CR

  • DB-backed persistence on every enabled service is a prerequisite for scaling; the operator rejects replicas > 1 and autoscaling for file-based backends

  • Prefer the direct REST API for production inference and the SDK remote store for Python
