Module 02: Hands-on Exercise

In this module you will create InferenceObjective resources that define priority tiers for multitenant workloads, then drive load to validate that priority-based queuing, fairness, and load shedding work as designed.

Flow control manages request queuing, prioritization, and fairness between the Inference Gateway and InferencePool backends. When a request arrives:

  1. The Gateway automatically injects two headers based on authentication: x-gateway-inference-fairness-id, which groups requests from the same authentication source for fair queuing, and x-gateway-inference-objective, which determines request priority by matching an InferenceObjective resource.

  2. The request enters a priority-aware queue in the Endpoint Picker and waits for dispatch.

  3. The dispatch logic applies strict priority ordering: higher-priority requests dispatch before lower-priority requests, and requests at the same priority level use intra-band fairness policies.

  4. A saturation check monitors queue depth and KV cache utilization on model servers. When pool saturation is detected, dispatch is halted and all requests wait in their priority queues until capacity becomes available.

  5. When capacity is available, the request proceeds to the Scheduling layer. The endpoint is selected at dispatch time based on current capacity and prefix cache state — a late-binding approach that prevents requests from being locked to a server that might be saturated by the time the request is processed.

Platform administrators create InferenceObjective resources to define priority tiers. Higher integer values represent higher priority, and negative values designate sheddable requests that are queued and dispatched last:

Tier Priority Value Use Case

Critical

100

Interactive applications

Standard

0 (default)

Standard API calls

Sheddable

-1

Batch workloads

Learning objectives:

  • Create InferenceObjective resources that implement priority tiers for an InferencePool

  • Configure fairness policies and per-band capacity limits

  • Generate sustained concurrent load with an in-cluster load-generator pod to drive the pool toward saturation

  • Validate priority differentiation, rejection behavior, and observability under load

Complete the steps in this module only after enabling flow control in Module 01. Without the flowControl feature gate, InferenceObjective priorities are not enforced.

Exercise 1: Create priority tiers with InferenceObjective

Each InferenceObjective resource defines a priority value for requests matching it, scoped to a specific InferencePool. You create a critical tier for interactive applications and a sheddable tier for batch workloads.

  1. Create the critical tier. Resolve the InferencePool name from your project (the llm-d controller creates the pool when your LLMInferenceService is deployed), then write and apply the resource:

NS=abc123-user1
POOL=$(oc get inferencepools.inference.networking.k8s.io -n $NS -o jsonpath='{.items[0].metadata.name}')
echo "Using InferencePool: $POOL"
cat > critical-inference-objective.yaml <

  • metadata.name — The InferenceObjective name. Requests whose x-gateway-inference-objective header matches this name are assigned this priority. With ServiceAccount tokens, the header is set to the ServiceAccount’s namespace; with user tokens, to authenticated; anonymous requests get unauthenticated.

  • metadata.namespace — The namespace where the InferencePool is deployed.

  • priority — The priority value. Higher integer values represent higher priority; negative values designate lower-priority requests that are queued and dispatched last. If not specified, defaults to 0.

  • poolRefs[].group — The API group serving InferencePool on RHOAI 3.6: inference.networking.k8s.io.

  • poolRefs[].name — The name of the InferencePool resource this objective applies to. This field is required; the resolved name is echoed before the file is written.

InferenceObjective at apiVersion llm-d.ai/v1alpha2 is deprecated on RHOAI 3.6 — the API server warns use llm-d.ai/v1 on every write — and the v1alpha2 spec.poolRef field is not retained in storage. This workshop uses apiVersion llm-d.ai/v1 with the spec.poolRefs list. If you created objectives with the v1alpha2 form earlier, re-create them with the v1 form and confirm the pool binding with oc get inferenceobjective interactive-critical -n abc123-user1 -o jsonpath='{.spec.poolRefs}'.

cat > batch-inference-objective.yaml <

The negative priority value (priority: -1) means batch requests run at lower priority than interactive workloads and are the first to be dropped when the system reaches saturation, protecting real-time inference SLOs.

  1. Optional: After creating InferenceObjective resources, you can customize flow control behavior by configuring priority band capacity, request timeouts, and fairness policies in the spec.router.scheduler.config.inline section of your LLMInferenceService. The llm-d.ai/v1alpha1 config form from Module 01 applies here as well; apiVersion: llm-d.ai/v1 is the forward-compatible form on RHOAI 3.6:

apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
featureGates:
- "flowControl"
flowControl:
  maxBytes: 1073741824 (1)
  defaultRequestTTL: 1m (2)
  priorityBands:
  - priority: 100 (3)
    maxBytes: 536870912
    orderingPolicyRef: fcfs-ordering-policy (4)
    fairnessPolicyRef: round-robin-fairness-policy (5)
  - priority: 0
    orderingPolicyRef: fcfs-ordering-policy
    fairnessPolicyRef: round-robin-fairness-policy
  - priority: -1
    maxRequests: 1000
    orderingPolicyRef: fcfs-ordering-policy
    fairnessPolicyRef: global-strict-fairness-policy
1 maxBytes — Optional global queue capacity in bytes aggregated across all priority bands. When this limit is exceeded, new requests receive HTTP 429 errors. If set to 0 or omitted, only per-band limits apply.
2 defaultRequestTTL — The request timeout. Requests waiting longer than this duration receive HTTP 503 errors. Default is 1 minute.
3 priorityBands[].priority — The priority value for this band. Must match the priority values defined in your InferenceObjective resources.
4 orderingPolicyRef — The ordering policy. Default is fcfs-ordering-policy (first-come, first-served). Other supported policies are edf-ordering-policy (earliest deadline first) and slo-deadline-ordering-policy (orders by SLO-derived deadline).
5 fairnessPolicyRef — The fairness policy. The default global-strict-fairness-policy offers no tenant isolation and can result in starvation within a priority band. For equitable service distribution across tenants, use round-robin-fairness-policy.

Verify

  1. Confirm both InferenceObjective resources exist in your project:

oc get inferenceobjective -n abc123-user1

The output lists interactive-critical and batch-workload in your namespace.

  1. Check that the priority values were accepted:

oc get inferenceobjective interactive-critical -n abc123-user1 -o jsonpath='{.spec.priority}'

The output shows 100.

Both priority tiers are registered against your InferencePool. Next you will drive load and watch the flow control layer dispatch by priority.

Exercise 2: Generate sustained load with an in-cluster load generator

Flow control is work-conserving: when the InferencePool has available capacity, requests dispatch immediately with no added latency, and queuing plus priority enforcement activate only when the pool is saturated. You generate sustained concurrent traffic from inside the cluster with a load-generator pod, driving the Endpoint Picker toward saturation so that the llm_d_epp_flow_control_* metrics and the flow-control rejection behavior actually manifest.

This workshop’s demo environment is CPU-only and the model workload intentionally does not reach a serving state: the model init container cannot pull the pinned model repository, the Endpoint Picker reports llm_d_epp_ready_endpoints=0, llm_d_epp_flow_control_pool_saturation stays pinned at 1.0 (the gating set point), and the gateway answers requests with 503 rejected-no-endpoints. That is the documented demo state — the flow-control evidence this module collects (the x-llm-d-request-dropped-reason rejection headers, the llm_d_epp_flow_control_pool_saturation and llm_d_epp_flow_control_dispatch_cycle_duration_seconds series, and the llm_d_epp_ready_endpoints gauge) does not depend on the model serving. On a serving environment the same steps instead produce the 200/429 mix described in each verify section.

  1. Resolve the model service name and build the URL for its OpenAI-compatible endpoint on the MaaS gateway:

NS=abc123-user1
LLM_SVC=$(oc get llminferenceservice -n $NS -o jsonpath='{.items[0].metadata.name}')
URL="https://$(oc get httproute ${LLM_SVC}-kserve-route -n $NS -o jsonpath='{.spec.hostnames[0]}')/${NS}/${LLM_SVC}/v1/chat/completions"
MODEL_NAME=${MODEL_NAME:-RedHatAI/Qwen3-8B-FP8-dynamic}
echo $URL

The model service name is resolved from your project, and the URL host is discovered live from the spec.hostnames of the HTTPRoute verified in Module 01 (maas-llmd-demo-kserve-route) rather than composed by hand — the route hostname is the MaaS gateway listener host on the maas.apps.* wildcard domain, and the /{project}/{model-service}/v1/chat/completions path is the one that HTTPRoute binds. The wildcard resolves from in-cluster pods, so the load generator reaches the gateway directly. The model defaults to the llm-d runnable example (RedHatAI/Qwen3-8B-FP8-dynamic) — set MODEL_NAME to override.

  1. Create the load-test script as a ConfigMap. The script first runs a smoke test, then sends 5000 requests with 200 concurrent curl processes, alternating between the interactive-critical and batch-workload objective headers from Exercise 1. Each request asks for a long generation (max_tokens: 2048) to keep the model servers busy and prints the HTTP status and elapsed time per request:

read -r -d '' LOAD_SCRIPT << 'EOF' || true
#!/bin/sh
set -e
URL="$1"; CONCURRENCY="$2"; REQUESTS="$3"; MODEL="$4"
cat > /tmp/req.sh << 'REQEOF'
#!/bin/sh
if [ $(($2 % 2)) -eq 0 ]; then OBJ="batch-workload"; else OBJ="interactive-critical"; fi
curl -sk --max-time 600 "$1" \
  -H "Content-Type: application/json" \
  -H "x-gateway-inference-objective: $OBJ" \
  -d "{\"model\":\"$3\",\"messages\":[{\"role\":\"user\",\"content\":\"Request $2. Write a detailed essay about topic $2 covering history, analysis, and predictions.\"}],\"max_tokens\":2048}" \
  -o /dev/null -w "req=$2 objective=$OBJ status=%{http_code} time=%{time_total}s\n"
REQEOF
chmod +x /tmp/req.sh
echo "Smoke test..."
STATUS=$(curl -sk --max-time 30 -D /tmp/smoke-headers "$URL" \
  -H "Content-Type: application/json" \
  -H "x-gateway-inference-objective: interactive-critical" \
  -d "{\"model\":\"$MODEL\",\"messages\":[{\"role\":\"user\",\"content\":\"Hi\"}],\"max_tokens\":5}" \
  -o /dev/null -w "%{http_code}")
echo "Status: $STATUS"
if [ "$STATUS" = "200" ]; then
  echo "Model endpoints are ready; the load will exercise queuing and band-capacity rejections."
elif [ "$STATUS" = "503" ] && grep -qi "x-llm-d-request-dropped-reason: rejected-no-endpoints" /tmp/smoke-headers; then
  echo "NOTE: 503 rejected-no-endpoints - the pool has no ready model endpoints (the documented demo state)."
  echo "NOTE: Continuing: this rejection path is itself the flow-control evidence this exercise collects."
else
  echo "ERROR: Smoke test failed (HTTP $STATUS)"
  head -1 /tmp/smoke-headers
  exit 1
fi
echo "Sending $REQUESTS requests ($CONCURRENCY concurrent)..."
seq 1 "$REQUESTS" | xargs -P "$CONCURRENCY" -I{} /tmp/req.sh "$URL" {} "$MODEL"
echo "Done."
EOF
oc create configmap load-test-script -n $NS --from-literal=load.sh="$LOAD_SCRIPT"

The load script receives the URL, concurrency, request count, and model name as its four arguments ($4 is the model) and passes the URL, request number, and model to each per-request helper — req.sh reads the model from $3 — so the ConfigMap stays generic. The smoke test accepts both documented outcomes: Status: 200 on a serving environment, or Status: 503 with the x-llm-d-request-dropped-reason: rejected-no-endpoints header in this demo environment, where the script prints an honest NOTE and continues. Any other status (for example 401 or 404) stops the script because the URL or authentication is wrong.

  1. Create the load-generator pod. The URL and model from the previous step are substituted when the manifest is written:

cat > load-test-pod.yaml <

  • metadata.name — The load-generator pod name.

  • restartPolicy — Never, so the pod runs the load once and exits when finished, preserving its logs.

  • image — The load-generator image. The script only uses curl, so the lightweight curlimages/curl image is sufficient.

  • args — The gateway URL, concurrency (200 concurrent curl processes), total request count (5000), and the model name.

  • resources — The load generator only runs curl processes: a 500m CPU / 512Mi memory request with 2 CPU / 1Gi limits keeps the pod schedulable on clusters whose nodes are already near their CPU request capacity.

  • configMap.name — Mounts the load script created in the previous step at /scripts, where the command runs it from.

Press Ctrl+C to stop following the output. The smoke test must print Status: 200 (serving environment) or the 503 rejected-no-endpoints NOTE (this demo environment) before the load begins; any other status stops the script, so resolve the URL or authentication before continuing.

In production, the Gateway AuthPolicy sets the x-gateway-inference-objective header automatically based on authentication: ServiceAccount tokens map to the ServiceAccount’s namespace, user tokens to authenticated, and anonymous requests to unauthenticated. The load generator sets the header explicitly so that the two InferenceObjective tiers you created in Exercise 1 are exercised deterministically during the test.
The load test must generate enough traffic to trigger queuing without being rate-limited. If gateway authentication or rate limiting throttles the load before the pool saturates, you can disable authentication for testing by setting the security.opendatahub.io/enable-auth: "false" annotation on the LLMInferenceService. Production deployments must not set this annotation.

Verify

  1. After the load test completes, count the HTTP outcomes from the load-generator output:

oc logs load-test -n abc123-user1 | grep -o "status=[0-9]*" | sort | uniq -c

Each request line has the form req=<n> objective=<tier> status=<code> time=<seconds>. In this demo environment, every request returning status=503 with the x-llm-d-request-dropped-reason: rejected-no-endpoints response header is the expected outcome and confirms the exercise succeeded: the Endpoint Picker admits each request into its priority-band queue, finds zero ready model endpoints, and drops the request with an observable reason header instead of forwarding it to a dead backend. That rejection path is exactly what sheds load under saturation on a serving environment, so observing it here proves the flow-control rejection behavior end-to-end. On a serving environment, requests complete with status=200 while the pool has capacity; once concurrency drives the pool toward saturation, requests beyond a priority band’s queue capacity are rejected with status=429 and the x-llm-d-request-dropped-reason: rejected-saturated header, and requests that wait longer than the configured defaultRequestTTL (default 1 minute) are rejected with status=503 (rejected-ttl-expired). A mix of 200 and 429 counts is the success criteria on a serving environment; uniform 503 rejected-no-endpoints counts are the success criteria in this environment.

Now that you have generated sustained load with the in-cluster load generator, you will validate priority queuing and rejection behavior under load.

Exercise 3: Validate priority queuing and rejection behavior under load

With the load generator from Exercise 2 driving the pool toward saturation, you confirm that requests queue at the Endpoint Picker and dispatch by policy, and that rejections carry observable reason headers. The load test issues 5000 requests and, in this environment, rejections return immediately, so the pod may have already exited by the time you get here — its complete log remains available with oc logs load-test -n abc123-user1, and the flow-control series below persist after the run.

  1. While the load test is running, check that the model server pods are near capacity. On a serving environment under saturation, vllm:num_requests_running is at or near the --max-num-seqs cap and vllm:num_requests_waiting is above zero:

oc get pods -n abc123-user1 | grep vllm

Then, in the OpenShift web console, navigate to Observe > Metrics and run:

vllm:num_requests_waiting{namespace="abc123-user1"}

In this demo environment the model server never reaches a serving state, so the pod list shows a non-ready model pod and both vllm:num_requests_* queries return an empty result. That is the documented state, not a failure — use the Endpoint Picker’s own series in the next steps as the flow-control evidence for this environment.

  1. Monitor flow control metrics to confirm the flow control layer is queueing and dispatching by policy. In the OpenShift web console, navigate to Observe > Metrics and run:

llm_d_epp_flow_control_pool_saturation{namespace="abc123-user1"}

The llm_d_epp_flow_control_pool_saturation metric reports the saturation level of the inference pool: 1.0 is the gating set point at which dispatch halts, values above 1.0 indicate oversubscription past the gating threshold, and an idle pool reads 1.0. This is the primary flow-control health series exposed by the Endpoint Picker in this release — there is no per-queue queue_size metric. Related metrics exposed by the Endpoint Picker:

  • llm_d_epp_flow_control_capacity_utilization_bytes and llm_d_epp_flow_control_capacity_utilization_requests — per-band queue utilization, with a priority label matching your InferenceObjective values

  • llm_d_epp_flow_control_dispatch_cycle_duration_seconds — dispatch cycle latency histogram for the flow control layer

  • llm_d_epp_flow_control_stale_endpoints — model-server endpoints whose utilization metrics are stale, per saturation detector

  • llm_d_epp_ready_endpoints — model-server endpoints currently ready in the pool

    1. Alternatively, scrape the Endpoint Picker metrics endpoint directly. The endpoint serves HTTPS on port 9090 and requires bearer-token authentication: an unauthenticated request returns 401 Unauthorized, and the token of the Endpoint Picker’s own ServiceAccount is rejected with 403 — use your workshop user’s token:

LLM_SVC=$(oc get llminferenceservice -n abc123-user1 -o jsonpath='{.items[0].metadata.name}')
TOKEN=$(oc whoami -t)
oc port-forward svc/${LLM_SVC}-epp-service -n abc123-user1 9090:9090 &
sleep 3
curl -sk -H "Authorization: Bearer $TOKEN" https://localhost:9090/metrics | grep -E "^llm_d_epp_flow_control" | head -20

The output lists the live llm_d_epp_flow_control_* series for your inference pool, including pool_saturation. Stop the port-forward when you are done (for example with kill %1).

  1. Open the built-in observability dashboards to correlate traffic and performance. In the OpenShift AI dashboard, navigate to Observe & Monitor > Dashboard, then from the namespace filter select your project. In the LLM Traffic dashboard, review request rate and error rate; in the LLM Performance dashboard, review time to first token (TTFT) percentiles.

  2. When flow control rejects or evicts a request, the response includes an x-llm-d-request-dropped-reason header with a specific reason value. The sustained concurrent load from Exercise 2 triggers these rejections once a priority band’s queue capacity is exceeded:

HTTP Status Reason Cause

429

rejected-saturated

The priority band’s queue capacity is exhausted

503

rejected-ttl-expired

The request waited longer than the configured defaultRequestTTL

503

rejected-context-cancelled

The client disconnected while the request was queued

503

rejected-no-endpoints

The pool has zero ready endpoints

503

rejected-shutting-down

The Endpoint Picker is shutting down gracefully

Verify

On a serving environment under sustained load, vllm:num_requests_running is at or near the --max-num-seqs cap and vllm:num_requests_waiting is above zero on model server pods, confirming that requests are queuing at the Endpoint Picker and being dispatched by policy. In this demo environment both vllm:num_requests_* queries return an empty result because the model server never becomes ready — the expected outcome here, not a failure. Pivot to the Endpoint Picker’s own series instead: llm_d_epp_ready_endpoints reports the pool’s ready endpoint count (0 in this environment), and the flow-control series below confirm the queuing and rejection layers are active regardless of model state.

The llm_d_epp_flow_control_capacity_utilization_bytes and llm_d_epp_flow_control_capacity_utilization_requests metrics carry a priority label matching your InferenceObjective values, confirming that flow control tracks requests by priority band. In this environment the per-band counters stay at zero alongside the empty vLLM series: with zero ready endpoints, requests are dropped with rejected-no-endpoints rather than held in a band queue, and the per-request outcomes from Exercise 2’s verify are the observable evidence.

On a serving environment, if pool utilization remains at zero, increase the concurrency value in load-test-pod.yaml and run the load again to create saturation conditions where priority differentiation occurs.

Under sustained contention, higher-priority requests dispatch before lower-priority requests, and the batch tier (priority: -1) is the first to be dropped when the system reaches saturation.

  1. When you are done with this exercise, delete the load-test pod and script ConfigMap:

oc delete pod load-test -n abc123-user1
oc delete configmap load-test-script -n abc123-user1

Module summary

What you accomplished:

  • Created InferenceObjective resources that define critical (priority: 100) and sheddable (priority: -1) priority tiers for your InferencePool

  • Configured per-band capacity limits, request TTL, and fairness policies in the flow control configuration

  • Generated sustained concurrent load with an in-cluster load-generator pod to drive the Endpoint Picker toward saturation

  • Validated priority-based queuing, rejection behavior, and flow control metrics under load

Key takeaways:

  • InferenceObjective priorities are enforced by the flow control layer through strict priority ordering, with intra-band fairness policies distributing requests within each band

  • The default global-strict-fairness-policy offers no tenant isolation; use round-robin-fairness-policy for equitable service distribution across tenants

  • Rejections are observable through the x-llm-d-request-dropped-reason response header and the llm_d_epp_flow_control_* metrics

Next steps:

  • Tune the flow control configuration from Exercise 1 with capacity limits (maxBytes, maxRequests, defaultRequestTTL) matched to your model server’s memory and concurrency budget, then repeat the load test

  • Add a mid-tier InferenceObjective (for example, priority: 50) and watch the llm_d_epp_flow_control_capacity_utilization_* series split into three priority bands under load

  • Compare fcfs-ordering-policy against edf-ordering-policy and round-robin-fairness-policy on a serving environment to measure queue-time fairness across tenants
