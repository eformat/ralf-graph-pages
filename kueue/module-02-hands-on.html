Module 02: Hands-on Exercise

In this module you will work through the core Kueue workflow end to end: submit a distributed PyTorch training job as a TrainJob (the Kubeflow Trainer v2 API) to your LocalQueue, watch Kueue admit it, hold a second job that exceeds the quota, and monitor Kueue health with alerts and error messages.

Learning objectives:

  • Submit a training job to a LocalQueue with the kueue.x-k8s.io/queue-name label

  • Read Workload resources to see how Kueue admits and holds queued work

  • Use Kueue alerts and the documented error messages to troubleshoot queueing problems

Exercise 1: Submit a queued training job

You submit workloads to a queue by creating them in a Kueue-managed project with the kueue.x-k8s.io/queue-name label. Kueue creates a Workload resource for the job and only lets the job’s pods run when the quota is available.

On RHOAI 3.6, distributed PyTorch training runs through the Kubeflow Trainer v2 API: you create a TrainJob that references a ClusterTrainingRuntime, and the runtime supplies the training image and pod template. The example training script selects its backend dynamically: nccl for GPU, gloo for CPU, so it runs on the CPU-only workshop cluster; the Trainer controller injects the rendezvous environment (PET_NNODES, PET_MASTER_ADDR, and so on) into each training pod.

Create a file named trainjob.yaml that defines the training job, with the script passed inline through the trainer args:

cat > trainjob.yaml <<'EOF'
apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: kueue-trainjob
  labels:
    kueue.x-k8s.io/queue-name: workshop-lq
spec:
  runtimeRef:
    apiGroup: trainer.kubeflow.org
    kind: ClusterTrainingRuntime
    name: torch-distributed-cpu-torch211-py312
  trainer:
    numNodes: 1
    command: ["/bin/bash", "-c"]
    args:
      - |
        cat > /tmp/train.py <<'PYEOF'
        import os
        import torch
        import torch.distributed as dist

        nnodes = int(os.environ.get("PET_NNODES", "1"))
        nproc = int(os.environ.get("PET_NPROC_PER_NODE", "1"))
        node_rank = int(os.environ.get("PET_NODE_RANK", "0"))
        master_addr = os.environ.get("PET_MASTER_ADDR", "127.0.0.1")
        master_port = os.environ.get("PET_MASTER_PORT", "29500")
        rank = node_rank * nproc
        world_size = nnodes * nproc

        # Select backend dynamically: nccl for GPU, gloo for CPU
        backend = "nccl" if torch.cuda.is_available() else "gloo"
        dist.init_process_group(
            backend,
            init_method=f"tcp://{master_addr}:{master_port}",
            rank=rank,
            world_size=world_size,
        )
        device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
        tensor = torch.zeros(1, device=device)
        if rank == 0:
            tensor += 1
            for i in range(1, world_size):
                dist.send(tensor, dst=i)
        else:
            dist.recv(tensor, src=0)
        print(f"Running on rank {rank} out of {world_size} using {device} with backend {backend}.")
        print(f"Rank {rank}: Tensor value {tensor.item()} on {device}")
        dist.destroy_process_group()
        PYEOF
        python3 /tmp/train.py
    resourcesPerNode:
      requests:
        cpu: "1"
        memory: 2Gi
EOF

The kueue.x-k8s.io/queue-name label binds the TrainJob to the workshop-lq LocalQueue, which queues it against the ClusterQueue quota. The runtimeRef selects the torch-distributed-cpu-torch211-py312 ClusterTrainingRuntime — a platform-provided runtime that pins the CPU PyTorch training image. numNodes: 1 requests a single training node. The CPU and memory requests under resourcesPerNode must fit within the ClusterQueue nominal quota, or Kueue holds the job. When you apply the TrainJob, Kueue creates a Workload resource named trainjob-kueue-trainjob-<id> for it.

Inspect the training image that the runtime pins:

oc get clustertrainingruntime torch-distributed-cpu-torch211-py312 -o jsonpath='{.spec.template.spec.replicatedJobs[0].template.spec.template.spec.containers[0].image}'

The output shows the pinned CPU training image, registry.redhat.io/rhoai/odh-th-torch-cpu-py312-rhel9 at a digest (sha256:2a727b…​). List the other platform-provided runtimes with oc get clustertrainingruntime — GPU and ROCm variants pin their own images the same way.

The example runs on CPU through the torch-distributed-cpu-torch211-py312 runtime. To train on accelerators, reference a GPU-pinned runtime instead (for example torch-distributed-cuda130-torch211-py312 for NVIDIA or torch-distributed-rocm714-torch211-py312 for AMD) and create a ClusterQueue whose resource groups cover nvidia.com/gpu or amd.com/gpu — Kueue only admits workloads whose requests fit a flavor it knows.

Apply the training job:

oc apply -f trainjob.yaml -n abc123-user1

Verify

Monitor the running distributed training job:

oc get trainjobs -n abc123-user1

The kueue-trainjob TrainJob is listed. The STATE column stays empty while the job runs and shows Complete once the script finishes. Then check the pod logs. The Trainer controller creates the JobSet child jobs as <trainjob-name>-node-<index>:

oc logs job/kueue-trainjob-node-0 -n abc123-user1

The logs show each rank’s tensor value, for example Rank 0: Tensor value 1.0 on cpu. In the console, click Workloads → Pods and verify that the training pod kueue-trainjob-node-0-0-<suffix> is running or has completed. You can also select the training pods with the JobSet label: oc get pods -n abc123-user1 -l jobset.sigs.k8s.io/jobset-name=kueue-trainjob.

Now that you have submitted a queued training job, you will watch Kueue make scheduling decisions by submitting a second job that exceeds the quota.

Exercise 2: Watch Kueue make scheduling decisions

Kueue creates a Workload resource for every job that it manages. A Workload shows whether the job is admitted, pending, or suspended, and why.

Create a file named trainjob-xl.yaml — a copy of trainjob.yaml with the name kueue-trainjob-xl and resource requests that exceed the workshop-cq nominal quota of 8 CPU, for example cpu: "50" in resourcesPerNode:

sed -e 's/name: kueue-trainjob$/name: kueue-trainjob-xl/' \
    -e 's/cpu: "1"/cpu: "50"/' -e 's/memory: 2Gi/memory: 8Gi/' \
    trainjob.yaml > trainjob-xl.yaml

Apply the job:

oc apply -f trainjob-xl.yaml -n abc123-user1

List the Workloads:

oc get workloads -n abc123-user1

Expected output (abbreviated; the Workload names carry a generated suffix, so yours will differ):

NAME                              QUEUE         ADMITTED   FINISHED   AGE
trainjob-kueue-trainjob-9f4c2     workshop-lq   True       False      5m
trainjob-kueue-trainjob-xl-7b1d   workshop-lq   False      False      30s

The small job is admitted; the oversized job is not.

Diagnose why the oversized job is held from the console:

  1. In the OpenShift console, select your project from the Project list.

  2. Click Search, and from the Resources list, select Workload.

  3. Select the Workload resource that is created with the kueue-trainjob-xl job, and click the YAML tab.

  4. Check the text in the status.conditions.message field, which provides the reason for the pending state.

The message follows this pattern (example for a CPU quota shortage — the RHOAI documentation reports the same pattern for GPU shortages):

status:
  conditions:
  - lastTransitionTime: '2024-05-29T13:05:09Z'
    message: >-
      couldn't assign flavors to pod set node: insufficient quota
      for cpu in flavor default-flavor (requests 0 + 50 > maximum capacity 8)

While the workload is not admitted, the TrainJob stays suspended and no pods run: Kueue releases the JobSet’s pods only when the quota reservation succeeds.

Your console YAML view shows the same status.conditions structure as the example above; the message text in your cluster reflects its flavor names and quota numbers.

Verify

oc get workloads -n abc123-user1

The trainjob-kueue-trainjob-xl-<id> Workload shows ADMITTED False and its status.conditions.message explains the insufficient quota for cpu in flavor default-flavor in ClusterQueue.

Now that you have watched Kueue make scheduling decisions, you will monitor Kueue with alerts and the documented error messages.

Exercise 3: Monitor Kueue with alerts and error messages

Kueue ships alerting rules that each provide a link to a runbook with resolution instructions.

In the OpenShift console, in the Administrator perspective:

  1. Click Observe → Alerting.

  2. Click the Alerting rules tab to view a list of alerting rules for default and user-defined projects.

  3. Click the name of an alerting rule to see the condition that triggers it. The following table summarizes the alerting rules for Kueue resources.

Severity Name Alert condition

Critical

KueuePodDown

The Kueue pod is not ready for a period of 5 minutes.

Info

LowClusterQueueResourceUsage

Resource usage in the cluster queue is below 20% of its nominal quota for more than 1 day. Resource usage refers to any resources listed in the cluster queue, such as CPU, memory, and so on.

Info

ResourceReservationExceedsQuota

Resource reservation is 10 times the available quota in the cluster queue. Resource reservation refers to any resources listed in the cluster queue, such as CPU, memory, and so on.

Info

PendingWorkloadPods

A pod has been in a Pending state for more than 3 days.

If the Alert state of a rule is Firing, click Observe → Alerting and then the Alerts tab, open each alert for the firing rule, and in the Runbook section follow the linked runbook steps to identify the cause and resolve the situation.

When you troubleshoot queueing problems, these documented errors are the most common:

Error message

Cause

Resolution

Default Local Queue with kueue.x-k8s.io/default-queue: true annotation not found please create a default Local Queue or provide the local_queue name in Cluster Configuration.

No default local queue is defined, and a local queue is not specified in the cluster configuration.

In the console, select your project, click Search, and from the Resources list select LocalQueue. If a local queue exists, specify it in your configuration; if none exists, contact your administrator.

local_queue provided does not exist or is not in this namespace. Please provide the correct local_queue name in Cluster Configuration.

The specified local queue does not exist, or exists in a different namespace.

Check the spelling of the local queue name and that the namespace in your configuration matches your project.

failed calling webhook "mraycluster.kb.io" …​ no endpoints available for service "kueue-webhook-service"

The Kueue pod might not be running.

Check oc get pods -n openshift-kueue-operator, then contact your administrator.

Workload pods terminated before the image was pulled

Kueue waits 5 minutes by default before marking a workload as ready; a very large image that is still being pulled after that causes Kueue to fail the workload and terminate the pods.

Check the pod Events tab to see whether the image pull completed, then contact your administrator.

Verify

The alert’s Status changes from Firing to Resolved in Observe → Alerting → Alerts, and the alerting rule no longer lists a firing alert.

Clean up

Delete the training jobs and their workloads:

oc delete trainjob/kueue-trainjob -n abc123-user1
oc delete trainjob/kueue-trainjob-xl -n abc123-user1

Confirm that the Workloads are gone:

oc get workloads -n abc123-user1

The output shows No resources found in abc123-user1 namespace.

Module summary

What you accomplished:

  • Submitted a distributed PyTorch training job as a TrainJob to your LocalQueue and watched its pods run

  • Held a second job that exceeded the ClusterQueue quota and read the Workload conditions that explain why

  • Reviewed the Kueue alerting rules and the documented queueing error messages

Key takeaways:

  • The kueue.x-k8s.io/queue-name label routes a workload to a LocalQueue

  • On RHOAI 3.6, the TrainJob API (Kubeflow Trainer v2) submits distributed training; the referenced ClusterTrainingRuntime supplies the pinned training image

  • The Workload resource reports the admission decision, and its conditions explain held work

  • Kueue alerting rules fire with runbook links when queues or controller pods misbehave
