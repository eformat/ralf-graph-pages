Module 01: Getting Started with Guardrails and the AI Gateway

In this module you will learn how NeMo Guardrails enforcement attaches to the platform AI Gateway in Red Hat OpenShift AI 3.6, verify that the workshop cluster has the required pieces, and deploy a standalone NeMo Guardrails service with built-in detectors that you test yourself.

Learning objectives:

  • Explain how guardrail checks attach to the platform AI Gateway through the NemoGuardrails and AIGuardrail custom resources

  • Verify the guardrails prerequisites from the CLI

  • Deploy a standalone NeMo Guardrails service and test its input rails with /v1/guardrail/checks

How the integration works

The platform AI Gateway fronts model traffic for Red Hat OpenShift AI — requests from applications and agents, including tool-calling agents, flow through the gateway to the models behind it. The NeMo Guardrails integration in RHOAI 3.6 attaches guardrail enforcement to that gateway: unsafe content such as personally identifiable information (PII), secrets, and injection attempts is detected before traffic proceeds, without implementing guardrails in each application. Every caller that uses the gateway benefits from the same safety policy.

Two custom resources (CRs) cooperate to provide the enforcement:

  • NemoGuardrails — the provider. The TrustyAI operator reconciles this CR into a NeMo Guardrails server deployment, a service, a secured route, and a network policy. The CR carries the rails configuration: each entry in spec.nemoConfigs mounts one configuration, and its name is the configuration ID that attachments reference. There is no separate NemoConfig resource — the configurations are an inline list on the NemoGuardrails spec.

  • AIGuardrail — the attachment. This CR binds guardrail checks to the platform AI Gateway. Its spec.provider.nemo.ref points at a NemoGuardrails CR, and each entry in spec.checks selects one configuration by ID (configId) and a phase — Input evaluates the check on request content, Output on response content.

An attachment is accepted only after the gateway controller evaluates two gates, in order:

Gate Controlled by Requirement

Authorization

spec.allowedConsumers on the provider CR

The namespace of the AIGuardrail must be authorized to use the provider. The default is Same — only the provider’s own namespace.

Placement

spec.aiGatewayMode on the provider CR

The provider workload must run in an AI Gateway infrastructure namespace, where the gateway can discover its checks endpoint. With the default same-namespace placement, the gateway cannot bind the attachment.

When both gates pass and the provider workload is running, the gateway enforces the selected checks on traffic in the configured phases. You will observe each gate directly in Module 02: Hands-on Exercise.

Exercise 1: Verify the guardrails prerequisites

The platform AI Gateway and the TrustyAI component are external prerequisites that your workshop facilitator deployed. Verify that the pieces are in place before deploying a provider.

  1. Verify that the platform AI Gateway exists and is ready:

oc get aigateways

Expected output:

NAME                READY   VERSION
default-aigateway   True    1.27.3

  1. Verify that the TrustyAI component is managed and the NeMo Guardrails service is enabled:

oc get trustyai default-trustyai -o jsonpath='managementState={.spec.managementState} phase={.status.phase} nemoGuardrails={.spec.enabledServices.nemoGuardrails}{"\n"}'

Expected output:

managementState=Managed phase=Ready nemoGuardrails=true

  1. Verify that the guardrails CRDs are installed:

oc get crd nemoguardrails.trustyai.opendatahub.io aiguardrails.aigateway.opendatahub.io aigateways.components.platform.opendatahub.io

Each CRD is listed with its established version. If any command returns an error indicating the resource type is not found, ask your facilitator to complete the platform setup before continuing.

Verify

The oc get aigateways command shows default-aigateway with READY True, the TrustyAI component reports phase=Ready with nemoGuardrails=true, and all three CRDs are established. With the cluster prerequisites confirmed, the next step is to deploy a NeMo Guardrails provider whose rails you can test directly.

Exercise 2: Deploy a standalone NeMo Guardrails service

You can deploy NeMo Guardrails in a standalone mode without the full TrustyAI observability stack. In this exercise you deploy a provider with built-in detectors — Presidio sensitive data detection and regex pattern matching — that run entirely inside the NeMo Guardrails pod and require no external services or LLM calls.

  1. Create a file named nemo-ga-config.yaml holding the rails configuration:

apiVersion: v1
kind: ConfigMap
metadata:
  name: nemo-ga-config
  labels:
    app: nemo-ga-rails
data:
  config.yaml: |
    rails:
      config:
        sensitive_data_detection:
          input:
            entities:
              - EMAIL_ADDRESS
              - PERSON
              - PHONE_NUMBER
        regex_detection:
          input:
            patterns:
              - "\\b(password|secret|api[_-]?key|token)\\b"
              - "\\d{3}-\\d{2}-\\d{4}"
            case_insensitive: true
      input:
        flows:
          - detect sensitive data on input
          - regex check input

  1. Create a file named nemo-ga-rails.yaml holding the provider CR:

apiVersion: trustyai.opendatahub.io/v1alpha1
kind: NemoGuardrails
metadata:
  name: nemo-ga-rails
  annotations:
    security.opendatahub.io/enable-auth: 'true' <1>
spec:
  nemoConfigs:
    - name: pii-guardrails <2>
      configMaps:
        - nemo-ga-config <3>
      default: true <4>
  env:
    - name: OPENAI_API_KEY
      value: not-used <5>
1 security.opendatahub.io/enable-auth — Enables OpenShift AI authentication on the service route and publishes the internal status.endpoint field.
2 nemoConfigs[].name — The configuration ID. Attachments reference this value in spec.checks[].configId.
3 nemoConfigs[].configMaps — The ConfigMaps holding the rails configuration, mounted into the server.
4 nemoConfigs[].default — Marks this configuration as the one used when a request does not select one explicitly.
5 OPENAI_API_KEY — The built-in detectors used here need no LLM, so the value is unused; the variable satisfies the server’s environment expectations.

  1. Apply both files into your working project:

 
oc apply -f nemo-ga-config.yaml -n abc123-user1
oc apply -f nemo-ga-rails.yaml -n abc123-user1

  1. Wait for the CR to reconcile:

oc get nemoguardrails nemo-ga-rails -n abc123-user1 -w

Expected output:

NAME            PHASE   AGE
nemo-ga-rails   Ready   2m

Press Ctrl+C to exit the watch command.

If PHASE stays Progressing, inspect the CR conditions — Module 02: Troubleshooting attachment failures walks through the real failure modes, including pods that cannot schedule because the cluster is out of allocatable CPU.

  1. Set the guardrails route as an environment variable:

export GUARDRAILS_ROUTE=https://$(oc get routes/nemo-ga-rails -n abc123-user1 -o jsonpath='{.status.ingress[0].host}')
echo $GUARDRAILS_ROUTE

Verify

Test the service with safe content that should pass all rails:

curl -k -X POST $GUARDRAILS_ROUTE/v1/guardrail/checks \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -d '{
    "model": "test",
    "messages": [
      {"role": "user", "content": "What is the capital of France?"}
    ]
  }'

Expected output:

{
  "status": "success",
  "rails_status": {
    "detect sensitive data on input": {"status": "success"},
    "regex check input": {"status": "success"}
  }
}

Then trigger the Presidio detector with an email address:

curl -k -X POST $GUARDRAILS_ROUTE/v1/guardrail/checks \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -d '{
    "model": "test",
    "messages": [
      {"role": "user", "content": "Please contact me at alice@example.com"}
    ]
  }'

Expected output:

{
  "status": "blocked",
  "rails_status": {
    "detect sensitive data on input": {"status": "blocked"}
  },
  "guardrails_data": {
    "log": {
      "activated_rails": ["detect sensitive data on input"]
    }
  }
}

Finally, trigger the regex detector with a security keyword:

curl -k -X POST $GUARDRAILS_ROUTE/v1/guardrail/checks \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -d '{
    "model": "test",
    "messages": [
      {"role": "user", "content": "my password is hunter2 and my api_key is abc123"}
    ]
  }'

Expected output:

{
  "status": "blocked",
  "rails_status": {
    "regex check input": {"status": "blocked"}
  },
  "guardrails_data": {
    "log": {
      "activated_rails": ["regex check input"]
    }
  }
}

The status is blocked because the message tripped a configured rail, and guardrails_data.log.activated_rails names the rail that fired.

The /v1/guardrail/checks request and response schema follows the NeMo Guardrails server API documented in the upstream TrustyAI quickstart, and the public route accepts only /v1/* paths. If the server pod has not finished starting — for example, while the workshop cluster is short of allocatable CPU — the curl commands return connection errors. Re-run the verification once the pod is running, or ask your facilitator to share the captured output of the same probe.

You now have a working NeMo Guardrails provider whose rails behave as expected.

Module summary

What you accomplished:

  • Verified that the platform AI Gateway, the TrustyAI NeMo Guardrails service, and the guardrails CRDs are installed on the cluster

  • Deployed a standalone NeMo Guardrails provider with built-in Presidio and regex detectors

  • Blocked and allowed test messages using the /v1/guardrail/checks endpoint

Key takeaways:

  • The NemoGuardrails CR is the provider — the operator reconciles it into a server, service, route, and network policy

  • Each spec.nemoConfigs[].name is a configuration ID; attachments select configurations by that ID

  • Built-in detectors run inside the NeMo Guardrails pod and require no LLM calls

Next steps:

In the next module you attach this configuration to the platform AI Gateway with an AIGuardrail CR, and walk the authorization and placement gates that decide whether the gateway accepts the attachment.
