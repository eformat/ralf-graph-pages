Module 02: Hands-on Exercise

In this module you will work through the LoRA-aware routing tour end to end: you will inspect the routing layer that makes adapter-aware placement possible, verify the routing substrate behind a deployed llm-d model with oc, locate the platform’s LoRA routing strategy knob, and observe the request metrics that reveal how the scheduler places requests.

Learning objectives:

  • Recognize the routing-layer components and metrics that carry adapter identity

  • Verify the routing substrate of a deployed llm-d model — workload conditions, baseRefs, InferencePool, and gateway-accepted HTTPRoute

  • Locate the loraModelRoutingStrategy knob and determine which routing strategy your deployment’s route carries

Exercise 1: Explore the routing layer behind LoRA-aware routing

LoRA-aware placement happens inside the llm-d Endpoint Picker (EPP), the inference scheduler that processes every request for an LLMInferenceService deployment. The EPP exposes Prometheus metrics at the /metrics endpoint on the metrics service port, with the llm_d_epp_ prefix. The request metrics carry the labels you need to see adapter-aware routing:

Metric Labels What to observe

llm_d_epp_request_total

model_name, target_model_name, fairness_id, priority

Total requests processed by the scheduler; per-target counts show how traffic splits across adapters

llm_d_epp_request_ttft_seconds

model_name, target_model_name, fairness_id, priority

Time-to-first-token distribution; requests served by adapter-loaded pods should show lower TTFT

llm_d_epp_request_duration_seconds

model_name, target_model_name, fairness_id, priority

End-to-end request duration distribution

llm_d_epp_request_error_total

model_name, target_model_name, fairness_id, priority, error_code

Request errors by code; LoRA-aware fallback means requests still succeed when the adapter is not loaded

When your deployment routes adapter-targeted traffic, the target_model_name label distinguishes requests for each adapter from requests for the base model. If a request targets an adapter that no pod has loaded, LoRA-aware routing falls back to standard routing — the request completes through an ordinary pod instead of failing, and shows up in llm_d_epp_request_total without an adapter-warm placement.

The routing-group layer carries the same awareness: the controller partitions routing groups by model and LoRA adapter set, reporting GroupDegraded with reason MemberDivergence when members of a group serve different adapter sets. Members in different partitions continue to serve their own model at their own publisher path — readiness is not blocked.

Verify

You can name the label pair that distinguishes adapter-targeted requests, the metric that should drop for adapter-loaded pods, and the condition the controller sets when group members serve different adapter sets.

Now that you know which metrics carry adapter identity, you will verify the routing substrate behind the workshop’s deployed llm-d model and locate the platform knob that shapes how adapter identities are routed.

Exercise 2: Verify the routing substrate behind a deployed llm-d model

The llm-d deployment method in the model deployment wizard generates the whole routing substrate for you: an LLMInferenceService whose workload conditions tell you the stack is assembled, baseRefs that name the presets the service expands into, an InferencePool that groups the serving pods, an HTTPRoute published through the cluster gateway, and an Endpoint Picker (EPP) scheduler that owns placement decisions. In this exercise you inspect each layer with oc — the same substrate a LoRA-aware routing rollout extends.

  1. Reuse the workshop’s deployed llm-d model rather than deploying a second one: the cluster’s three worker nodes are already close to CPU capacity, and several other model deployments in the project sit Failed with Insufficient cpu. Start from the workload conditions of the LLMInferenceService:

    oc get llminferenceservice maas-llmd-demo -n abc123-user1 -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'

    Expected output shows the three workload conditions that matter for serving — RouterReady, SchedulerWorkloadReady, and MainWorkloadReady — alongside HTTPRoutesReady, InferencePoolReady, and WorkloadsReady, all True. The top-level Ready condition can read Unknown while platform validation settles (the live cluster reads Ready=Unknown, reason ValidationUnavailable, even though the serving path works — module 01 verified the API). The workload conditions are the signal to watch.

  2. Inspect how the service is wired into the routing layer. The baseRefs entries name the LLMInferenceServiceConfig presets the service expands into:

    oc get llminferenceservice maas-llmd-demo -n abc123-user1 -o yaml | grep -A 4 baseRefs

    Expected output shows the single preset reference behind this deployment — the CPU workload template from the platform preset list you saw in module 01:

    spec:
  baseRefs:
  - name: v3-6-0-kserve-config-llm-template-cpu

    The model section of the same output shows where the weights come from: this deployment references a ModelCar OCI URI directly (oci://quay.io/redhat-ai-services/modelcar-catalog:qwen2.5-0.5b-instruct).

  3. Verify the route that publishes the service. The generated HTTPRoute attaches to the cluster gateway and sends traffic to the inference pool:

    oc get httproute maas-llmd-demo-kserve-route -n abc123-user1 -o jsonpath='{range .status.parents[*]}{.parentRef.name}{"\t"}{range .conditions[*]}{.type}={.status}{" "}{end}{"\n"}{end}'

    Expected output shows the maas-default-gateway parent with Accepted=True and ResolvedRefs=True, plus Kuadrant auth and rate-limit policy conditions on the same parent. Now check what the route matches on and where it sends traffic, and how the pool connects the route to the scheduler:

    oc get httproute maas-llmd-demo-kserve-route -n abc123-user1 -o jsonpath='{.spec.rules[0].matches}{"\n"}{.spec.rules[0].backendRefs}{"\n"}'
oc get inferencepool maas-llmd-demo-inference-pool -n abc123-user1 -o jsonpath='{.spec.endpointPickerRef}{"\n"}{.spec.targetPorts}{"\n"}'

    Expected output: the route’s only match is a path prefix (/abc123-user1/maas-llmd-demo/v1) and its backend is InferencePool maas-llmd-demo-inference-pool on port 8000; the pool points at the Endpoint Picker service (maas-llmd-demo-epp-service, port 9002, failure mode FailOpen) and targets the model servers on port 8000.

  4. Inspect the scheduler that owns placement. The service carries the Endpoint Picker configuration inline, and the deployed scheduler process adds a metrics source to it:

    oc get llminferenceservice maas-llmd-demo -n abc123-user1 -o jsonpath='{.spec.router.scheduler.config.inline}'
oc get deploy maas-llmd-demo-kserve-router-scheduler -n abc123-user1 -o jsonpath='{.spec.template.spec.containers[0].args[1]}'

    Expected output: an EndpointPickerConfig (apiVersion llm-d.ai/v1alpha1) with the flowControl feature gate, a utilization-detector plugin (kvCacheUtilThreshold: 0.8, queueDepthThreshold: 5, metricsStalenessThreshold: 200ms) wired as the saturation detector, and — in the deployed scheduler’s --config-text — a metrics-data-source plugin fetching pod metrics over https. There is no adapter-aware plugin in the default preset: the placement signals are cache utilization, queue depth, and metrics freshness.

  5. Locate the platform’s LoRA-aware routing knob. The KServe inferenceservice-config configmap documents loraModelRoutingStrategy — the setting that selects how LLMInferenceService LoRA adapter expansion represents model identities in generated HTTPRoutes:

    oc get cm inferenceservice-config -n redhat-ods-applications -o yaml | grep -B4 -A12 loraModelRoutingStrategy

    Expected output shows the strategy documentation: the default exact generates one Exact header match per adapter identity; regex collapses the base model and all adapters into a single anchored RegularExpression header match. A service pins its own value with the annotation serving.kserve.io/lora-model-routing-strategy; without the pin, a change reaches every LoRA service on its next reconcile. The documentation also names the practical ceilings: Envoy binds at the 4096-character header value limit (roughly 70 adapters), Istio allows a 32768 program size, and a rejected pattern surfaces as an xDS NACK in the gateway controller’s logs — not on the HTTPRoute.

  6. Determine which strategy your deployment’s route actually carries. This cluster’s active generated ingress configuration renders loraModelRoutingStrategy: regex, so a LoRA-enabled service here would expand base model plus adapters into one anchored RegularExpression header match. The workshop’s model serves the base model only — no adapters are deployed — so its route carries no header matches at all: routing is by path prefix, which you saw in step 3. Confirm that honestly:

    oc get httproute maas-llmd-demo-kserve-route -n abc123-user1 -o jsonpath='{.spec.rules[0].matches}{"\n"}'

    Expected output: a single PathPrefix match — no Exact and no RegularExpression header matches, because a base-model route has nothing to expand. The strategy choice becomes visible in the route only once adapters exist; that expansion is what the knob documents and what this workshop does not exercise.

Advanced: enabling LoRA on vLLM — not exercised in this environment. The steps above inspect the routing substrate and the strategy knob; they do not enable adapters. An operator with cluster capacity would add --enable-lora and --lora-modules to the vLLM runtime through the VLLM_ADDITIONAL_ARGS environment variable; each adapter identity then expands into the generated HTTPRoute according to the active loraModelRoutingStrategy — one Exact header match per identity under exact, one anchored regex under regex. This workshop does not exercise that path: the cluster’s three worker nodes are already saturated (several model deployments sit Failed with Insufficient cpu), and patching adapter flags onto the serving stack risks the one healthy serving path this workshop uses. Treat the knob inspection as the hands-on surface for this Developer Preview feature.

Verify

  • The LLMInferenceService workload conditions (RouterReady, SchedulerWorkloadReady, MainWorkloadReady) read True, and baseRefs names the preset the service expands into.

  • The generated HTTPRoute is accepted by maas-default-gateway, its only backend is the inference pool, and the pool points at the Endpoint Picker service.

  • You located loraModelRoutingStrategy in the inferenceservice-config configmap, can state the difference between exact and regex, and verified the workshop’s route carries a plain path-prefix match because no adapters are deployed.

  • You read the not exercised here callout and can describe how an operator with capacity would enable adapters on vLLM.

Now that the substrate is verified, you will send inference requests and observe the routing metrics.

Exercise 3: Observe request routing metrics

With a deployed model serving requests, the EPP request metrics let you see how the scheduler places requests — even in a workshop without multiple adapters, the same metrics show how requests flow and how warm pods answer faster.

  1. Send the same conversational request several times so the base model warms up on a pod. Copy the Inference endpoint URL from your model details page, then send the request. The workshop’s MaaS gateway enforces Kuadrant authentication, so every request must carry a Bearer token — paste your gateway API key into the TOKEN placeholder below; unauthenticated requests are rejected with HTTP 401 before they reach the model. The Make authenticated inference requests chapter of the llm-d documentation describes the same Authorization-header pattern:

    INFER_URL=$(oc get llminferenceservice maas-llmd-demo -n abc123-user1 -o jsonpath='{.status.url}')
MODEL_NAME=maas-llmd-demo
TOKEN=
curl -k $INFER_URL/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "'"$MODEL_NAME"'",
    "messages": [{
      "role": "user",
      "content": "What is Red Hat OpenShift AI?"
    }]
  }'

    The INFER_URL capture resolves to the same Inference endpoint URL shown on your model details page — the workshop’s maas-llmd-demo deployment. A successful response returns HTTP 200 with a JSON body containing a choices array whose entries carry the generated message.content reply and a model field echoing the deployed model name. MODEL_NAME is set to the name the workshop’s deployed model serves — maas-llmd-demo (the deployment also answers to publishers/abc123-user1/models/maas-llmd-demo). A model value that is not a served name, such as the upstream repository id, fails with HTTP 404 NotFoundError, and a request with a missing or invalid token is rejected by the gateway with HTTP 401 before it reaches the model. Repeat the request three or four times without changing the message.

  2. Observe the request metrics while the requests are processed. The EPP publishes its metrics on a token-protected https endpoint; in this cluster the scheduler’s ServiceMonitor scrapes it into user-workload monitoring and prefixes every metric name with kserve_ (adding exported_namespace, llm_isvc_name, and llm_isvc_component labels on the way). In the console, open Observe > Metrics and query {name=~"kserve_llm_d_epp.*"} — look for kserve_llm_d_epp_request_ttft_seconds and kserve_llm_d_epp_request_total (the same series carry the llm_d_epp_ prefix at the source).

  3. Interpret what you see: the first requests after a cold start pay warm-up latency — the same effect adapter swaps cause in multi-adapter deployments — and repeated requests should settle into a lower TTFT as the serving pod warms up. Requests that cannot find an adapter-matched pod fall back to standard routing and still complete, so no requests fail purely because of routing.

vLLM parameters on the LLMInferenceService shape warm-up behavior the same way they shape adapter cold-load latency: --gpu-memory-utilization controls GPU memory available for caches (0.6-0.7 for latency-sensitive workloads, 0.85-0.9 for throughput-optimized workloads). Adjust these only if you need to tune the behavior.

Which metrics are scraped into your cluster’s monitoring stack depends on your workshop configuration. In this environment the maas-llmd-demo-kserve-llm-isvc-scheduler ServiceMonitor handles the scrape — query the kserve_-prefixed series in the console’s Observe section. If they are not visible, ask your facilitator how to reach the EPP metrics service in your environment.

Verify

You sent repeated requests and observed at least one of the llm_d_epp_ request metrics (or its kserve_-prefixed series in the monitoring stack) — total request counts and the TTFT distribution are the two that respond immediately.

Module summary

What you accomplished:

  • Inspected the EPP request metrics that carry model_name and target_model_name adapter identity

  • Verified the routing substrate behind a deployed llm-d model — workload conditions, baseRefs, gateway-accepted HTTPRoute, inference pool, and the inline Endpoint Picker configuration

  • Located the loraModelRoutingStrategy knob and determined that the workshop’s base-model route carries a plain path-prefix match

Key takeaways:

  • target_model_name is the label that exposes adapter-targeted routing in the request metrics

  • loraModelRoutingStrategy — exact versus regex — is a platform-level knob; a service pins its own value with the serving.kserve.io/lora-model-routing-strategy annotation

  • LoRA-aware routing changes placement, not availability — fallback keeps requests completing
