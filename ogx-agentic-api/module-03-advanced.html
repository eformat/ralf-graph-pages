Module 03: Advanced APIs — what runs on this build

In this module you will survey the advanced side of the OGX agentic surface — grounding answers with file_search, citation annotations, guardrails, rerank, connectors, and the Tool Runtime — and learn which parts of that surface actually run on the workshop build, which are registered but degraded, and which are target-state only. Every claim in this module was verified against the workshop OGX server, and every exercise below either runs successfully or reproduces a documented, exact error signature.

Learning objectives:

  • Inspect what a live OGX build actually exposes: providers, the published OpenAPI path list, the internal route table, and the connectors registry

  • Construct requests against the native rerank API and interpret its error signatures

  • Explain the file_search grounding workflow and file_citation annotations as target-state design, and reproduce the exact gates that block them on this build

  • Explain the fail-closed guardrails design for the Responses API as concept reading

  • Distinguish the Tool Runtime API (target-state) from the tool-related routes that are registered on this build, with their observed statuses

This feature is a Technology Preview. Support levels within the API surface differ — some APIs are listed at higher support levels in the 3.6 docs, while Conversations, Tool Runtime, and Vector_IO are Technology Preview or Developer Preview. On this Technology Preview build (OGX 1.4.2+rhaiv.0), availability differs further still from the documented target state: see the build-availability matrix in Module 01. Endpoints and parameters shown here may change between releases.

All exercises use the workshop’s shared OGX server. If you have not already, set the endpoint from Module 02:

export OGX_URL="https://aml-ogx-tls-autorag-ml-demo.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com"

Exercise 1: Inspect what your OGX build actually exposes

Before writing code against an OGX server, find out what it really exposes. There are three different views of an OGX build — the published OpenAPI specification, the internal route table, and actual runtime behavior — and on this build they disagree. This exercise teaches you to check all three.

  1. Confirm you are talking to the workshop build:

curl -s "$OGX_URL/v1/version"

Expected output:

{"version":"1.4.2+rhaiv.0"}

  1. Fetch the published OpenAPI specification and count the registered paths:

curl -s "$OGX_URL/openapi.json" | python3 -c 'import json,sys; print(len(json.load(sys.stdin)["paths"]))'

Expected output:

43

  1. List the providers configured on the server:

curl -s "$OGX_URL/v1alpha/admin/providers" | python3 -m json.tool

On the workshop server you should see three providers: vllm-inference and vllm-embedding (both remote::vllm, pointing at the Llama 3.2 3B and BGE-M3 vLLM services), and pgvector (remote::pgvector) backing vector storage.

  1. Inspect the internal route table:

curl -s "$OGX_URL/v1alpha/admin/inspect/routes" | python3 -m json.tool | head -40
Compare the internal route table with the published OpenAPI spec. On this build /v1/responses* routes appear in the internal table yet return 404 in practice, and the /v1alpha/admin/connectors and /v1alpha/admin/tools routes are missing from the table yet still answer. Neither the OpenAPI spec nor the route table alone is an availability guarantee — only a live request tells the truth.

  1. List the connector registry:

curl -s "$OGX_URL/v1alpha/admin/connectors"

Expected output:

{"data":[]}

The registry is empty on the workshop server. Note what happens when you request a connector that does not exist — the read path works and returns a well-formed error:

curl -s "$OGX_URL/v1alpha/admin/connectors/demo-mcp-01"

Expected output:

{"error":{"message":"Connector 'demo-mcp-01' not found. Use 'client.connectors.list()' to list available Connectors."}}

Verify

  • GET /v1/version returns 1.4.2+rhaiv.0.

  • The OpenAPI spec publishes exactly 43 paths on this build.

  • GET /v1alpha/admin/providers lists three providers, including pgvector.

  • GET /v1alpha/admin/inspect/routes returns the internal route table, and you can find at least one route that behaves differently in practice (for example /v1/responses).

  • GET /v1alpha/admin/connectors returns an empty registry, and the GET-by-id path returns the structured Connector …​ not found error for an unknown id.

With the survey complete, every exercise that follows either runs against a live route or reproduces an exact error signature — starting with the native rerank API.

Exercise 2: The rerank API — request shape and error signatures

The native rerank API (/v1alpha/inference/rerank) re-orders a list of candidate documents by relevance to a query. Its request schema requires model, query, and items — an array of candidate strings (the field is items, not documents as in some other rerank APIs — using the wrong field name is itself a useful error to see). An optional max_num_results caps the number of returned pairs. A successful call returns {"data":[{"index":…​,"relevance_score":…​}]}, sorted by score descending.

On the workshop build the route and its validation stack are fully alive, but no rerank-typed model exists, so every well-formed request is rejected. This exercise teaches you the request shape and the exact error signatures, so you can distinguish a client bug from a build limitation — and be ready when a build ships a rerank-typed model.

  1. Send a request with the wrong field name (documents instead of items) and observe the validation error:

curl -s -X POST "$OGX_URL/v1alpha/inference/rerank" \
  -H "Content-Type: application/json" \
  -d '{"model":"vllm-inference/aml-llama32-3b","query":"refund window","documents":["a","b"]}'

Expected output — the validator names the missing field:

{"error":{"message":"{'errors': [{'loc': ['body', 'items'], 'msg': 'Field required', 'type': 'missing'}]}"}}

  1. Now send a schema-correct request with items:

curl -s -X POST "$OGX_URL/v1alpha/inference/rerank" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "vllm-inference/aml-llama32-3b",
    "query": "What is the refund window?",
    "items": [
      "Returns are accepted within 30 days of purchase.",
      "The meeting starts at 10am in the main conference room.",
      "Support tickets are answered within 24 hours."
    ],
    "max_num_results": 2
  }'

Expected output — the model-typing gate:

{"error":{"message":"Model 'vllm-inference/aml-llama32-3b' is of type 'llm' rather than the expected type 'rerank'"}}

The same 400 occurs with the second workshop model (vllm-embedding/aml-bge-m3, itself mis-typed as llm — see Module 01). The root cause is model typing: the server has no model typed rerank, and neither configured model can serve the route.

On this build the rerank API cannot return relevance scores. What you can verify — and what the exercises above prove — is that the route is registered, the request schema is enforced (items, not documents), and the failure mode is a precise, machine-readable error rather than a silent success. On a build with a rerank-typed model, the identical request returns the {"data":[{"index":…​,"relevance_score":…​}]} body described above.

Verify

  • The documents-field request returns a 400 whose message names body.items as missing — proof that the route and its validation are live.

  • The schema-correct request returns 400 with the exact message Model '…​' is of type 'llm' rather than the expected type 'rerank'.

  • You can state the required request fields (model, query, items) and the response shape (data sorted by relevance_score descending) for a future build.

From rerank’s registered-but-degraded route, the next exercise turns to the file_search grounding workflow — fully gated on this build and taught as reference design for a future one.

Exercise 3: Ground answers with file_search and citations (reference for a future build)

Not runnable on OGX 1.4.2+rhaiv.0. Two independent gates block this workflow on the workshop build:

  • POST /v1/vector_stores returns 400 with {"error":{"message":"Model 'None' not found. Use 'client.models.list()' to list available Models."}} — vector-store creation cannot resolve an embedding model (the request schema has no embedding-model override, and both configured models are typed llm).

  • GET /v1/models reports the workshop’s embedding service vllm-embedding/aml-bge-m3 with custom_metadata.model_type: "llm", so /v1/embeddings rejects it and no embeddings can be computed.

The workflow additionally requires the Responses and Files APIs, which are absent on this build (POST /v1/responses returns 404; enabling apis.responses or apis.files in the base config crash-loops the server — see Module 01). Treat the remainder of this exercise as reference material for a future build with an embedding-typed model; do not expect it to run here.

The workflow has four stages: upload a file to the Files API, create a vector store, index the file into the store, then query through the Responses API with the file_search tool. In a notebook cell against a future build that ships these APIs, the flow looks like this:

# 1. Upload the file to the Files API
with open("your-document.pdf", "rb") as f:
    file_info = client.files.create(file=("your-document.pdf", f), purpose="assistants")

# 2. Create a vector store backed by an embedding-typed model
vector_store = client.vector_stores.create(
    name="test_vector_store",
    extra_body={
        "embedding_model": embedding_model_id,
        "embedding_dimension": embedding_dimension,
        "provider_id": "pgvector",
    },
)

# 3. Add the uploaded file to the store; indexing is asynchronous
client.vector_stores.files.create(
    vector_store_id=vector_store.id,
    file_id=file_info.id,
    chunking_strategy={
        "type": "static",
        "static": {"max_chunk_size_tokens": 700, "chunk_overlap_tokens": 100},
    },
)

# 4. Query through the Responses API with the file_search tool
response = client.responses.create(
    model=model_id,
    input="Ask a question that is answered by your uploaded document",
    tools=[{"type": "file_search", "vector_store_ids": [vector_store.id]}],
)
print(response.output_text)

When you include the file_search tool with vector_store_ids, OGX retrieves relevant chunks from the specified vector store and provides them to the model as context. The response carries OpenAI-compatible file_citation annotations so applications can trace any statement back to its source document:

annotations = response.output[0].content[0].annotations
print(annotations)

Expected shape on a future build:

[
  {
    "type": "file_citation",
    "file_id": "file-57610eaac6364459bfefae60377837b7",
    "filename": "your-document.pdf",
    "index": 139
  }
]

Each file_citation identifies the source file by file_id and filename, plus the index of the cited position. Annotations are enabled by default and returned only through the Responses API with the file_search tool. Their accuracy depends on the underlying model — smaller models can produce less precise attributions even when retrieval works correctly.

Verify

On this build you verify the gate, not the workflow:

  • GET /v1/vector_stores returns 200 with an empty list — no vector store exists on the server.

  • A minimal create attempt reproduces the documented signature:

curl -s -X POST "$OGX_URL/v1/vector_stores" -H "Content-Type: application/json" -d '{"name":"probe"}'

Expected output:

{"error":{"message":"Model 'None' not found. Use 'client.models.list()' to list available Models."}}

  • You can name the four stages of the grounding workflow (upload, create store, index, query with file_search) and state where file_citation annotations appear in the response.

With the grounding gates mapped, the next exercise shifts to design reading: the fail-closed guardrails enforced inside the Responses API.

Exercise 4: Responses API guardrails (concept reading)

Not demonstrable on OGX 1.4.2+rhaiv.0. Guardrails are enforced inside the Responses API, and POST /v1/responses returns 404 on this build — the route is absent from the published OpenAPI spec, and enabling apis.responses in the base config crash-loops the server. The design below is worth reading because it shapes how OGX handles content moderation, but you cannot exercise it on the workshop server.

OGX’s built-in guardrails use a moderation_endpoint configuration pointing at any OpenAI-compatible /v1/moderations endpoint. The configuration lives on the responses provider, not at the CRD level, and is set by the platform administrator. Clients opt in per-request by setting guardrails: true on the Responses API request:

curl -s -X POST "$OGX_URL/v1/responses" \
  -H "Content-Type: application/json" \
  -d '{"model": "<model-id>", "input": "test moderation", "guardrails": true}'

The guardrails check is designed to fail closed: any error blocks content rather than allowing it through. HTTP errors or timeouts block content with a "moderation service unavailable" error; an invalid JSON response blocks with an "invalid response" error; a missing or malformed results array blocks with an "unexpected format" error; and any result flagged true blocks content with the flagged category names. Only when no errors occur and no result is flagged does content pass.

If guardrails is set to true but no moderation_endpoint is configured on the responses provider, the server returns a 400 error instructing the client to contact their platform administrator.
The moderation endpoint connection uses the system certificate authority (CA) trust store or the CA bundle configured via spec.tls.trust.caCertificates. Authentication is handled via moderation_headers, which are server-side only and never exposed to clients.

For production deployments, the recommended guardrails path is the RHOAI NeMo Guardrails integration, managed through the NemoGuardrails CRD (trustyai.opendatahub.io/v1alpha1) and the MCPGuardrailsMode toggle on the TrustyAI component spec.

Verify

On this build you verify the absence and the design:

  • POST /v1/responses with any JSON body returns 404 on this build.

  • You can explain the fail-closed principle: every moderation error path (unavailable service, invalid JSON, malformed results, flagged category) blocks content instead of passing it.

Exercise 5: Tool Runtime — target-state versus registered routes

The Tool Runtime API is the native OGX API that lets a model dynamically call a tool at runtime, with tool groups managed by the server. On OGX 1.4.2+rhaiv.0 it is target-state: there is no /v1/tool-runtime endpoint to call. The route is absent from the published OpenAPI spec (43 paths), and a live request confirms it:

curl -s "$OGX_URL/v1/tool-runtime"

Expected output:

{"detail":"Not Found"}

What is registered on this build is a set of tool-adjacent administrative routes. The table below lists every tool-related route in the OpenAPI spec and its observed status on the workshop server:

/v1alpha/admin/connectors

GET

200 {"data":[]} — works (read-only)

Empty connector registry; the read path is functional

/v1alpha/admin/connectors/{id}

GET

404 with a structured error for unknown ids — works

There is no way to create a connector over HTTP (see below)

/v1alpha/admin/connectors/{id}/tools

GET

Registered but untestable

No connector can be created on this build, so the sub-resource cannot be populated

/v1/admin/tools

GET

500 — internal server error

Documented in the OpenAPI spec (ListToolDefsResponse) but broken on this build; even read-only tool listing fails

/v1/tools

GET

404 — not registered

/v1/tool-runtime

—

Absent

Not in the OpenAPI spec; GET returns 404. The API the docs describe is target-state on this build

Connectors cannot be registered through the API on this build — connector creation is config-side only, declared in the OGXServer configuration by the platform administrator:

curl -s -X POST "$OGX_URL/v1alpha/admin/connectors" \
  -H "Content-Type: application/json" \
  -d '{"connector_id":"demo-mcp-01","url":"https://example.com/mcp","connector_type":"mcp","server_label":"demo-mcp"}'

Expected output:

{"detail":"Method Not Allowed"}

As with other native OGX APIs, which APIs are enabled is defined by the run.yaml file shipped with the distribution; platform administrators can supply a custom run.yaml to enable advanced workflows or integrate additional providers.

The 3.6 docs do not include a worked client example for the Tool Runtime API. Treat this exercise as an honest survey: the Tool Runtime itself is target-state on this build, and the registered tool routes are limited to read-only (or broken) administrative surfaces.

Verify

  • GET /v1/tool-runtime returns 404 and /v1/tool-runtime is absent from curl -s "$OGX_URL/openapi.json" | python3 -c 'import json,sys; print("\n".join(json.load(sys.stdin)["paths"]))'.

  • GET /v1alpha/admin/connectors returns 200 {"data":[]} and the POST create attempt returns 405 Method Not Allowed.

  • GET /v1/admin/tools returns 500 on this build.

  • You can name the two tool-related routes that are registered and read-only (/v1alpha/admin/connectors list and get-by-id).

Module summary

What you accomplished:

  • Inspected the live OGX build three ways — OpenAPI spec (43 paths), internal route table, and runtime behavior — and saw why only live requests are an availability guarantee

  • Exercised the native rerank API’s request schema and reproduced its documented error signatures (validation 400, model-typing 400)

  • Reproduced the exact gates that block the file_search grounding workflow on this build and studied the full upload → store → file_search → citations flow as reference design

  • Read the fail-closed guardrails design for the Responses API as concept reading

  • Mapped the Tool Runtime API as target-state and audited every registered tool-related route

Key takeaways:

  • Registration is not availability: /v1/responses routes appear in the internal route table yet return 404, while /v1alpha/admin/* routes answer without appearing in it

  • Error signatures are documentation — a 400 that names the expected model type or request field tells you precisely which layer rejected you (validation, model typing, or upstream resource)

  • Model typing gates several surfaces on this build: no rerank-typed model, and the embedding service is typed llm, which cascades into vector stores, vector-io, and rerank

  • The grounding (file_search + file_citation) and guardrails designs are target-state worth knowing — see the build-availability matrix in Module 01 for what a future build must ship
