Module 02: Responses and Conversations hands-on

In this module you will connect an OpenAI SDK client to the workshop’s shared OGX server, sanity-check inference with Chat Completions, and build a stateful, multi-turn chat with the Conversations API. You deploy nothing yourself: the guided path consumes the workshop’s shared OGXServer over HTTPS, and every step runs against that live server.

Learning objectives:

  • Connect to the shared workshop OGX server and verify it is healthy and at version 1.4.2+rhaiv.0

  • Configure an OpenAI SDK client against the OGX route and select a large language model (LLM) by model_type

  • Sanity-check inference with Chat Completions

  • Persist conversation items in the OpenAI array-wrapped shape and drive multi-turn context explicitly through Chat Completions

  • Recognize the surfaces that silently no-op or are absent on this build: flat item bodies, the conversation parameter on Chat Completions, and the Responses API

This feature is a Technology Preview. While the Conversations API is functional and suitable for evaluation, some endpoints and parameters might change in future releases. It is not recommended for production use. On the workshop build (OGX 1.4.2+rhaiv.0), availability differs further still from the documented target state — see the build-availability matrix in Module 01.

Exercise 1: Connect to the workshop OGX server

The guided path uses the workshop’s shared OGX server: OGXServer aml-ogx in the autorag-ml-demo project, exposed through an HTTPS route. It is already deployed and in the Ready phase, so there is no oc apply step in this module — you only verify it and connect.

Running your own OGXServer. Everything in this module works against any reachable OGXServer. If you want to stage your own for a self-hosted or air-gapped run, see the optional appendix in the feature tree at deploy/README.md ("Running your own OGXServer") for an example OGXServer custom resource and its prerequisites. The shared workshop server is used everywhere else in this module.

  1. Export the workshop OGX route:

export OGX_URL="https://aml-ogx-tls-autorag-ml-demo.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com"

  1. Check that the server is healthy:

curl -s "$OGX_URL/v1/health"

Expected output:

{"status":"OK"}

  1. Check the OGX version:

curl -s "$OGX_URL/v1/version"

Expected output:

{"version":"1.4.2+rhaiv.0"}

  1. List the models registered on the server:

curl -s "$OGX_URL/v1/models"

Expected output (abridged):

{"object":"list","data":[
  {"id":"vllm-inference/aml-llama32-3b", ...,
   "custom_metadata":{"model_type":"llm","provider_id":"vllm-inference",...}},
  {"id":"vllm-embedding/aml-bge-m3", ...,
   "custom_metadata":{"model_type":"llm","provider_id":"vllm-embedding",...}}]}

  1. In your workbench notebook or local Python environment, install the client libraries:

pip install -q openai rich

  1. Configure an OpenAI SDK client pointing at the workshop OGX route. The base_url must include the /v1 path suffix so the SDK routes requests to the OpenAI-compatible surface:

from openai import OpenAI
import rich

# The workshop OGX server exposes an OpenAI-compatible API on its route.
# The base_url must include the /v1 path suffix when using the OpenAI SDK.
OGX_URL = "https://aml-ogx-tls-autorag-ml-demo.apps.ocp5-m6wl4-2plgg.sandbox1832.opentlc.com"
client = OpenAI(
    api_key="not-needed",
    base_url=f"{OGX_URL}/v1"
)

  1. List the models through the SDK and select the first LLM:

models = client.models.list()
rich.print(models)

model_id = next(m for m in models if m.custom_metadata["model_type"] == "llm").id
On this build both registered models report model_type: "llm" — the embedding model vllm-embedding/aml-bge-m3 is mis-typed, which is why embeddings are unusable on this server (see Module 01). The selection pattern picks the first llm-typed model, which on this server is vllm-inference/aml-llama32-3b, the model the workshop uses for generation. If you prefer to be explicit, set model_id = "vllm-inference/aml-llama32-3b" directly.

Verify

  • curl -s "$OGX_URL/v1/health" prints {"status":"OK"}.

  • curl -s "$OGX_URL/v1/version" prints {"version":"1.4.2+rhaiv.0"}.

  • curl -s "$OGX_URL/v1/models" lists vllm-inference/aml-llama32-3b and vllm-embedding/aml-bge-m3, both with custom_metadata.model_type of llm.

  • model_id is assigned without raising StopIteration and equals vllm-inference/aml-llama32-3b.

With the client connected, you can now sanity-check inference before layering on the agentic APIs.

Exercise 2: Sanity-check inference with Chat Completions

Before using the agentic APIs, confirm the inference path works with a simple Chat Completions call against the shared server.

response = client.chat.completions.create(
    model=model_id,
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "What is the capital of France?"},
    ],
    temperature=0,
)
# Optional verification check
assert len(response.choices) > 0, "No response after basic inference on ogx server"
content = response.choices[0].message.content
rich.print(content)

Verify

  • The assert does not raise, meaning at least one choice was returned.

  • The printed content answers Paris.

Inference is confirmed. Now you will use the Conversations API to build a multi-turn chat with server-side state.

Exercise 3: Build a stateful conversation with the Conversations API

The Conversations API manages server-side conversation state: you create a conversation, store messages in it as conversation items, and build multi-turn context from that stored history.

Responses API: not available on OGX 1.4.2+rhaiv.0. POST /v1/responses returns 404, and enabling apis.responses in the base config crash-loops the server (KeyError: Api.responses). Earlier versions of this module drove multi-turn state through the Responses API — that flow cannot run on this build. See Module 01 for the build-availability matrix.

  1. Create a conversation:

# Step 1: Create a conversation
conversation = client.conversations.create(
    metadata={"topic": "pet-care", "user": "demo-user"}
)
conversation_id = conversation.id
rich.print(conversation)

  1. Add a conversation item. The body must use the OpenAI array-wrapped item shape:

# Step 2: Store the first user message as a conversation item
client.conversations.items.create(
    conversation_id=conversation_id,
    items=[
        {
            "type": "message",
            "role": "user",
            "content": [
                {"type": "input_text",
                 "text": "I have a rabbit. What is its living quarters called?"}
            ],
        }
    ],
)
On this build, only the array-wrapped shape shown above persists items. A body with items in any other form — a flat {"role": …​, "content": …​} object, items given as a single object instead of an array, or array entries that are not typed message objects — returns HTTP 200 with the conversation object while storing nothing: a follow-up items list comes back empty. The failure is silent, so always list the items back after adding them.

  1. List the stored items to confirm they persisted, in ascending order:

# Step 3: List all messages in the conversation
items = client.conversations.items.list(conversation_id, order="asc")
for item in items.data:
    print(f"{item.role}: {item.content[0].text}")

  1. Drive the conversation by passing the stored history explicitly to Chat Completions. Turn 1 uses the stored rabbit question; turn 2 then relies on that history to answer a follow-up about a second pet:

# Step 4: Multi-turn context via Chat Completions with explicit history
def history_from(conversation_id):
    items = client.conversations.items.list(conversation_id, order="asc")
    messages = [{"role": "system",
                 "content": "You are a helpful assistant. Keep responses brief."}]
    messages += [{"role": item.role, "content": item.content[0].text}
                 for item in items.data]
    return messages

# Turn 1: the model sees the rabbit question from the stored history
reply1 = client.chat.completions.create(
    model=model_id, messages=history_from(conversation_id), temperature=0
)
answer1 = reply1.choices[0].message.content
print(answer1)

# Store the assistant reply so later turns see it too
client.conversations.items.create(
    conversation_id=conversation_id,
    items=[
        {
            "type": "message",
            "role": "assistant",
            "content": [{"type": "input_text", "text": answer1}],
        }
    ],
)

# Turn 2: store the follow-up, then ask again with the full stored history
client.conversations.items.create(
    conversation_id=conversation_id,
    items=[
        {
            "type": "message",
            "role": "user",
            "content": [
                {"type": "input_text",
                 "text": "I also have a dog. What are its living quarters called?"}
            ],
        }
    ],
)
reply2 = client.chat.completions.create(
    model=model_id, messages=history_from(conversation_id), temperature=0
)
print(reply2.choices[0].message.content)
The Responses-era pattern of passing conversation=<id> to Chat Completions and letting the server attach turns to the stored history does not work on this build: the raw Representational State Transfer (REST) call returns 200 but persists nothing to the conversation, and the current OpenAI SDK does not expose the parameter on chat.completions.create. Passing the history explicitly, as shown above, is the reliable pattern on OGX 1.4.2+rhaiv.0.

You can also drive the conversation REST endpoints directly. The Conversations API exposes POST /v1/conversations, GET /v1/conversations/{id}, POST /v1/conversations/{id}/items (add items), and DELETE /v1/conversations/{id}. A top-level POST /v1/conversations/{id} also exists, but on this build it rejects the array-wrapped body with a 422 demanding a metadata field — it is not the items persistence path. Items persist only when POSTed in the array-wrapped shape to the /items subpath. The conversation_id variable from the Python cells above lives in a different scope from your shell, so export the conv_…​ id from the Step 1 create response first:

# paste the conv_... id printed by Step 1's create response
export CONVERSATION_ID=conv_xxxxxxxxxxxxxxxx

curl -s -X POST "$OGX_URL/v1/conversations/$CONVERSATION_ID/items" \
  -H "Content-Type: application/json" \
  -d '{"items":[{"type":"message","role":"user","content":[{"type":"input_text","text":"I have a rabbit. What is its living quarters called?"}]}]}'
Deleting a conversation removes the conversation and its full history. This cannot be undone.

  1. Clean up the conversation when you are done:

# Step 5: Clean up
client.conversations.delete(conversation_id)

Verify

  • conversations.items.list(conversation_id, order="asc") returns the messages you added, in ascending order, with role and content[0].text populated.

  • Turn 2 answers with a dog’s living quarters (for example a kennel) without you repeating the rabbit context — the model referenced the history you passed from the stored items.

  • Adding a flat body such as {"metadata": {…​}, "role": "user", "content": "…​"} to POST /v1/conversations/{id} returns HTTP 200 but stores nothing — the items list stays empty. This is the silent no-op the WARNING above describes.

  • After client.conversations.delete(conversation_id), GET /v1/conversations/{id} returns 404.

You now have a stateful, multi-turn chat working against OGX with the Conversations API. In the next module you will survey the advanced APIs and see exactly which of them run on this build.

Module summary

What you accomplished:

  • Connected an OpenAI SDK client to the shared workshop OGX server and verified it is healthy at version 1.4.2+rhaiv.0

  • Sanity-checked inference with Chat Completions against vllm-inference/aml-llama32-3b

  • Built a multi-turn, stateful chat: Conversations items persisted in the OpenAI array-wrapped shape, with history passed explicitly to Chat Completions

  • Identified what does not work on this build: the Responses API, the conversation parameter on Chat Completions, and flat conversation-item bodies

Key takeaways:

  • The OGX base_url must include the /v1 path suffix when using the OpenAI SDK

  • Conversation items persist only in the OpenAI array-wrapped shape — {"items":[{"type":"message","role":…​,"content":[{"type":"input_text","text":…​}]}]} — while flat single-item bodies return 200 but silently store nothing

  • On OGX 1.4.2+rhaiv.0 you drive multi-turn context by passing conversation history explicitly to chat.completions; the Responses API is not available on this build
